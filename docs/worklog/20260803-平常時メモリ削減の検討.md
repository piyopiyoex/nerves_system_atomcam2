# 2026-08-03 平常時メモリ削減の検討

## 文書情報

- 日付: 2026-08-03
- 種別: 設計検討
- 状態: 検討完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

RTSP 配信を含む常用時のメモリ逼迫を、方式 B(ネイティブ実装)の成否に
依存せず緩和するための提案。

関連: [RTSP 実装方針 技術相談](20260803-RTSP実装方針の調査.md)、
[長時間動作 記録](20260802-長時間動作の検証.md)

## 背景と目的

本機は Linux に 92MB(`MemTotal` 87,700 kB、スワップなし)しかなく、
ベンダーカメラ + RTSP を動かした常用時の `MemFree` は 2MB 前後まで下がる。
[長時間動作 記録](20260802-長時間動作の検証.md)で確認したとおり、停止の
主因はメモリリークではなかったが、**余裕が乏しいこと自体が長期運用の
安定性リスク**であり、大きめの転送やスパイクで飽和しやすい。

方式 B(`iCamera_app` を排除して 18MB 削減)は研究テーマで成否が読めない。
一方 **BEAM のメモリは、B の成否に関わらず常時効く削減余地**であり、
本提案の主対象とする。

## 実測ベースライン(2026-08-03、有線・ベンダーカメラ停止時)

### システム全体

| 項目 | 値 |
| --- | --- |
| MemTotal | 87,700 kB |
| ベンダー停止時 MemFree | 約 20,000〜25,000 kB(Cached 大) |
| **ベンダー + RTSP 稼働時 MemFree** | **約 1,500〜2,000 kB** |
| `beam.smp` RSS(最大の常駐プロセス) | 約 34MB |
| `iCamera_app` RSS(稼働時) | 約 18MB |

### BEAM 内部の内訳(`:erlang.memory/0`)

| 区分 | 値 | 内容 |
| --- | --- | --- |
| total | 26.4 MB | processes + system |
| system | 15.2 MB | ERTS 本体・アロケータ・コード索引など |
| code | 8.1 MB | ロード済み BEAM モジュール |
| processes | 11.3 MB | 全プロセスのヒープ・スタック |
| binary | 1.5 MB | |
| ets | 0.6 MB | |
| atom | 0.5 MB | |

`beam.smp` の RSS 34MB は、上記 total 26MB に ERTS 実行体・共有ライブラリ・
アロケータのキャリア断片が加わったもの。

### 既に最小化されている点

- **スケジューラは 1/1**(シングルコアを正しく検出)、非同期スレッド 1。
  スケジューラ数によるアロケータ多重化は起きていない
- リリースは `strip_beams` 済み(Docs のみ保持)

つまり「スケジューラ数を減らす」系の定番チューニングは既に効いており、
残る削減は **ロードするコード量・プロセス・アロケータ挙動**が対象。

## 削減レバー(期待効果順)

### A. 不要 OTP アプリの削減(code + processes に効く)

現在 34 個の OTP アプリが起動している。開発補助を含むため、本番で不要な
ものを外せば code(8MB)と processes を減らせる。候補と判断:

| アプリ | 役割 | 判断 |
| --- | --- | --- |
| `toolshed` / `iex` | SSH コンソールの対話環境 | **保持推奨**。実験機ではデバッグ価値が高い。外すと SSH で IEx が使えなくなる |
| `runtime_tools` / `sasl` | 実行時計測・SASL レポート | 計測に使わないなら削減候補 |
| `ring_logger` | リングバッファログ | 保持(障害解析に有用)。ただしバッファ縮小は可(下記 B) |
| `nerves_motd` | 起動時 MOTD 表示 | 削減候補(機能への影響なし) |
| `mdns_lite` | `nerves.local` 名前解決 | IP 固定運用なら削減候補。ただし利便性低下 |

**方法**: `mix.exs` の依存と `shoehorn` の起動リストから 1 つずつ外し、
各々の削減量を実測する。一度に外さない(切り分け不能になる)。

**リスク**: デバッグ性・利便性とのトレードオフ。実験機の位置づけを踏まえ、
`toolshed`/`iex`/`ring_logger` は残す前提で、それ以外を評価する。

### B. RingLogger のバッファ縮小(processes に効く)

`RingLogger.Server` は現状 RSS 約 587kB。バッファ長を既定から縮めれば
数百 kB 削減できる。障害解析に必要な最小限に調整する。

```elixir
config :ring_logger, buffer_size: 100   # 既定より小さく
```

### C. ERTS アロケータ調整(system 15MB に効く・実験的)

シングルスケジューラでもアロケータはキャリアを事前確保する。`vm.args` で
未使用メモリを OS へ返しやすくする設定を試す。効果は環境依存で**要実測**。

```text
+MBacul 0        # binary_alloc: 使用率に関わらずキャリアを解放
+Mut false       # 未使用アロケータの最適化を無効化
+MMsco true      # single carrier を優先し断片化を抑える
```

これらは**当たり外れがある**ため、1 設定ずつ入れて `:erlang.memory/0` と
`beam.smp` の RSS を前後比較する。悪化したら戻す。

### D. mdns_lite / vintage_net の設定見直し

- `mdns_lite` の通知サービス・ホスト数を必要最小限にする
- `vintage_net` のログレベル・スキャン頻度を見直す

効果は小さいが低リスク。

### E.(参考)iCamera_app は方式 B の範疇

常用時の第 2 の消費者は `iCamera_app`(18MB)。これは方式 B で
`iCamera_app` を自前実装に置き換えられれば削減できるが、本提案の対象外。
方式 B が成功すれば本提案の成果と合わせてさらに余裕が生まれる。

## 方法論

BEAM のメモリ削減は理論値が読みにくく、**実測駆動**で進める。

1. **1 変更ずつ**入れて、前後で `:erlang.memory/0` と `beam.smp` の RSS、
   および常用時(ベンダー + RTSP 稼働)の `MemFree` を比較する
2. 各変更後に**機能確認**(SSH、RTSP 配信、心拍、ファーム更新)を行い、
   デバッグ性を落としていないか確認する
3. **24 時間連続運転**で `MemFree` の推移を記録し、断片化による漸増が
   ないことを確認する(既存の `/data/sampler.exs` を流用)
4. 効果と副作用を記録し、正味プラスのものだけ採用する

## 段階計画

### フェーズ 1: 低リスクな確実分

- B(RingLogger 縮小)、D(mdns_lite/vintage_net)、A のうち機能影響のない
  もの(`nerves_motd` 等)。数百 kB〜1MB 級の確実な削減を積む

### フェーズ 2: アロケータ実験

- C を 1 設定ずつ実測。system(15MB)からの削減を狙う。効果が出れば
  最大の単一改善になりうるが、出ないこともある

### フェーズ 3: アプリ削減の評価

- A の削減候補を 1 つずつ外して実測。デバッグ性とのトレードオフを踏まえ、
  実験機として許容できる範囲を見極める

## リスクと注意

| リスク | 内容 | 対応 |
| --- | --- | --- |
| デバッグ性の低下 | `toolshed`/`iex`/`ring_logger` を外すと障害解析が困難に | これらは残す。外すのは補助アプリのみ |
| アロケータ設定の逆効果 | 断片化やスループット低下 | 1 設定ずつ、前後比較。悪化したら戻す |
| 見かけの削減 | RSS が減っても Cached を圧迫しては意味がない | 再利用可能メモリ(MemFree + Cached + Buffers)で評価する |
| 効果の過大評価 | 数百 kB の積み上げは 2MB の逼迫を根本解決しない | 本提案は「余裕の底上げ」。根本解決は方式 B(18MB)側 |

## 期待できる規模感

確実に取れるのはフェーズ 1・3 で合わせて **1〜3MB 程度**の見込み。
フェーズ 2(アロケータ)が当たれば追加で数 MB の可能性があるが不確実。
常用時 `MemFree` を 2MB から数 MB 台に押し上げ、スパイク耐性を上げるのが
現実的な到達目標。**根本的な余裕は方式 B の 18MB 削減**であり、本提案は
それまでの底上げと、B 成功後のさらなる最適化の両方に効く。
