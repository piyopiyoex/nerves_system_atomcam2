## 目的

MicroSD カードへ変更を加えずに、稼働中の Atom Cam 2 を調査し、ADR 0005 で安全に前提とできるファイルシステムとデバイスパスを確認する。

## 保護対象カーネル

書き込み可能な起動用ファイルシステム上のカーネルは、必須の SHA-256 と一致した。

```text
b50658eac32b57fdcb20383d82a54e6439acd7a3f7e9cb8b43edf4a4b89b03bc
```

稼働中のカーネルは次の版を報告した。

```text
Linux version 3.10.14__isvp_swan_1.0__
```

保護対象カーネルと、その検証方法には変更を加えていない。

## 現在の MicroSD 構成

`/proc/partitions` では、MicroSD デバイス一つと、その上のパーティション一つが確認された。

```text
179        0   15267840 mmcblk0
179        1   15266816 mmcblk0p1
```

関係するマウント状態は次のとおりであった。

```text
/dev/mmcblk0p1 /media/mmc vfat rw
/dev/mmcblk0p1 /boot vfat ro
/dev/loop0 / squashfs ro
```

`/dev/rootdisk0` の別名や、二番目の MicroSD パーティションは存在しなかった。現在の単一 FAT パーティションは媒体のほぼ全容量を占めるため、ADR 0005 の構成へ移行するには、既存媒体への上書き更新ではなく fwup の `complete` による再構築が必要である。

## 保護対象カーネルが対応するファイルシステム

`/proc/filesystems` では、次の関連ファイルシステムが確認された。

```text
ext2
squashfs
vfat
exfat
jffs2
```

ext4 と F2FS は報告されなかった。

したがって、保護対象カーネルを変更せず、通常の MicroSD ブロックパーティション上で Linux のファイルシステムとして必要な性質を備えることが確認できた候補は ext2 のみである。JFFS2 は生のフラッシュ向けであり、SquashFS は読み取り専用、FAT 系は意図する `/data` の性質を満たさない。

## 現在の利用者空間道具

現在のルートファイルシステムには、次の道具が含まれていなかった。

```text
mkfs.ext2
mke2fs
e2fsck
fsck.ext2
tune2fs
dumpe2fs
resize2fs
blkid
```

BusyBox の `lsblk` は存在したが、util-linux と同様の列指定には対応していなかった。

## 判断材料

ADR 0005 の最初の実装では ext2 を使用する。ただし、電源断と復旧の実機試験に合格することを条件とする。

`fwup.conf` を変更する前に、次を行う。

- e2fsprogs の作成・検査用道具をルートファイルシステムへ追加する。
- 作成したファームウェアに `mkfs.ext2`、`e2fsck`、`fsck.ext2` が含まれることを確認する。
- MicroSD の列挙順だけに依存せず、起動デバイスから導出した安定したアプリケーション用パーティションのパスを用意する。

ext2 にはジャーナルがない。書き込み中断と復旧の試験で不適切と判明した場合は実装を止め、保護対象カーネルの変更は別の意思決定として扱う。

## ext2 利用者空間道具の検証

`BR2_PACKAGE_E2FSPROGS=y` を有効にしてシステムを再構築し、検証済み Atom Cam 2 制御カーネルを使って見本アプリケーションのファームウェアへ組み込んだ。

最終的に統合された SquashFS に、次のファイルが含まれることを確認した。

- `/sbin/mke2fs`
- `/sbin/mkfs.ext2`
- `/sbin/e2fsck`
- `/sbin/fsck.ext2`

保存された統合済みルートファイルシステムは、次の性質を持つ。

- SHA-256: `989e7cfbf39734623a77ed35f563c9c7db566815cddb48e20e1093a9b229487d`
- 大きさ: `19144704` バイト
- ファームウェア UUID: `edd3b032-09f5-597f-0e92-ce1339c9a8a0`

既存の一パーティション Flat SD 構成で物理 Atom Cam 2 を起動し、次を確認した。

- `mke2fs`、`mkfs.ext2`、`e2fsck`、`fsck.ext2` は `/sbin` から解決できる。
- 四つの命令はいずれも実行できる。
- e2fsprogs の版は `1.47.4` である。
- `/proc/filesystems` に ext2 が存在する。
- 稼働中の制御カーネルの SHA-256 は引き続き必須値と一致する。

この検証ではファイルシステムの作成も、ブロックデバイスの変更も行っていない。保護対象カーネルと利用者空間が ext2 の作成・修復に対応することは確認できたが、パーティション作成、マウント、永続化、修復、電源断への耐性は別の節目とする。

## 安定したルートディスク別名の検証

### 実装の境界

標準的な Nerves のルートディスク別名を、独自 initramfs の変更で実現してはならない。生成カーネルは梱包時に保護対象 Atom Cam 2 制御カーネルへ置き換えられ、その SHA-256 が検証されるためである。

別名は、Erlang 起動前に書き込み可能なルートファイルシステムから `/usr/bin/atomcam2-pre-run` が作成する。

実装内容は次のとおりである。

- `/proc/mounts` から、マウント済みの起動用パーティションを特定する。
- 親の MMC ブロックデバイスを導出する。
- SD カード全体を示す `/dev/rootdisk0` を作成する。
- 起動用パーティションを示す `/dev/rootdisk0p1` を作成する。
- 二番目のパーティションが存在するときだけ `/dev/rootdisk0p2` を作成する。
- 二番目のパーティションがない場合は、古い `/dev/rootdisk0p2` を削除する。
- 事前実行用手順に必要な BusyBox の `ln` と `rm` を有効にする。

実装の記録は次のコミットである。

```text
3bce8ed feat(system): establish stable root disk aliases
```

### 最初の実機検証

最初のファームウェアは起動し、デバイス検出では期待するパスが得られた。

```text
root_disk=/dev/mmcblk0
boot_partition=/dev/mmcblk0p1
data_partition=/dev/mmcblk0p2
```

しかし事前実行報告は次を記録した。

```text
rootdisk_links=0
```

三つの別名はいずれも存在しなかった。

```text
/dev/rootdisk0=absent
/dev/rootdisk0p1=absent
/dev/rootdisk0p2=absent
```

対象には実行可能な `ln` がなく、`System.cmd("ln", ...)` は `:enoent` を返した。`/bin/busybox` は存在したが、`ln` 小道具は無効であった。

```text
ln: applet not found
```

そこで BusyBox に次を追加した。

```text
CONFIG_LN=y
CONFIG_RM=y
```

### 成功した実機検証

再構築したファームウェア UUID は次である。

```text
aca4fabc-c008-5727-b1f6-baff68bcd133
```

必要な命令が存在した。

```text
ln=/bin/ln
rm=/bin/rm
```

一パーティション構成の稼働中カードでは、次の別名が確認された。

```text
/dev/rootdisk0 -> /dev/mmcblk0
/dev/rootdisk0p1 -> /dev/mmcblk0p1
/dev/rootdisk0p2 absent
```

事前実行報告でも、別名作成が成功していた。

```text
stage=pre_run_complete
rootdisk_links=1
root_disk=/dev/mmcblk0
boot_partition=/dev/mmcblk0p1
data_partition=/dev/mmcblk0p2
hostname=nerves
wlan0_present=0
```

保護対象カーネルは変更されていない。この節目では、パーティションの作成、拡張、初期化、マウントなどを行っていない。

### 結論

保護対象カーネルを変更せず、物理 SD カードと既存起動用パーティションに対する安定したパスを用意できた。

```text
/dev/rootdisk0
/dev/rootdisk0p1
```

将来のデータ用別名は、`/dev/mmcblk0p2` が存在するまで意図的に作成しない。

```text
/dev/rootdisk0p2
```

これにより `fwup.conf` で ADR 0005 の構成を実装するためのデバイスパス前提が整った。ただし、パーティション作成、ext2 初期化、`/data` へのマウント、更新時の保持、工場出荷状態への初期化は未検証である。

## ホスト側パーティション構成の検証

### 実装

MicroSD は次の構成とする。

```text
partition 1: FAT boot and provisioning filesystem
partition 2: Linux application-data partition
```

起動用パーティションは 512 MiB に固定する。

```text
BOOT_PART_OFFSET=2048
BOOT_PART_COUNT=1048576
```

データ用パーティションは直後から始める。

```text
DATA_PART_OFFSET=BOOT_PART_OFFSET+BOOT_PART_COUNT
DATA_PART_COUNT=1048576
```

パーティション 2 は MBR 種別 `0x83` を使用し、媒体の残り全体へ拡張する。

`complete` はパーティション 2 を作成済みファイルシステムにせず、先頭を次のように無効化する。

```text
raw_memset(${DATA_PART_OFFSET}, 256, 0xff)
```

`upgrade` は両パーティションの期待位置を要求し、パーティション 1 の保護対象カーネルとルートファイルシステムだけを更新する。パーティション 2 には書き込まない。

実装の記録は次のコミットである。

```text
df62180 feat(system): add persistent data partition layout
```

### ファームウェア構築の検証

`ATOMCAM2_KERNEL_IMAGE` が保護対象制御カーネルを指すことを確認して再構築した。梱包されたカーネルの SHA-256 は変更されず、fwup 1.16.0 でファームウェア書庫を正常に構築できた。これにより、構成の解析と資源参照が成功することを確認した。

### `complete` の検証

`complete` を 2 GiB の通常ファイルへ適用した。物理ブロックデバイスや MicroSD には書き込んでいない。

結果の MBR は次のとおりである。

```text
partition 1:
  start=2048
  size=1048576
  type=c
  bootable=true

partition 2:
  start=1050624
  size=3143680
  type=83
```

これにより、パーティション 1 は 512 MiB のまま、パーティション 2 は直後から媒体末尾まで広がり、Linux 用 MBR 種別を使うことを確認した。パーティション 2 の先頭セクターはすべて `0xff` であり、ホスト側の調査でもファイルシステム署名は見つからなかった。

### `upgrade` による保持の検証

パーティション 2 に印を置いてから `upgrade` を適用した。先頭 1 MiB の SHA-256 は更新前後で同一であった。

```text
ab5df0f2d357f9458eee77fb40058e364cf9d12fef10fe0879f5b03653c1ae3f
```

パーティション表は変わらず、印もバイト単位で保持された。ホスト画像上で `upgrade` がデータ用パーティションを保持することを確認した。

### 旧構成の拒否

旧一パーティション構成だけを持つ別の 2 GiB 画像に `upgrade` を適用すると、必須のパーティション 2 がないため拒否された。

```text
fwup: Couldn't find applicable task 'upgrade'. If task is available, the task's requirements may not be met.
```

### 結論

ホスト側では次を確認した。

- `complete` は拡張可能な Linux データ用パーティションを別に作成する。
- `complete` はデータ用パーティションを未初期化状態にする。
- `upgrade` は新しい二パーティション構成を要求する。
- `upgrade` は旧一パーティション媒体を拒否する。
- `upgrade` はデータ用パーティションを保持する。
- 保護対象制御カーネルは変更されない。

初回起動時の ext2 作成、`/data` へのマウント、Nerves Runtime の初期化、NervesSSH・NervesTime の永続化、実機起動、修復、電源断、工場出荷状態への初期化は、この時点では未検証である。

## ファイルシステム復旧方針の調査

### 標準 Nerves Runtime の挙動

見本アプリケーションは `nerves_runtime 0.13.13` を固定している。`Nerves.Runtime.Init` は、おおむね次の順で動作する。

1. 現在のアプリケーション用パーティションのマウント状態を調べる。
2. `/data` が読み取り専用ならアンマウントする。
3. 読み書き可能でマウントを試みる。
4. マウントできなければ `mkfs.ext2` を実行する。
5. 再度読み書き可能でマウントする。

Atom Cam 2 では、初期化命令は次と同等になる。

```text
mkfs.ext2 -U 3041e38d-615b-48d4-affb-a7787b5c4c39 -F /dev/rootdisk0p2
```

標準初期化処理は、作成前に `e2fsck` を実行しない。そのため、明示的に未初期化にした状態、修復可能な障害、修復不能な障害、一時的なデバイス欠落を区別できず、単なるマウント失敗で復旧可能なデータを消すおそれがある。

### 独自初期化処理の境界

Nerves Runtime は次により初期化処理を差し替えられる。

```elixir
config :nerves_runtime, init_module: MyApp.FilesystemInit
```

一回だけ動作し `:ignore` を返す `GenServer` が、標準の境界に合う。対象命令の実行には `Nerves.Runtime.cmd/3` を再利用でき、実行ファイルがない場合は例外ではなく状態 `255` を返す。

### 無効化印の判定

`/dev/rootdisk0p2` の先頭 128 KiB を Elixir から直接読み取った。初期化済み物理ファイルシステムは次を返した。

```text
initialization_region_size: 131072
initialization_region_state: existing_filesystem
```

厳密に全バイトが `0xff` の場合だけ作成を許可し、読み取り失敗、短い読み取り、それ以外の内容は既存または不明な状態として扱う。

### 復旧方針

Atom Cam 2 では標準初期化処理を差し替える。

- 明示的な無効化印の場合だけ作成する。
- 既存ファイルシステムでマウントに失敗した場合は `e2fsck -p -f` を実行する。
- 状態 `0` または `1` の場合だけ再マウントする。
- 再起動必須値 `2` を含む状態、または失敗状態では `/data` をマウントしない。
- 既存または不明なファイルシステムを自動作成し直さない。

## 安全なファイルシステム初期化処理

コミット `244ef5e` で `Atomcam2NervesApp.FilesystemInit` と `:nerves_runtime, :init_module` の上書き、および印と修復状態に関する試験を追加した。

自動作成を許すのは、データ用パーティションの先頭 128 KiB が厳密に `0xff` の場合だけである。既存内容、未知の内容、短い読み取り、読み取り失敗、マウント失敗、検査失敗、実行ファイル欠落は、いずれも作成を許可しない。

既存または不明な状態では次を行う。

1. 読み書き可能なマウントを試す。
2. 失敗後に確実にアンマウントする。
3. `e2fsck -p -f` を実行する。
4. 状態 `0` または `1` のときだけ再マウントする。
5. それ以外では、作成せず `/data` を未マウントのままにする。

状態 `2` と `3` は再起動が必要として報告する。`6` など複合失敗状態では、失敗を優先する。

ホスト試験は当初 6 件、実際の `File.open/3` 戻り値に対する回帰試験追加後は 7 件すべて成功した。固定した `nerves_runtime 0.13.13` の利用 API と引数順も確認した。

対象ファームウェアは次である。

```text
UUID: 6b3b37d0-0484-515a-aac2-2294825a4e93
nickname: grunt-crucial
size: 20981813 bytes
creation time: 2026-07-20 10:56 JST
```

最終ルートファイルシステムには `Elixir.Atomcam2NervesApp.FilesystemInit.beam`、`sys.config` の上書き、期待するパーティション情報が含まれた。

## 独自初期化処理の実機検証

既存 ext2 を保持したまま fwup `upgrade` を適用し、パーティション表、ファイルシステム UUID、先頭 1 MiB、保護対象カーネル、永続化印、SSH 鍵、NervesTime 状態がすべて変化しないことを確認した。

起動後は `/dev/rootdisk0p2` から `/data` が ext2 で読み書き可能にマウントされ、初期化処理は一回だけ動作して終了した。正常な既存ファイルシステムは作成も修復もされず、通常再起動後も状態を保持した。

この時点では、明示的無効化印による作成、マウント失敗時の修復、再起動必須状態、電源断、工場出荷状態への初期化が未検証であった。

### 最初の安全な失敗

最初の起動では `/data` が作成・マウントされず、印は残った。原因は、コールバック付き `File.open/3` が `{:ok, region}` を返すのに、そのタプル全体を判定関数へ渡していたことだった。結果は `:unknown` となり、安全な `:mount_or_repair` が選ばれた。

この失敗により、認識できない読み取り結果が作成を許可しない安全性を確認できた。

コミット `8e18c27` で成功値を明示的に取り出すよう修正し、実際の戻り値形に対する回帰試験を追加した。

修正版ファームウェアは次である。

nickname: cloud-snack

## 修復可能な障害の事前認定

物理カードへ変更する前に、256 MiB の使い捨て ext2 画像で修復可能な障害を選定した。

```text
filesystem: ext2
block size: 4096 bytes
inode size: 256 bytes
host e2fsprogs: 1.47.2
```

### 却下した候補 A

主スーパーブロックの `s_first_data_block` を `0` から `1` へ変更すると、最初のマウントは失敗したが、`e2fsck -p -f` は状態 `8` を返し、代替スーパーブロックが必要になったため却下した。

### 採用した候補 B

ルート inode 2 の `i_blocks` だけを `8` から `0` へ変更した。ディレクトリの大きさとブロックポインタは維持した。

最初の読み書きマウントは次で失敗した。

```text
mount status: 32
error: Structure needs cleaning
```

`e2fsck -p -f` は次を報告した。

```text
Inode 2, i_blocks is 0, should be 8. FIXED.
```

状態は `1` で、修復後の読み書きマウントは成功した。UUID と既知ファイルのハッシュは変化せず、最後の検査は状態 `0` であった。この候補を物理試験用に採用した。

## 物理媒体での自動修復検証

### 復元用バックアップ

物理障害を加える直前に、次の完全画像を作成した。

```text
/home/mnishiguchi/Backups/atomcam2/20260720-before-filesystem-repair-test.img
```

SHA-256 は次である。

```text
182f98fcf550a9fed0c2efa9050cfa57e16025ad78bf1983333682e7a19cf7e5
```

15,634,268,160 バイトの物理カードと大きさ・内容が一致することを確認した。

### 書き込み前条件

物理ファイルシステムは次の状態であった。

```text
UUID: 3041e38d-615b-48d4-affb-a7787b5c4c39
block size: 4096
inode size: 256
mount count: 2
```

ルート inode の位置を物理メタデータから個別に導出した。

```text
inode table block: 903
inode table offset: 3698688
root inode offset: 3698944
root i_blocks offset: 3698972
whole-device i_blocks offset: 541618460
root mode: 0x41ed
root size: 4096
root first direct block: 1413
```

元の `i_blocks` は次である。

```text
08 00 00 00
```

### 制御した物理障害

パーティション 2 の該当四バイトだけを `8` から `0` へ変更した。

```text
before: 08 00 00 00
after:  00 00 00 00
```

書き込み手順は、対象デバイス、ファイルシステム形状、元バイトを再確認し、四バイトだけを書き込み、同期・読み戻しを行い、周囲の inode バイトが変化していないことを確認した。パーティション表、保護対象カーネル、先頭 128 KiB は変化しなかった。

### 対象上での修復

最初の起動でカーネルは次を報告した。

```text
EXT2-fs (mmcblk0p2): error: corrupt root inode, run e2fsck
```

独自初期化処理は既存ファイルシステムとして `mount_or_repair` を選び、修復後に `/data` を読み書き可能でマウントした。

修復後のルート inode は次であった。

```text
inode table block: 903
inode table offset: 3698688
root inode offset: 3698944
root i_blocks offset: 3698972
root mode: 16877
root size: 4096
root i_blocks: 8
root i_blocks bytes: 08000000
root first direct block: 1413
```

対象が意図的に壊した値を `0` から `8` へ戻してから `/data` をマウントしたことを確認した。

ファイルシステム UUID、永続化印、SSH ホスト鍵、認証鍵、NervesTime 状態は保持された。保護対象カーネルとパーティション構成も変化しなかった。

## 修復後の再起動と最終オフライン検証

修復済みファイルシステムで通常再起動し、再度 `/data` が読み書き可能でマウントされ、ルート inode と永続データが保持されることを確認した。新たな root inode 破損メッセージは出なかった。

その後 `Nerves.Runtime.poweroff/0` で正常終了し、ホストで未マウント状態を確認した。オフライン ext2 情報は次であった。

```text
filesystem UUID: 3041e38d-615b-48d4-affb-a7787b5c4c39
filesystem state: clean
block size: 4096
inode size: 256
mount count: 2
```

ホストで次を実行した。

```sh
e2fsck -f -n /dev/sda2
```

五段階すべてを完了し、状態 `0` を返した。

```text
files: 17 of 922080
blocks: 66877 of 3685632
```

### 最終結論

物理試験により、次を確認した。

- 厳密な無効化印だけを認識し、その場合だけ作成する。
- 既存ファイルシステムの内容は保持対象として扱う。
- 破損した ext2 ルート inode は最初のマウントで拒否される。
- 対象上で無人修復を実行できる。
- 修復状態 `1` を受け入れて再マウントする。
- 意図的に壊した inode 情報を復元する。
- 修復済みファイルシステムを読み書き可能でマウントする。
- UUID とアプリケーションデータを保持する。
- 通常再起動後も動作する。
- 正常終了後に clean 状態となる。
- 最終オフライン検査が状態 `0` で成功する。

試験中、保護対象制御カーネル、パーティション構成、安定したデバイス別名、永続状態の場所は維持された。

ADR 0005 を受理する前に必要な物理検証は完了した。このコミットでは、状態変更を別に確認・記録できるよう、ADR 0005 は引き続き Proposed のままとする。
