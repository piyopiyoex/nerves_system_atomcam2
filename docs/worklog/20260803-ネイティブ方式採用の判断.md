## 相談の要点

ベンダーアプリ `iCamera_app` を排除し、Ingenic の libimp を自前で駆動して
RTSP 配信する「方式 B」の本格着手を検討している。設計と計画は
[提案書](20260803-iCamera非依存RTSP配信の検討.md)にまとめた。着手前に、
**投資判断とリスクの潰し方**について助言をいただきたい。個々の症状ではなく、
「この計画は筋が良いか」「最初に何を確かめれば無駄足を避けられるか」が論点。

前回の相談([ネイティブカメラ実装 技術相談](20260803-ネイティブカメラ実装の調査.md))は
`IMP_System_Init` の停止という**症状**の切り分けだった。今回はその助言
(「実機の libimp.so をそのまま使え」)を受けて計画を立て直した上での、
**推進の是非とビルド戦略**の相談。

## これまでに確定した事実

| 項目 | 状態 |
| --- | --- |
| センサー | GC2053(I2C `0x37`)。実機に `sensor_gc2053_t31.ko` |
| ISP / エンコーダ | `tx_isp_t31.ko` / `avpu.ko`。実機に存在 |
| libimp | 実機 `/atom/system/lib/libimp.so`(1.1.1、**uClibc 0.9.33.2 / GCC 4.7.2** ビルド) |
| uClibc ランタイム | 実機 `/atom/lib/` に一式(`ld-uClibc.so.0`、0.9.33.2) |
| デバイスノード | `iCamera_app` なしで、モジュール insmod だけで生成されることを確認済み |
| float ABI | musl(soft-float)と libimp(hard-float)は別プロセスにすれば共存可。理解確認済み |
| 後段 | v4l2loopback + v4l2rtspserver は実機で配信実績あり(再利用可能) |
| メモリ予約 | `mem=92M rmem=36M`。ISP/VPU バッファは rmem 側で RSS に出ない見込み |

## 提案しているアーキテクチャ

```text
Nerves（musl/soft-float）
  └ CameraNative GenServer（監督・自動再起動）
       │ loopback + 状態ファイル（ABI 非依存のバイト列）
  atomcam2-camera（uClibc/hard-float、実機 libimp.so を動的リンク）
       └ IMP_System_Init → ISP → sensor → framesource → encoder
             → エンコード済みフレームを /dev/video0 へ write()
  /dev/video0（v4l2loopback、既存）→ v4l2rtspserver（既存）→ RTSP
```

要点は「**後段(配信)は再利用し、前段(libimp 駆動)だけを新規に作る**」こと。

## 未解決の最大リスクと、想定している対処

### リスク 1: 実機の古い uClibc 0.9.33.2 に対してどうビルドするか(最重要)

実機 libimp は **uClibc 0.9.33.2 / GCC 4.7.2**(2012 年頃)でビルドされている。
この libimp.so を動的リンクする自前プログラムを、どのツールチェーンで
ビルドすべきか。候補:

- **(a) Ingenic 純正の GCC 4.7.2 + uClibc 0.9.33.2 ツールチェーンを入手**して
  ビルド。実機と完全一致するが、入手性が課題
- **(b) 実機の `/atom/lib` を sysroot として使い**、モダンなコンパイラで
  リンク。uClibc の ABI 互換性(0.9.33.2 と新しめの GCC)が不安
- **(c) chroot 実行前提**にして、ビルドの libc 版差を実行時に吸収する
- **(d) 静的リンクは不可**(libimp は uClibc に動的依存する .so のため)

**この点が最大の不確実要素**。同種の Ingenic 機を触っている立場から、
**現実的にどの経路を採るべきか**を知りたい。

### リスク 2: libimp を「別プロセスから叩くだけ」で本当に動くか

ベンダーは `iCamera_app` の前に `ver-comp` を実行している。ISP/センサーの
初期化に、モジュール insmod と `IMP_System_Init` 以外の**ベンダー固有の
前処理**(共有メモリキー、`/proc`・`/sys` の設定、特定の初期化順序、
センサー電源/リセット GPIO)が隠れている可能性がある。

- libimp は「モジュールをロードして `IMP_System_Init` を呼べば動く」設計か、
  それとも**ベンダーの init スクリプト群と密結合**していて、単体プロセスでは
  埋められない前提があるか
- あるなら、`ver-comp` の `open`/`ioctl`/`/proc` アクセスを観察して再現する
  想定だが、この方針で十分か

### リスク 3: 配信経路の選択(loopback 経由か、RTSP 内蔵か)

提案では既存の v4l2loopback + v4l2rtspserver を再利用し、ネイティブプロセスは
`/dev/videoN` へ書くだけにしている。一方 thingino の prudynt-t は libimp の
上に RTSP を内蔵する。

- **loopback 再利用**(開発量小、実績ある後段をそのまま)と
  **prudynt-t 移植**(一体だが、prudynt は OpenIPC カーネル前提で SDK 系統も
  異なる)、どちらが筋が良いか
- prudynt-t も別 OEM の libimp/SDK でビルドされているなら、リスク 1 と同じ
  「ビルド系統不一致」を抱えないか

## 質問したいこと

1. **リスク 1(uClibc ビルド戦略)の最善手は。**
   実機の古い uClibc 0.9.33.2 libimp を使う前提で、(a)〜(c) のどれが現実的か。
   他に定石があれば

2. **libimp は単体プロセスで駆動可能か。**
   モジュール + `IMP_System_Init` だけで足りるか、`ver-comp` 等の前処理が
   本質的に必要か。必要なら、それを見つける最短の方法は

3. **配信経路は loopback 再利用と prudynt-t 移植のどちらが妥当か。**

4. **メモリ見積もりの妥当性。**
   ISP/エンコーダのバッファが rmem(予約 36MB)側で、プロセス RSS に
   出ないという理解は正しいか。ネイティブプロセスの RSS を 3〜6MB と
   見積もっているが、この規模感は妥当か

5. **投資判断: 最初に潰すべき単一の不確実性は何か。**
   本格着手の前に「これが駄目なら方式 B は筋が悪い」と分かる、最小の実験は
   何か。工数を大きく使う前の go/no-go を早く出したい

6. **見落としているリスク・別の道は。**
   例えば、ベンダーの `rtsp` バイナリや `sdkshellcalltool` を使う道、あるいは
   方式 B を諦めて方式 A+C(監視強化)に集中すべきという判断もありうるか

## 判断材料(背景)

- 方式 B は[実装方針の相談](20260803-RTSP実装方針の調査.md)で

- 実験機の位置づけで、まず「動く」ことを重視している
- 先行事例 [atomcam_tools](https://github.com/mnakada/atomcam_tools) は
  **glibc + ベンダーファーム上**で libimp を使っており、本件のように別
  ユーザー空間(Nerves)へ統合した前例はない

## 結論(2026-08-03): 採用した進め方

セカンドオピニオンを受けて方針を確定した。**計画自体は技術的に筋が良い。
ただし最大の未証明点は RTSP でも libimp でもなく「古い Ingenic SDK を自前
プロセスから再利用できること」の一点**であり、ここを 1〜2 日の最小実験で
go/no-go 判定してから本格着手する。

### 投資判断

**方式 A を維持しつつ、方式 B を研究テーマとして並行開発**する。方式 A は
既に価値を生んでおり、B は成功すれば価値が大きく、失敗しても A に戻れる。
この条件ならリスクは限定される。

### go/no-go 実験: 最小の "Hello libimp"

**RTSP・エンコーダ・フレーム・Nerves 連携を一切入れない。**

```c
int main(void) {
    IMP_System_Init();
    printf("OK\n");   /* fflush 必須 */
    IMP_System_Exit();
}
```

これが自前プロセスで正常終了すれば、方式 B の成功確率は一気に上がる。
通らなければ、その理由を調べるだけで済む。**「RTSP が流れること」ではなく
「`IMP_System_Init()` が単独で成功すること」を最初の判定基準に据える**のが
最も投資効率が高い。

### ビルド戦略の優先順位(確定)

1. **(a) 純正 Ingenic SDK のクロスツールチェーン(GCC 4.7.2 / uClibc
   0.9.33.2)を探す** — 第一候補。libimp は「同じ SDK 前提」で作られており、
   ABI 以外にも TLS・crt・startup・relocation・libgcc まで一致させたい
2. **(b) 実機 `/atom/lib` を sysroot にする** — 見つからない場合の次善。
   ただし **C++ は使わない**(libstdc++ が絡むと破綻する)。純 C で通す
3. **(c) chroot は実行環境の話でビルド問題の解決にならない**(gcc が生成する
   バイナリは変わらない)

### 初期化の盗み方(リスク 2 への対処)

- カーネル側初期化(insmod でデバイスノード生成)は済んでいる。残るは
  `IMP_System_Init()` が期待する **`/proc`・`/sys`・GPIO・共有メモリ・
  セマフォ・daemon 通信**のいずれか
- **`ver-comp` を strace し**、`open`/`openat`/`ioctl`/`mmap`/`shm*`/`sem*`/
  `connect`/`socket`/`readlink` と `/proc`・`/sys`・`/dev` アクセスだけ抽出。
  「実は一回これを書いている」が見える可能性がある
- 有望な実験: **`ver-comp` を先に起動・終了させてから**自前プロセスで
  `IMP_System_Init` を呼ぶ。動けば「初期化だけ盗めば済む」

### 見落としがちなリスク(助言で追加)

- **センサー登録**: GC2053 を tx-isp へ登録する処理を `iCamera_app` が
  行っている可能性。センサドライバがロード済みでも libimp から見えない
  ことがある。strace で `ioctl` に現れる
- **`sdkshellcalltool`**: `ver-comp` より重要な可能性。起動順が
  `iCamera_app → sdkshellcalltool → libimp` なら観察対象に加える

### 確定した論点

- **配信経路は loopback 継続**(迷わない)。後段は既に動いており、prudynt-t
  移植は SDK 差分問題を蒸し返すだけ。**論点を増やさない**
- **メモリ見積もりは妥当**。ISP/VPU/フレームバッファは rmem/CMA 側で RSS に
  出ない。RSS 増は stack・heap・libimp.so・libc・小さな queue 程度で、
  3〜6MB(むしろ 2〜4MB でも驚かない)

### 実施順序(確定)

1. 純正 SDK クロスツールチェーンを探す(見つかれば以後の不確実性が激減)
2. 最小プログラム(`IMP_System_Init` → `IMP_System_Exit`)を作る
3. `ver-comp` を strace し、自前プロセスとのアクセス差分を見る
4. `IMP_System_Init` が単独成功した時点で **go 判断**。以後 ISP →
   FrameSource → Encoder → `/dev/video0` を一段ずつ追加
5. 最後に Nerves との GenServer 統合

この順序なら最大の不確実性を最初の数日で評価でき、失敗しても投下工数を
最小化できる。

## スパイク結果(2026-08-03): GO

**go/no-go の判定基準「`IMP_System_Init()` が自前プロセスで正常終了する」を
達成した。方式 B は GO。** タイムボックス Day 1〜2 相当を 1 セッションで通過。

### 実行結果

```text
hello-libimp: calling IMP_System_Init()
---- FPGA board is ready ----
  Board UID : 30AB6E51 / HW ID : 72000460 / rev : 5DE5A975 / date : 20190326
-----------------------------
hello-libimp: IMP_System_Init() = 0
hello-libimp: OK
hello-libimp: IMP_System_Exit() returned
```

**`iCamera_app` なし・`ver-comp` なし・ベンダー init スクリプトなしで、
`IMP_System_Init()` が戻り値 0(成功)で完走した。** 前回のハング(方式 B
試行 2)は SDK ビルド系統の不一致が原因だったと確定。

### 成功に至った鍵

1. **純正ツールチェーンの入手**: `Dafang-Hacks/mips-gcc472-glibc216-64bit`。
   実機と完全一致する **Ingenic r2.3.3 2016.12 GCC 4.7.2 / uClibc**
   (`mips-linux-uclibc-gnu-gcc`)。FP ABI も hard-float で一致
2. **実機の libimp をそのまま使用**(セカンドオピニオンの助言どおり)。
   `/atom/system/lib` の `libimp.so` / `libalog.so` / `libsysutils.so` を
   動的リンク
3. **インタプリタパスの解決**: ビルド時に
   `-Wl,--dynamic-linker=/atom/lib/ld-uClibc.so.0` を指定。Nerves ルートには
   `/lib/ld-uClibc.so.0` が無いため
4. **カーネルモジュール**: `tx_isp_t31` / `sensor_gc2053_t31` / `avpu` を
   insmod(既にロード済みでも可)
5. 実行: `LD_LIBRARY_PATH=/atom/system/lib:/atom/lib`、`/data` から実行
   (`/tmp` は noexec)

### 途中の紛らわしい誤検知(記録)

動的リンカを明示起動(`ld-uClibc.so.0 ./prog`)したとき
「Standalone execution is not enabled」と出たが、これは**この古い uClibc の
ldso が standalone 起動を無効化しているだけ**で、ベンダーのゲートではなかった。
`--dynamic-linker` でインタプリタを埋め込み、直接実行することで解消した。

### 追加で判明した重大リスクと解決(エンコーダ ABI)
当初の想定になかった落とし穴として、**エンコーダ API だけ SDK バージョン間で
ABI が非互換**だった。デバイス libimp は T31 1.1.1 の新 API
(`IMP_Encoder_SetDefaultParam`)で、atomcam_tools サンプルの旧ヘッダでは
`invalid resolution(0x0)` になる。正しい 1.1.1 ヘッダを GitHub
`cgrrty/Ingenic-SDK-T31-1.1.1-20200508` から取得して解決。ストリームは
`IMPEncoderPack.offset`(絶対アドレスでない)+ リング折り返しで読む。
→ **リスク 1(ビルド)・リスク 2(標準実行)に続き、エンコード実装リスクも解消**。

### 残りのステージ
Stage 4: エンコード出力を v4l2loopback(`/dev/video0`)へ書き出し、既存の
v4l2rtspserver で配信(= 方式A と同じ後段に native ソースを差し込む)。
Stage 5: `atomcam2-camera` パッケージ化 + `CameraNative` GenServer 化。
メモリ削減の実測は Stage 4 の常駐形態で取得する。
