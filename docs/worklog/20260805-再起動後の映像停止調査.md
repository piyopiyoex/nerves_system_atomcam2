# 2026-08-05 再起動後の映像停止調査

## 文書情報

- 日付: 2026-08-05
- 種別: 技術調査
- 状態: 調査完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

native カメラ(`camd` + libimp, Ingenic T31)で、**ソフト再起動 / camd の
kill を経ると、次回起動で初期化 API はすべて成功(戻り値 0)するのに
エンコーダにフレームが 1 枚も渡らず、RTSP が上がらない**不具合(従来の
「問題B」)。今回、sprop 欠落(問題C)の恒久対策を入れて実機検証しようと
した際に問題Bで再現し、**安定起動の本質的ブロッカー**として浮上した。

**問題Bが解けない限り、問題Cの対策も動作確認できない**(フレームが
流れて初めて SPS/PPS を prepend できるため)。順序として問題Bの解決を
優先したい。

各項目は **観測事実 / 有力仮説 / 未解明事項** に分けて記す。

対象: AtomCam2(Ingenic T31 + GC2053)、Nerves(BEAM)+ native `camd`
(C, uClibc, libimp 1.1.1)。camd は `MuonTrap.Daemon` が OS プロセスとして
監督し、終了すれば再起動する。関連:
[native カメラ不具合 技術相談](20260804-ネイティブカメラ不具合の調査.md)問題B、
[RTSP sprop 欠落 技術相談](20260805-RTSP初期情報欠落の調査.md)。

## 1. 観測事実

### 1-1. 今回の再現ログ(OTA ソフト再起動後、192.168.31.31)

camd の初期化は**全て成功**し、main ループ直前まで到達:

```
camd: IMP_ISP_EnableTuning       = 0
camd: FrameSource_CreateChn      = 0
camd: Encoder_CreateChn          = 0
camd: Encoder_RegisterChn        = 0
camd: Encoder_CreateChn(jpeg)    = 0
camd: Bind FS->OSD               = 0
camd: Bind OSD->ENC              = 0
camd: IMP_OSD_Start              = 0
camd: FrameSource_EnableChn      = 0
camd: loopback ready             = 0
camd: Encoder_StartRecvPic       = 0
camd: night -> off (ircut+ir led)
camd: running at 3000 kbps. control via /tmp/camd.ctl
camd:   clock/logo ... / quit          ← ここが最新ログ(main ループ直前)
```

- **この後が一切出ない**。main ループには
  `PollingStream(CHN,1000)` の直後に `i<30` で毎フレーム
  `camd: dbg i=%d PollingStream=%d got=%d` を出す診断がある。**その 1 行目
  すら出ない** = 最初の `IMP_Encoder_PollingStream` が(1 秒タイムアウトの
  はずが)**返ってこない**。
- **【最重要】これは「フレームが来ない」以前に、API 仕様との乖離**。
  `IMP_Encoder_PollingStream(CHN, 1000)` は 1000ms で必ず timeout(≠0 or
  -1)を返すべき API。**その timeout すら返らない**のは、単なる無フレーム
  ではなく、**libimp 内部またはカーネルドライバ側の待ち状態(wait_event /
  sem_wait / futex 等)が壊れて解除されない**ことを示唆する。teardown 仮説
  以上に価値のある手掛かり(セカンドオピニオン §7)。次段の `strace -tt`
  で「ioctl(ドライバ待ち)/ poll(FD 待ち)/ futex(libimp ロック)」の
  どれで止まっているかを一点特定できる。
- センサは通電・streaming(dmesg で `gc2053` 認識)。
- `/tmp/camd.ready` **未作成** → `v4l2rtspserver` 起動せず(TCP 8554 closed)。
- CameraNative は `phase: :starting` のまま。

### 1-2. 物理電源断(パワーサイクル)でのみ復旧

同一個体で、**電源を抜き差しすると正常化**(フレームが流れ RTSP 復旧、
SDP に sprop も入る)。**ソフト再起動では復旧しない**ことを繰り返し確認。
発生は間欠的だが、**反復 kill / ソフト再起動の後に出やすい**。

### 1-3. camd は teardown を持つが、正常終了時しか走らない

`camd.c` は完全な後始末シーケンスを持つ(行 733-752):

```c
/* for ループが break した後にだけ実行される */
IMP_Encoder_StopRecvPic(CHN);
IMP_FrameSource_DisableChn(CHN);
IMP_System_UnBind(&osd_cell, &enc_cell);
IMP_System_UnBind(&fs_cell, &osd_cell);
IMP_OSD_DestroyGroup(GRP);
IMP_Encoder_DestroyChn(CHN);
IMP_Encoder_DestroyGroup(CHN);
IMP_FrameSource_DestroyChn(CHN);
IMP_System_Exit();
IMP_ISP_DisableSensor();
IMP_ISP_DelSensor(&si);
IMP_ISP_Close();
```

- for ループを抜けるのは **`quit` 制御コマンド** か **frames 上限到達**の
  ときだけ。
- **SIGTERM / SIGINT のハンドラが無い**。`MuonTrap.Daemon` がプロセスを
  終了させる(通常 SIGTERM → 猶予後 SIGKILL)とき、**この teardown は
  一切走らず、`IMP_System_Exit` / `DisableSensor` も呼ばれない**。

### 1-4. 補足

- 修正版 camd(VERSION 8、問題C対策)はデプロイ済みだが、上記 1-1 の
  wedge 状態のため**動作未検証**。問題C対策は問題Bとは独立で、フレームが
  流れれば有効になる設計。

## 2. 有力仮説(確率評価つき)

共通の骨子は「**ソフト終了時に何か重要な後始末が行われず**、次回 init は
各 API が 0 を返す(ただし『Create 成功 ≠ 新規生成』の可能性あり、後述)が
実際にはパイプラインが起動せず、`PollingStream` の内部待ちが壊れて返らない。
ソフト再起動ではリセットされず、パワーサイクルでのみ復旧する」。
**「SIGTERM/teardown 不足が主因」とまでは断定しない**(セカンドオピニオン
§7 の是正)。候補を確率で並べる:

| 仮説 | 主観確率 | 補足 |
| --- | --- | --- |
| teardown 不足で IMP 状態が残る | 40〜50% | 1-3 と整合。ただし未証明 |
| ISP/Encoder ドライバが HW を完全リセットできない | 30〜40% | 1-2(電源断でのみ復旧)と整合 |
| libimp 内部のデッドロック/待ち状態 | 10〜20% | 1-1(timeout すら返らない)と整合 |
| その他 | 〜5% | |

- 補足: **`IMP_Encoder_CreateChn` 等が 0 を返しても「既存 Channel を
  返しただけ」**の実装があり得る(SDK では珍しくない)。= init 成功が
  「新規生成」を意味しない可能性。これは teardown 不足仮説を補強する。
- 機序整合: 1-3(teardown が kill 時に走らない)+ 1-1(次回 init は 0 だが
  無フレーム・`PollingStream` が返らない)+ 1-2(電源断でのみ復旧)。

## 3. 未解明事項(切り分け未実施)

- **真因未確定**。「ソフト状態(IMP のプロセス外リソース / ドライバ状態)が
  汚れている」のか、「T31 映像 HW が物理的にリセットを要する」のか、
  **まだ切り分けていない**。これが核心。
- `IMP_System_Exit` 等の teardown が **プロセスをまたいで**状態を戻すのか、
  それともドライバ(`tx_isp` 等カーネルモジュール)側にしか効かないのか。
- `MuonTrap.Daemon` が送るシグナルと猶予時間の実際(SIGTERM の有無、
  SIGKILL までの秒数)。camd が SIGTERM を捕捉して teardown する時間が
  あるか。
- **`PollingStream` が「返らない」理由**: エンコーダにフレームが来ない
  (FrameSource/IPU が出していない)のか、エンコーダ内部で待っているのか。
- ドライバ再ロード(`rmmod tx_isp; insmod tx_isp`)や sysfs 経由で映像
  ブロックをソフトリセットできるか(未調査)。

## 4. 検討中の対策と、相談したい論点

### 案0: 終了方法を変えた反復再起動試験 + strace(最優先の切り分け)
セカンドオピニオン推奨。**対策より先にこれで原因帯を確定する。**

- **終了方法 3 通りを各 ~100 回**再起動して再現率を比較:
  ① `quit` 制御コマンド → 正常 teardown 経路 → MuonTrap 再起動
  ② SIGTERM → (現状ハンドラ無し=即死)
  ③ SIGKILL → 即死
  判定: **③だけ壊れる → ほぼ teardown 不足**。**②でも壊れる →
  SIGTERM 処理不足**。**①でも壊れる → IMP 自体の再初期化能力の問題**
  (teardown を通しても駄目 = HW/ドライバ寄り)。
- **wedge 個体で `strace -tt -p <camd>`**: `PollingStream` が
  `ioctl`(ドライバ待ち)/ `poll`(FD 待ち)/ `futex`(libimp ロック)の
  どこで止まっているかを一点特定(1-1 の API 仕様乖離の正体)。
- **`IMP_Encoder_GetFd()` + `select()`** が使えるなら、`PollingStream` の
  代わりに正規 FD 監視ルートへ。停止箇所の切り分けも容易。

### 案1: camd に SIGTERM ハンドラを入れ、正常 teardown を通す(切り分けの要)
- SIGTERM/SIGINT を捕捉して for ループの `quit` を立て、既存の teardown
  (`IMP_System_Exit` 他)を実行してから exit する。
- **これで「ソフト再起動でも復旧する」なら原因はソフト状態、しなければ
  HW リセットが要る、と確定できる**(最重要の切り分け)。
- **論点(1)**: MuonTrap の SIGTERM 猶予内に teardown(センサ停止含む、
  数百 ms〜秒)を完了できるか。猶予を延ばす設定が要るか。
- **論点(2)**: libimp はスレッドセーフ非保証。シグナルハンドラ内で
  IMP API を直接呼ぶのは危険なので、ハンドラでは flag セットのみにし、
  main ループが抜けて teardown する形が妥当か(ただし PollingStream が
  ブロック中だと抜けられない懸念 → 論点3)。

### 案2: 起動時に「防御的 teardown / リセット」を先に行う(セカンドオピニオンは反対)
- camd 起動直後、init 前に `IMP_System_Exit` 等で前回の残骸を掃除してから
  init する。ただし未 init 状態で Exit を呼ぶ副作用が不明。
- **セカンドオピニオンは反対**: SDK は「Init 前 Exit」を想定していない
  ことが多く、未初期化状態への Exit は実装依存で危険。**採らない方針**。

### 案3: 無フレーム検出 → 自己終了 → 段階的エスカレーション
- `PollingStream` を短いタイムアウトで回し、**N 秒フレームが来なければ
  camd を自己 exit**(MuonTrap が再起動)。それでも駄目なら
  `Nerves.Runtime.reboot()`、なお駄目ならハード的手段、と段階化。
- **論点(4)**: ただし 1-1 では PollingStream 自体が返らない(タイムアウト
  無視)。タイムアウトを効かせる方法、または別スレッド/`IMP_Encoder_GetFd`
  + select で監視して wedge を検出する方法はあるか。

### 案4: ドライバ / HW レベルのソフトリセット(最終手段)
- `tx_isp` 等カーネルモジュールの再ロード、または T31 の映像ブロックを
  sysfs/レジスタ経由でリセットして、パワーサイクル無しで復旧できるか。
- **論点(5)**: これは実現可能か。可能なら安定起動を完全にソフトで
  担保できる。
- **セカンドオピニオン注意**: sensor → ISP → FrameSource → Encoder → OSD が
  密結合で、`tx_isp` だけ reload しても済まない/かえって壊す恐れ。**最後の
  手段**に留める。

### 全体の論点
- **論点(6)**: 安定起動の観点で、どれを本命に据えるべきか。私は
  「案1(SIGTERM teardown)で切り分け → ソフト起因なら案1で解決、
  HW 起因なら案3/案4」の順を想定しているが妥当か。
- **論点(7)**: そもそも teardown を毎回確実に通せれば、wedge は起きない
  のか(=正常 kill さえ保証すれば運用上は十分か)。OTA 更新のたびに
  ソフト再起動が入るため、ここが担保できないと運用が不安定。

## 5. 制約と前提

- H.264 RTSP 配信は既存の主機能。**回帰厳禁**。
- `camd` は libimp を叩く単一スレッド C デーモン。libimp はスレッド
  セーフ非保証(ロック順序非公開)。
- メモリ厳しい(Linux から見える RAM 85MB、rmem 予約 36MB)。
- 制御カーネル(`factory_t31_ZMC6tiIDQN`)は差し替え禁止。ドライバは
  vermagic 一致のためだけに Buildroot でビルドしている。
- OTA(`mix upload`)は必ずソフト再起動を伴う。**運用上、ソフト再起動で
  確実に復旧できることが安定起動の要**。
- 現状 2 個体: 192.168.1.77(過去に sprop あり・正常)、192.168.31.31
  (今回 OTA 後に問題B wedge、要パワーサイクル)。

## 6. 求める意見(要約)

1. **切り分け方針**: 案1(SIGTERM teardown)で「ソフト状態 vs HW リセット
   要」を切り分ける、という進め方は妥当か。他に決定的な切り分けは。
2. **teardown が kill 時に走らない**ことが問題Bの主因、という仮説の当否。
3. `PollingStream` が返らない wedge を **camd 側で検出・自己回復**する
   現実的手段(GetFd+select、別スレッド監視、タイムアウト強制)。
4. ソフトのみで T31 映像ブロックを**リセットする手段**(ドライバ再ロード等)
   の有無。
5. 全体の優先順位(安定起動を最短で担保する道筋)。

## 7. セカンドオピニオン回答(2026-08-05)と方針確定

### 是正点
- **「SIGTERM/teardown が主因」と断定しない**。観測からは「ソフト終了時に
  重要な後始末が行われない」までが自然で、主因は確率で持つ(§2 に反映)。
- **最重要手掛かりは `PollingStream` が timeout すら返さない = API 仕様との
  乖離**(§1-1 に強調追記)。libimp 内部/ドライバの待ち状態が壊れている
  可能性で、teardown 仮説より価値が高い。
- **`CreateChn`=0 が「新規生成」を意味しない**可能性(既存 Channel を返す
  実装)。
- SIGTERM ハンドラは賛成だが **ハンドラ内で IMP API を呼ばない**
  (`volatile sig_atomic_t quit` を立てるだけ、teardown は main で)。
  ただし **`PollingStream` が返らないと flag を見に行けない**のが本質的
  課題(→ 案0 の strace / GetFd で先に停止箇所を潰す)。
- **案2(Init 前 Exit)は反対**、**案4(ドライバ reload)は最終手段**。

### 確定した進行順序(安定起動確立まで)
1. **`quit` 正常終了で ~100 回の再起動試験**(teardown を通した場合の
   再現性確認)。
2. **`strace -tt` / `IMP_Encoder_GetFd()`** で `PollingStream` の停止箇所を
   特定。
3. **SIGTERM ハンドラ追加**(flag のみ)で正常 teardown 経路へ誘導。
4. なお再現するときのみ、ドライバ再ロード / 映像 HW ソフトリセットを検討。
5. **問題Bが解決し安定起動が確立してから、問題C(SPS/PPS 周期送出・
   READY タイミング=VERSION 8)の検証へ**。

> 総合評価: 論点整理は良好。技術的な唯一の是正は、teardown を第一原因と
> 断定しないこと、および「API 仕様との乖離(timeout 不返し)」を最重要
> 手掛かりとして強調すること(本節・§1-1・§2 で反映済み)。
