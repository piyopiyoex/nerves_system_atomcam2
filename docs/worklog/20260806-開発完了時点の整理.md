## 1. 今日判明した真因と修正

### (A) RTSP がダッシュボード ON で無出力 wedge する

- ダッシュボードの映像タブが `/snapshot.jpg` を毎秒ポーリング →
  camd の **JPEG エンコーダチャンネルが H.264 チャンネルとバッファを
  共有**していたため、並行アクセスで無出力 wedge。
- 実機 A/B(192.168.1.77、reboot 20+ 回)で
  **ダッシュボード無効化 20/20 成功 vs 有効化 3/3 失敗**を確認し確定。
- **修正(VERSION 30)**: JPEG チャンネルを独立バッファ化(当初 640x360
  に縮小)。
- 詳細: [RTSP と Web ダッシュボードの競合調査](20260806-RTSPと状態画面の競合調査.md)、
  [JPEG/H.264 チャンネル分離 提案書](20260806-JPEGとH264の経路分離.md)。

### (B) 画面全体がマゼンタ/紫色になる(フル解像度化で顕在化)

- JPEG チャンネルをフル解像度(1920x1080)に上げたところ(VERSION 31)、
  実機 2 台で画面全体が紫化。当初「フル解像度化による ISP 資源圧迫」
  と誤診断し 640x360 に戻した(VERSION 32)が、**1 台(1.32)は戻しても
  紫が残った**。
- **決定打**: 1.32 の Nerves SD を抜きメーカー純正ファーム+純正アプリ
  で確認 → **自然な発色**。同一ハードウェアで発色が変わった = ソフト
  ウェア側の問題と確定(ハード故障ではない)。
- **真因**: `/etc/sensor/gc2053-t31.bin`(ISP キャリブレーションファイル)
  が Nerves rootfs に存在しなかった。`ISP: open ... failed` ログは以前
  から両機に出ていたが「両機とも同じだから無害」と誤認していた。
- **修正(VERSION 34)**: 実機の `/atom/system/etc/sensor/gc2053-t31.bin`
  (2 台で SHA256 完全一致、機種共通データ)を
  `package/atomcam2-camera/gc2053-t31.bin` としてリポジトリに追加し、
  `$(TARGET_DIR)/etc/sensor/` へインストール。
- **フル解像度は VERSION 35 で再度有効化し、両機とも紫化しないことを
  確認済み**。「フル解像度化 = 危険」ではなく「キャリブレーション欠落」
  が真因だったと実証。
- 診断用に `wb get|auto|daylight|cloudy|shade|manual <r> <b>` コマンド
  を camd.ctl に追加(VERSION 33)。対称な手動ゲイン探索は収束しない
  ことを確認済み(対症療法、本命はキャリブレーションファイル)。
- 詳細: [ISP キャリブレーション欠落 技術相談](20260806-ISP補正情報欠落の調査.md)。

### (C) ダッシュボード UI 改善

- 映像タブ: アプリ/camd バージョン表示、リフレッシュ 0.5 秒化、
  スナップ表示トグル削除、夜間 ON/OFF/自動ボタンを復元。
- 操作タブ・動作確認タブ: 全ボタンをページ遷移なしの Ajax 化。
- 詳細: [ダッシュボード UI 改善 実装報告書](20260806-状態画面の改善記録.md)。

### (D) OSD への実測 FPS 表示

- OSD デバッグパネルの `Camera:` 行に、ノミナル値ではなく**壁時計基準
  で実測した FPS**を追加(`camd.c` VERSION 36、`/tmp/camd.fps` を
  1 秒おきに書き出し、`camera_native.ex` が読んで OSD 文字列に合成)。
- 両機(1.77・31.31)で `FPS: 25` 前後の表示を確認済み。

### (E) 起動時 IP アドレス音声アナウンス

- 「起動しました。」に続けて、eth0/wlan0 それぞれの IPv4 アドレスを
  「(有線/無線) あいぴー (1桁ずつ) ドット … です」の形式で読み上げる
  機能を追加(`Atomcam2NervesApp.BootAnnounce.announce_ip/0`)。
- 音声素材は Open JTalk(めいちゃん = `mei_normal.htsvoice`、
  `~/nerves_examples/open_jtalk_elixir` を利用)で 15 クリップを合成
  (`package/atomcam2-boot-announce/digits/`、
  `ATOMCAM2_BOOT_ANNOUNCE_VERSION` 3→6)。
- **実機検証で判明した追加修正**: 合成直後のクリップは既存の
  「起動しました」音声よりかなり音量が小さく(peak 差 約13〜19dB)、
  聞き比べで明らかに分かるレベルだった。全クリップを `ffmpeg` で
  peak -1dB へ正規化して解消(VERSION 6)。
- 192.168.1.77(eth0/wlan0 両方稼働)と 192.168.31.31(カナリヤ機)の
  両方で、起動音声・IP 発声・音量が正しいことを確認済み。
- 詳細: [起動時 IP 発声 提案書](20260806-起動時IP発声の実装記録.md)。

## 3. ビルド・投入手順

```bash
# camd(C, uClibc/1.1.1)クロスビルド
D=/tmp/claude-1000/-home-owner-piyopiyoex-nerves-system-atomcam2/39fe2451-5dc9-4559-9436-240a9efe8d5e/scratchpad
GCC=$D/mips-gcc472/bin/mips-linux-gnu-gcc
SDK_INC=$D/sdk111
SAMPLES_INC=$D/atomcam_tools/custompackages/package/ingenic_samples/libimp-samples
DEVLIBS=$D/ingenic-lib/T31/lib/1.1.1/uclibc/4.7.2
cd package/atomcam2-camera
"$GCC" -muclibc -msoft-float -O2 -march=mips32r2 \
  -I"$SDK_INC" -I"$SAMPLES_INC" \
  -Wl,--dynamic-linker=/atom/lib/ld-uClibc.so.0 \
  camd.c -L"$DEVLIBS" -limp -lalog -lpthread -lm -lrt \
  -o atomcam2-camd
# -muclibc -msoft-float が必要(このツールチェーンは multilib、
# 何も付けないと glibc/hard-float 版が選ばれヘッダが見つからない)。
# libimp.so 自体は hard-float ビルドなので "uses -mhard-float" の
# リンカ警告が出るが無害(既存バイナリでも同じ警告が出る)。

# ファーム(camd.c 変更時は .mk の VERSION を必ず +1。local package は
# ファイル変更だけでは再ビルドされず stale が乗る)
cd examples/atomcam2_nerves_app
export MIX_TARGET=atomcam2 ATOMCAM2_SYSTEM_SOURCE=local \
  ATOMCAM2_KERNEL_IMAGE=/home/owner/piyopiyoex/nerves_system_atomcam2/target/atomcam2-control/factory_t31_ZMC6tiIDQN
mise exec -- mix firmware
mise exec -- mix upload <ip>
# upload 後は Nerves.Runtime.reboot() で有効化(スロット切替は次回起動)
```

- カーネル SHA ピン(`b50658ea…`)は**絶対に変更しない**。
- `ATOMCAM2_KERNEL_IMAGE` は `target/atomcam2-control/factory_t31_ZMC6tiIDQN`
  を指す(リポジトリ内、SHA256 検証済み)。**未設定だとビルドが
  `ATOMCAM2_KERNEL_IMAGE must point to...` で失敗する**。
- ビルドコマンドは必ず `examples/atomcam2_nerves_app` に `cd` してから
  実行すること。バックグラウンド実行後は cwd がリセットされることが
  あるため、次のコマンドで `cd` を省略すると
  `Your project is using Nerves bootstrap but doesn't depend on Nerves`
  で失敗する。
- OTP は mise 経由(OTP29)。詳細は [運用リファレンス](20260805-運用手順の整理.md) §8。

## 4. デバイス取り扱いの鉄則(重要、前日から継続)

- **`killall -9` 連打・過剰 reboot をしない**。T31 ISP/VPU が wedge し、
  camd init 成功でも sensor/ISP 無出力になり得る。
- プロセス停止は必ず **SIGTERM**。
- **物理電源断は提案禁止**(ユーザ明言)。今日も 1.32 が完全無応答に
  なった際、ユーザが自主的に電源を入れ直した(こちらから提案しない)。
- **推測で断定しない**。今日も「フル解像度化が原因」「IR-cut 機械摩耗」
  と 2 度誤診断し、いずれもユーザの指摘(「ハード故障と決めつけるな」
  「フル解像度より後に症状が出た」)で軌道修正した。**1 手ごとに結果
  (キャプチャ/ログ)を見てから結論する**。
- **ハード/ソフトの切り分けに迷ったら、同じハードウェアで別のソフト
  スタックを動かして比較する**のが最も確実(今日はメーカー純正ファーム
  起動で証明した)。
- 応答は**日本語**で。
- カナリヤ機は 192.168.31.31([[atomcam2-canary-device]]、当日中に
  1.32 から移動。同一個体が拠点移動で IP が変わることがある)。実験は
  ここを優先し、他機は断りなく叩かない。

## 5. 画像キャプチャの確実な取得法

```elixir
# IEx(ssh <ip>)で
File.rm("/tmp/camd.jpg"); File.touch("/tmp/camd.snap")
Process.sleep(2500)
b = File.read!("/tmp/camd.jpg")
IO.puts(Base.encode64(b))
```
→ ローカルで `sed 's/^:ok//' raw.txt | base64 -d > out.jpg`
(SSH 出力が `:ok` と base64 が同一行に連結されるため `sed` で除去する。
改行区切りと誤認して `tail -n +2` 等で行を丸ごと捨てると全データを
失うので注意)。

- ダッシュボードの映像タブを開いたブラウザが起動中だと `/snapshot.jpg`
  ポーリングと競合し `/tmp/camd.jpg` が短時間で消えることがある
  (`File.read!` が enoent になる)。**2〜3 回リトライすれば通る**。
- **camd の snap 成功自体が camd 健全性の指標**(snap_ok = フレーム
  生成中)。
