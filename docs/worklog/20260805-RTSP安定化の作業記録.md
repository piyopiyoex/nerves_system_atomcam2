RTSP の sprop 間欠欠落(問題C)対策から始まり、**VLC で映らない問題が実は
ネットワーク(VPN/RTP 経路)要因**だったと判明し、最終的に **sprop 修正
(GO ハンドシェイク)** と **マルチ拠点 Wi-Fi(ビルド時 env var)** を実装
した記録。長い試行錯誤を含むため、結論を先に置く。

## 結論(TL;DR)
1. **sprop 間欠欠落は「起動レース」が原因**。camd が READY 直後に即
   `StartRecvPic` し、frame1 の SPS/PPS を **rtspserver 接続前に write →
   ENOTTY で消失**していた。**GO ハンドシェイク**(rtspserver が読み始めて
   から StartRecvPic)で解決。**ストリームは一切改変しない**(v4l2rtspserver
   は既定で SPS/PPS を IDR 前に繰り返すので、一度捕捉できれば sprop は載る)。
2. **「VLC で映らない」の主因はファームではなく VPN/RTP 経路**だった。
   IPSec 単体だと RTP(UDP)の宛先が別サブネットの実 IP になり映像が消失。
   L2TP/IPSec は仮想 IP がカメラ側サブネットに乗るので映る。**回避は VLC の
   RTSP-over-TCP 強制**。この記録の後半にある RTP 経路の切り分けを参照。
3. **マルチ拠点 Wi-Fi をビルド時 env var で焼き込む**方式を追加(参考:
   `hello_kiosk_7inch`)。OTA だけで自宅/会社の両 SSID が反映される。

## 1. 迷走とその教訓(問題C: sprop)

当初 sprop 欠落を「camd の H.264 出力が悪い」と誤診し、camd を V8〜V17 まで
作り直した(prepend でストリームを書き換える等)。**これは筋が悪かった**:

- prepend(各 IDR 前に SPS/PPS を手動挿入)を入れたら、ffmpeg `-c copy` では
  同じに見えるのに VLC で映らなくなった → **VLC 表示回帰**と誤認。
- 途中で **READY 遅延 → `write` が errno 25(ENOTTY)で失敗**という別バグも
  踏んだ(リーダー未接続だと v4l2loopback は write 不可)。
- **決定的な誤り**: テストホストが VPN 経由で、私の ffmpeg は
  `-rtsp_transport tcp`(RTP を TCP 多重化)で通っていたため「配信できて
  いる」と誤認。VLC 既定の UDP では届いていなかった。
- **リバート版(前日動いた版)でも VLC で映らなかった**ことが、
  「ファーム無罪」の決定的証拠だった。→ 原因はネットワークと確定。

**教訓**: 「RTSP は繋がるが映像が来ない」→ まず **RTP(UDP)の宛先・経路**を
疑う。ffmpeg で切り分けるなら **`-rtsp_transport udp`**(`tcp` は経路問題を
隠す)。開発ホストが VPN 経由かを常に意識する。詳細:
[sprop修正 VLC表示回帰 技術相談](20260805-RTSP修正後の再生回帰調査.md)。

## 2. sprop 修正(採用した実装)

- **camd(package/atomcam2-camera/camd.c, VERSION 18)**
  - READY 作成後、**`/tmp/camd.go` を待ってから `StartRecvPic`**。
    frame1(SPS/PPS/IDR)を **rtspserver 接続後**に書くので取りこぼさない。
    8s タイムアウトのフォールバックあり。
  - **SIGTERM ハンドラ**(`sigaction`+`SA_RESTART`、`sig_atomic_t` フラグの
    み)で kill 時も IMP teardown を通す(問題B の緩和)。
  - **ストリームは非改変**(prepend 撤去)。
- **CameraNative**: rtspserver 起動 1.5s 後に `/tmp/camd.go` を作成。
- v4l2rtspserver は既定で「IDR 前に config(SPS/PPS)を繰り返す」(`-c` で
  無効化)。**rtspserver が一度 SPS を捕捉すれば sprop は安定**。
- 実機確認(直結 192.168.1.32、同一 L2): sprop 常時あり、UDP RTP 到達、
  **VLC 表示 OK**。`camd: go after 1600 ms (rtsp reader attached)`。

## 3. VLC が映らなかった真因(ネットワーク)

- RTSP `SETUP` 応答の `destination=` は **接続元 IP**(LIVE555 仕様)。
- **L2TP/IPSec**: クライアントにカメラ側サブネットの仮想 IP → `destination`
  同一サブネット → **UDP 映像が届く**(前日 222.66 で表示 OK)。
- **IPSec 単体**: 実 IP(例 192.168.1.38)のまま → `destination` がカメラと
  別サブネット → 戻り UDP がポリシー外/経路無しで消失 → RTSP(TCP)は
  繋がるが**映像だけ来ない**(当日 31.31 で NG)。
- **対策**: ①VLC で RTSP-over-TCP 強制(最簡)、②L2TP/IPSec、③IPSec に
  仮想 IP 割当。

## 4. マルチ拠点 Wi-Fi(ビルド時 env var)

- **問題**: atomcam2 は wifi を **SD の `nerves-provisioning.conf`(実行時)**
  からのみ読むため、ビルド時 env var が **OTA で運ばれず**、会社 SSID
  (2 つ目)が未登録だった → 現在地(会社)で wlan0 が繋がらなかった。
  ※ スキャンで見えた近隣の別 SSID を一時「登録済み」と誤読していた。
- **修正**(参考 `hello_kiosk_7inch` のビルド時 env var 方式):
  - `WifiProvisioning` が `NERVES_WIFI_SSID` / `_2` / … を**コンパイル時に
    キャプチャ**(`@build_provisioning`)。**実 SSID はソースに書かない**
    (env var 由来なので git 汚染なし)。
  - `runtime.exs` で **ビルド焼き込み + SD ファイルをマージ**(SD が優先=
    個体別上書き可)。
  - 2 拠点の env var を設定してビルド → OTA。
- 実機確認: wlan0 の networks が `["<自宅SSID>", "<会社SSID>"]`(2 拠点)に
  なり、会社 AP へ接続・IP 取得・`:internet` を確認。**実 SSID は記録しない**。

## 6. RTSP がすぐ止まる問題の深掘り（後半セッション）

「再起動後すぐ／数秒で RTSP が止まる」を切り分けた。**camd は健全**（`/tmp/camd.snap` 直接生成で JPEG が出る＝フレーム生成 OK）で、原因は camd ではなかった。

### 原因①（修正済み）: night の ISP 切替が encoder を stall
- `apply_night()` の **`IMP_ISP_Tuning_SetISPRunningMode(NIGHT/DAY)` が stream 中に H.264 エンコーダを wedge** させ、camd のフレームループが数秒後に停止（=「3秒で止まる」）。
- 既定が `auto` のため、**暗所で gain がしきい値付近を毎秒 flap** → その度に IR-cut を叩き stream を乱す（=「15秒で止まる」）。
- **修正（camd VERSION 24）**: `SetISPRunningMode` を除去し、night は **IR-cut（GPIO 53/52 Hブリッジ）+ IR LED（GPIO 26）のみ**で実現。既定を **auto→off** に。ISP の昼夜チューニングは安定と引き換えに捨てる。night は明示指示時のみ。
- ※ダッシュボードの IR-cut テストが「ISP を触らず GPIO だけ」だったのと同じ理由（[GPIO/周辺機器メモ]）。

### 原因②（未解決・観察対象）: v4l2rtspserver の :epipe crash-loop
- **v4l2rtspserver（live555 version 2025.10.13）が起動バナー直後に `:epipe` で繰り返しクラッシュ**（`v4l2rtspserver exited (:epipe); restarting` 多数）。camd は無関係で健全。
- これが「復旧しては数秒で停止」の本体であり、**当初からの『RTSP が止まる』問題の正体**の可能性が高い。
- sprop 捕捉も一発では決まらない**確率的レース**（v4l2rtspserver が起動時に一度だけ sprop を計算しキャッシュ、その窓に camd のフレームが当たるか。GO 遅延調整・SPS バースト・GO 撤去連続配信・ポーリング短縮のいずれも安定化せず、一部は悪化）。

### 教訓: 過剰な churning で T31 ISP/VPU が wedge する
- **`killall -9` 連打・過剰な reboot** で ISP/VPU パイプラインが wedge。camd init は全成功（`=0`, "running 3000 kbps"）でも **sensor/ISP が無出力**（snapshot 503）になり、**warm reboot でも解消しにくい**（[制御カーネル差し替え禁止]と別軸のハード状態）。
- 切り分けは必ず **SIGTERM**（clean teardown）で。`-9` は encoder を poison し次起動も無出力ループ。

### 復帰点（この時点にいつでも戻れる）
- タグ **`checkpoint-20260805-night-fix`** / ブランチ **`checkpoint/20260805-night-fix`**（push 済み、commit 55d65eb）。
- 内容: **camd VERSION 24（night 修正）**＋ `camera_native` は main `0c9c242`（watchdog 検知20s, GO 1.5s）。**デバイス稼働中ファームと同一**。
- 復帰: `git checkout checkpoint-20260805-night-fix` → `MIX_TARGET=atomcam2 ATOMCAM2_SYSTEM_SOURCE=local mix firmware` で再ビルド。
- 現在は**このまま放置して安定性を観察中**。

### 収束短縮は撤回済み
- PR #42（watchdog 検知 6s + settle grace）は **PR #43 で revert**。単一 boot の sprop 捕捉率（~3割）自体は改善できず、外れ boot 連続で数分かかる悪いテールがあるため、確実動作の検知20s版へ戻した。

## 7. 画像のマゼンタ(紫かぶり)の切り分けと修正(camd VERSION 25→29)

「白いレースカーテンが自然光で画像全体マゼンタ」を実機キャプチャで切り分け。**故障ではなく IR-cut フィルタの極性逆転**だった。

### 切り分け(推測せずデータで確定)
- OSD 白オーバーレイは白く出るのにシーンだけマゼンタ → 後段の一律色かぶりでなく **センサ+ISP が捉えた映像自体**。
- `SetISPRunningMode(DAY)` を入れても・IR-cut を「昼」にしても変化なし、と一つずつ潰した(いずれも×)。
- IR-cut を GPIO で両方向にパルスしキャプチャ比較 → **`A=0,B=1` でカーテンが白く写り、`A=1,B=0` でマゼンタ**。フィルタは正常動作、**極性が逆**と判明。

### 修正(VERSION 29)
- `ircut_move` の A/B を反転: **DAY(to_night=0)=A=0,B=1(IR 遮断)**、NIGHT=A=1,B=0。パルス 120→**300ms**(機械式が確実に着座)。
- night は `SetISPRunningMode` を使わず **IR-cut + IR LED のみ**、**既定 off**（ISP 昼夜切替は stream 中に呼ぶとエンコーダ stall。EnableTuning 直後に置くのもパイプライン無出力で×）。起動時 `apply_night(0)` で昼位置へ着座。
- 両機（31.31 / 1.77）で**起動時からカーテンが白く**出ることをキャプチャ確認。

### 残課題
- 明部は白くなったが**暗部に紫が残る**。低照度時の色再現由来と思われる（IR-cut とは別、ISP AWB 調整領域）。**切り分け予定: 31.31 を 1.77 と同じ場所へ移動して照度比較**。
- VERSION 29 のコミットは照度切り分け後に判断（現状は working tree に保持、両機に投入済み）。

### 画像取得のコツ
- dashboard のスナップ polling と競合して scp が file 消失で失敗しがち。**camd に snap 要求 → `File.cp("/tmp/camd.jpg","/tmp/keep.jpg")` で退避 → `File.read!|>Base.encode64` を IEx 出力 → ローカルで `base64 -d`** が確実。
