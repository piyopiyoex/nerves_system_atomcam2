## 相談の要点

Atom Cam 2 の RTSP 配信について、3 つの実装方式が並行して存在する状態に
なっている。それぞれ長所短所があり、**どれを本命に据え、どこに労力を割くか**の
戦略判断について助言をいただきたい。個別の技術詳細ではなく、方針の優先順位が
論点。

## 背景

Atom Cam 2 は Ingenic T31 SoC + GC2053 センサーの IP カメラ。映像は SoC 内蔵の
ISP でハードウェアエンコード(H.264/H.265)される。本プロジェクトは Nerves
(Erlang/OTP、musl)で動く。

映像取得には**ベンダー製カメラアプリ `iCamera_app`(ブラックボックス)**が
関与し、これが ISP とエンコーダを専有する。ここが全ての制約の根源。

## 3 つの方式

### 方式 A: ベンダーアプリの出力を横取り(現行・稼働中)

`iCamera_app` のエンコード出力を `LD_PRELOAD` フックで横取りし、v4l2loopback
経由で v4l2rtspserver から配信する。

- **長所**: **実機で動作している**。再エンコードなし。1080p H.264 約 18fps 配信、
  自動起動・監視まで実装済み
- **短所**: ベンダーアプリがブラックボックスのため、その失敗モードを継承する
  - モバイルアプリが HD ライブに切り替えるとエンコーダチャンネルが競合し、
    RTSP のフレーム供給が止まる(アプリを閉じれば自動復旧)
  - **HD/SD 切り替えを繰り返すとベンダーのパイプライン全体が停止し、
    自動復旧しない**(要電源再投入)。CPU 飢餓が原因と判明済み
  - 停止を検知しても、ベンダーアプリは安全に再起動できない(仕様上リブートが必要)

### 方式 B: libimp を直接使う自前実装(調査中・難航)

ベンダーアプリを排除し、実機の libimp(Ingenic の ISP/エンコーダ SDK)を
自前プログラムから直接叩いてパイプラインを組む。

- **長所**: ブラックボックスを完全排除。解像度・fps・ビットレート・チャンネルを
  自由に制御でき、停止を検知して自前で再起動できる。`iCamera_app`(RSS 18MB)を
  排除できてメモリも浮く
- **短所・現状**: `IMP_System_Init()` 付近で初期化が進まず停止する
  ([別の技術相談](20260803-ネイティブカメラ実装の調査.md)参照)。
  libimp と実機カーネルモジュールの整合性、uClibc 0.9.33.2 という古い
  ランタイム、ISP 初期化手順の不明点など未解決が多い。**成功するか不透明で、
  工数も読めない**

### 方式 C: 監視層だけ改善して方式 A の弱点を埋める(新規案)

方式 A のまま、Elixir の監視層を強化して「HD/SD 切り替えで止まったら検知して
自動復旧する」ようにする。

- 動作実績のある別プロジェクト
  [hello_usbcam_rtsp](https://github.com/kurokouji)(NanoPi NEO + USB カメラ +
  Nerves、H264 約 30fps 配信を実機確認済み)の監視設計が参考になる:
  - `MuonTrap.Daemon.start_link` で daemon を GenServer にリンク
  - `trap_exit` で daemon の死を即座に検知してリトライに変換
    (再起動連鎖を防ぐ)
  - ヘルスチェックでデバイスノードの消失を検知して掴み直す
- **長所**: 低工数。**実用上の最大の弱点(全面停止からの自動復旧)を直接埋める**
- **短所**: ベンダーアプリのブラックボックス性は残る。チャンネル競合そのものは
  解消しない(検知して復旧するだけ)。停止からの復旧に**リブートを伴う**
  可能性がある(ベンダーアプリの再開制約のため)

## 現状の到達点

| 方式 | 状態 |
| --- | --- |
| A | 稼働中。HD/SD 切り替えの全面停止が唯一の実用的弱点 |
| B | `IMP_System_Init` で停止。成否不透明 |
| C | 未着手。設計は参考実装から流用可能 |

## 質問したいこと

1. **無人運用の IP カメラとして、方式 A + C(監視強化)で十分実用に足るか。**
   「HD/SD 切り替えで稀に止まるが、監視層が検知して(必要ならリブートして)
   自動復旧する」という状態は、無人運用として許容範囲か。それとも
   「稀にリブートが挟まる」こと自体が IP カメラとして失格か

2. **方式 B(自前 libimp)に投資する価値はあるか。**
   これは「完全な独立」と引き換えに、成否不透明・工数不明のリスクを負う。
   同種の Ingenic カメラ改造(thingino / OpenIPC)の経験から見て、
   **libimp 直叩きは現実的に到達可能なゴールか、それとも底なし沼か**

3. **段階戦略として妥当か。**
   「まず方式 C で実用レベルに引き上げて出荷可能にし、方式 B は長期の研究
   課題として並行する」という段取りを考えている。これは妥当か。それとも
   中途半端で、どちらかに集中すべきか

4. **見落としている第 4 の道はないか。**
   例えば ベンダーアプリを**完全には排除せず、より賢く制御する**方法
   (HD/SD 切り替えを検知して事前にフックを退避する、チャンネル競合を
   避ける設定を強制する、など)。あるいは方式 B のリスクを下げる別ルート
   (thingino のバイナリをそのまま持ち込む、等)

## 補足: 判断材料

- このプロジェクトは**実験的**な位置づけで、まず「動く」ことを重視している
- 常用時の空きメモリは 2MB 前後(全 87MB)と厳しい。方式 B で 18MB 浮くのは
  中長期には効く
- 現行の方式 A は既にコミット済みで、PR として出せる状態
- 方式 B は先行事例(atomcam_tools)が glibc + ベンダーファーム上で動かして
  おり、**別ユーザー空間(Nerves)へ統合した前例はない**

## 結論(2026-08-03): 採用したロードマップ

セカンドオピニオンを受けて、次の方針を決定した。**A を製品路線、C を最優先
開発、B を研究テーマ**とする。判断軸は「技術的な美しさ」ではなく
**期待値(成功確率 × 価値 ÷ 工数)**。

| 方式 | 位置づけ | 根拠 |
| --- | --- | --- |
| A | 製品路線(正式版) | 稼働済み。C と組み合わせれば「暫定」ではなく完成したアーキテクチャ |
| C | **最優先開発** | 低工数で最大の弱点(全面停止からの自動復旧)を埋める。着手初日から価値が出る |
| B | 研究テーマ | 成功すれば価値大だが、停止箇所が `IMP_System_Init`(カーネル/ISP 境界)で成否・工数が読めない。期待値が低い |

### 決定事項 1: A+C を「暫定版」ではなく完成形とみなす

無人運用の IP カメラで重要なのは「リブートが起きないこと」ではなく
**「人手なしで復帰できること」**。市販の NAS・ルーター・監視カメラも
「内部異常 → 自動再起動」で復帰する設計は一般的で、ウォッチドッグ復帰の方が
むしろ信頼性が高い。したがって A+C は正式なアーキテクチャたりうる。

### 決定事項 2: 段階的復旧を設計する(いきなり reboot しない)

停止検知から復旧までを段階化する。

```text
RTSP 停止を検知
  → まず RTSP サーバーを再起動(数秒)
  → まだ供給が戻らなければ ベンダーカメラを再起動
  → それでも駄目なら OS 再起動(最後の手段)
```

各段の間に猶予と再判定を挟み、軽い手段から順に試す。この設計は方式 C の
`RtspServer` 監視層に実装する。参考実装 hello_usbcam_rtsp の
`trap_exit` + ヘルスチェックの思想をそのまま使える。

### 決定事項 3: 平常時のメモリ削減を並行する

常用時の空きメモリが約 2MB(全 87.7MB)と厳しい。方式 B の 18MB 削減効果を
待たずとも、平常時のメモリを減らせば長期運用の安定性が上がる。

実測したベースライン(ベンダーカメラ停止時、RSS 上位):

| プロセス | RSS |
| --- | --- |
| `beam.smp` | **34,288 kB** |
| `wpa_supplicant` | 3,396 kB |
| 他はすべて 1MB 未満 | — |

**最大の消費者は BEAM(34MB)** で、方式 B が排除する `iCamera_app`(18MB)より
大きい。BEAM のメモリプロファイル改善(不要アプリの削減、ヒープ設定の見直し)は、
B の成否に関わらず効く。ただし BEAM 削減は慎重に行う(機能低下と表裏)。

この方針なら、B が成功しなくてもシステム全体の信頼性を底上げでき、B が
成功すればその成果をさらに活かせる。

### 見送った/保留した第 4 の道

- **HD 競合の事前回避**(アプリの HD 切り替えイベントを検知してフックを一時退避)
  — 実現すればリブート不要になり価値が高い。ただしアプリ側イベントを観測できるかに
  依存する。**方式 C の実装中に、ベンダーログや `/proc` から切り替えを検知できるか
  調査する**(検知できれば段階的復旧の最初の一手として組み込む)
- **thingino を丸ごと利用** — OS 全体であり、持ち込むほど Nerves との整合性が
  壊れる。参考にとどめ、直接流用はしない

### 実装時に判明した設計上の修正(重要)

方式 C を実装する過程で、**素朴な「3 段階復旧(RTSP 再起動 → ベンダー再起動 →
reboot)」はこのシステムでは正しくない**ことが分かった。

- **RTSP サーバーの再起動は無効**。停止の原因はフレーム供給元(ベンダーの
  エンコーダ)の上流にあり、v4l2rtspserver を再起動しても、フレームの来ない
  loopback に繋ぎ直すだけ。hello_usbcam_rtsp では「daemon の死」が問題の本体
  だったが、本システムでは daemon は生きたままフレームだけが枯れる
- **ベンダーカメラの再起動も無効**。ベンダーランタイムは「停止後の再開に
  リブートが必要」という制約を持つため、その場での再起動ができない
- したがって供給停止に対する実効的な復旧は **reboot しかない**

さらに厄介なのは、**reboot はモバイルアプリの正当な HD 視聴と衝突する**点。
HD ライブ視聴中は ch0 のフレームが RTSP 側に来なくなる(競合)が、これは
異常ではなく、アプリを閉じれば復旧する。フレーム不在だけを見て reboot すると、
**HD 視聴中のユーザーを巻き込んでリブートしてしまう**。

「回復不能な停止」と「正当な HD 視聴」を安全に区別するには、CPU 飢餓の
兆候(loadavg)など二次シグナルが要る。これは実機で検証してから入れるべきで、
**フレーム停止からの自動 reboot は別ステップに分離**した。

### 今回実装した範囲(安全な第一歩)

- **フレーム心拍**: video-hook が転送フレームごとに心拍ファイル
  (`/tmp/atomcam2-video-hook.beat`)を更新。供給が止まれば mtime が凍る。
  loopback にフレームカウンタが無く、ベンダーが「running」と偽るこの環境で、
  唯一信頼できる供給停止シグナル
- **RtspServer の監視**: 稼働中に心拍の進みを監視し、停止が続けば
  `status` と警告ログで可視化する(既定で約 1 分後)。**自動 reboot はしない**
- テスト 3 件追加(心拍前進で無警告、凍結で警告 1 回・再起動なし、再開で回復)

自動 reboot を入れなかったのは前述の「HD 視聴巻き込み」を避けるため。まず
可視化までを入れ、実機で loadavg による区別を検証してから復旧を足す。

### 実機検証で見つけた 2 つのバグ(ユニットテストでは出ない)

心拍はユニットテストでは `frame_health` をモックするため通るが、実機では
2 点の不具合で心拍ファイルが生成されなかった。オンデバイス検証でしか
出ない種類のバグ。

1. **MIPS の `open()` フラグ値が汎用と違う**。`O_CREAT` を汎用値 `0100`(0x40)で
   定義していたが、**MIPS は `O_CREAT = 0x100`**。誤った値では新規作成にならず、
   存在しないファイルへの書き込みが `ENOENT` で失敗していた。
   フレーム自体は正常に流れていた(VLC で 739KB 受信)ため、フックの本体は
   動作しており、心拍の open だけが失敗という切り分けができた
2. **chroot のパス不一致**。フックはベンダー chroot 内で動くため
   `/tmp/atomcam2-video-hook.beat` は Nerves から見て `/atom/tmp/...` に書かれる。
   RtspServer(Nerves 側)の読み取りパスを `/atom/tmp/...` に合わせた

どちらも「フレームは流れているのに心拍が無い」という症状で、
`find / -name '*.beat'` が空・ループバックのフォーマットは設定済み・
`PollingStream` 失敗ゼロ、という観測から特定した。
