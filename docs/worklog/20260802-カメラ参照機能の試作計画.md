## 文書情報

- 状態: 検討完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

ベンダー製カメラランタイム(`iCamera_app`)に依存せず、映像の取得・エンコード・
配信を自前で実装するための調査と提案。

関連: [RTSP 配信 提案書](20260802-RTSP配信方式の検討.md)、
[長時間動作 記録](20260802-長時間動作の検証.md)

## 背景: なぜスクラッチ実装か

現行の RTSP 配信はベンダーランタイムのエンコード出力を LD_PRELOAD フックで
横取りする方式であり、実機検証で次の限界が確認された。

- **ベンダーランタイムはブラックボックス**で、エンコーダパイプラインの挙動を
  制御できない。モバイルアプリの HD/SD 切り替えでフレーム供給が止まり
  (チャンネル競合)、切り替えを繰り返すと**パイプライン全体が停止して
  自動復旧しない**([長時間動作 記録](20260802-長時間動作の検証.md)の
  インシデント B)
- 停止を検知しても**安全に再起動する手段がない**(停止後の再開には
  リブートが必要という制約もベンダー側の仕様)
- 解像度・ビットレート・フレームレート・チャンネル構成を**一切変更できない**

映像パイプラインを自前で持てば、これらすべてが解決する。

## 調査結果: ゼロから書く必要はない

「スクラッチ」といっても ISP のレジスタを直接叩く必要はない。Ingenic SoC の
IP カメラには成熟したオープンソースエコシステムが存在する。

### thingino-firmware(最有力の参考実装)

[themactep/thingino-firmware](https://github.com/themactep/thingino-firmware)
は Ingenic SoC 用のオープンソースカメラファームウェア(MIT ライセンス、
Buildroot ベース)。**T31 を含む T 系 SoC を広くサポート**し、RTSP / ONVIF を
提供する。

重要な点として、[対応カメラ一覧](https://github.com/themactep/thingino-firmware/wiki/Cameras)
に **Wyze v3 の専用ページがあり、ATOM Cam 1 も Wyze v2 系として記載**されて
いる。本システムの制御カーネルは **Wyze Cam v3 の GPL カーネルから
ビルドしており、ATOM Cam 2 は Wyze v3 と同系ハードウェア**である。つまり
thingino が動かしている構成と、我々の土台はほぼ同一。

### 構成部品

| 部品 | 役割 | 出所 |
| --- | --- | --- |
| `libimp` | Ingenic の ISP/エンコーダ SDK(ユーザー空間ライブラリ)。ISP 設定、H.264/H.265 ハードウェアエンコード、フレーム取得 API を提供 | ベンダー機にも搭載(`/system/lib/libimp.so`)。musl/glibc/uclibc 各ビルドの再配布リポジトリあり(gtxaspec/ingenic-lib) |
| **prudynt-t** | libimp の上に載る**オープンソースの RTSP ストリーマ**。thingino の標準ストリーマ(後継の Raptor を開発中) | thingino 系(gtxaspec/prudynt-t) |
| センサードライバ | GC2053 等のカーネルモジュール | ingenic-sdk(thingino が保守)。またはベンダー機の `/atom` 領域の .ko をそのまま使用 |
| ISP ドライバ | tx-isp カーネルモジュール | ベンダー機の .ko を使用。[opensensor/isp](https://github.com/opensensor/isp) にオープン実装の取り組みもある |
| ISP チューニング | センサー校正データ(画質を決める) | ベンダー機の `/atom` 領域から利用 |

atomcam_tools も同系統の部品
([openmiko/ingenic_videocap](https://github.com/openmiko/ingenic_videocap)、
libimp サンプル)をパッケージ化しており、T31 系での実績は十分にある。

### 本システムにとって特に有利な点

1. **カーネルは既に同じ**。thingino が対象とする Wyze v3 と同じ GPL ソースから
   ビルドしており、モジュールの vermagic 一致ビルドの手順も確立済み
   (有線 LAN・v4l2loopback で実証)
2. **musl ビルドの libimp が存在する**(ingenic-lib)。つまりストリーマを
   **Nerves の rootfs 内でネイティブに動かせる**。chroot も uClibc も
   LD_PRELOAD フックも不要になる
3. **RTSP 基盤は流用できる**。prudynt-t は RTSP サーバーを内蔵しているため、
   現行の v4l2loopback + v4l2rtspserver の経路すら不要になる可能性がある
4. **メモリが浮く**。`iCamera_app`(RSS 18MB)+ `assis` + `hl_client` を
   prudynt-t(数 MB 級)に置き換えられれば、87MB 機で常に逼迫していた
   メモリに 15MB 前後の余裕が生まれる

## 方式比較

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A(推奨)** | **prudynt-t を移植**し、ベンダーの ISP/センサー .ko + libimp(musl)で動かす | 実績あるコードベース。RTSP/スナップショット/OSD 内蔵。開発量最小 | C++ / live555 依存。カスタマイズは fork 管理 |
| B | libimp を直接使う**最小デーモンを自作**(Ingenic サンプル/ingenic_videocap 参考)、既存の v4l2loopback + v4l2rtspserver に接続 | 構成が最小。既存 RTSP 経路を流用。Elixir からの制御粒度が細かい | エンコーダ設定・再起動処理を自作。prudynt が解決済みの問題を再実装 |
| C | ISP ドライバまで含む完全自作 | 依存ゼロ | 非現実的(ISP は文書化されておらず、opensensor/isp も途上)。却下 |

**推奨は案 A**。まず prudynt-t をそのまま動かし、必要になった時点で
案 B の方向(最小化)へ削るのが最短。

## 提案アーキテクチャ

```text
Nerves(musl ユーザー空間、chroot なし)
  ├── カーネルモジュール: tx-isp / センサー / avpu(ベンダー .ko を流用)
  ├── prudynt-t(libimp musl 版とリンク)
  │     └── RTSP :8554(H.264/H.265、解像度・fps・ビットレート自由)
  └── CameraNative GenServer(新規)
        ├── モジュールロード → prudynt 起動 → ヘルス監視
        ├── フレーム供給停止を検知したら再起動(プロセス kill → 再 insmod)
        └── VendorCamera と排他制御(ISP は同時に 1 利用者のみ)
```

- **ベンダーモードとネイティブモードは排他**。`/data` の設定で選択し、
  既存の Atom アプリ互換(VendorCamera)は選択肢として残す
- 監視・再起動は既存の `FirmwareHealth` / `RtspServer` の流儀を踏襲。
  ブラックボックスだった「止まったら打つ手なし」が「自前で再起動できる」に変わる

## 失うもの(明示)

ネイティブモード動作中は **Atom モバイルアプリ・クラウド連携・アプリからの
録画参照が使えない**(ISP を専有するため)。これは方式の本質的な制約であり、
両立が必要な利用者はベンダーモードを選ぶ。連続録画・NAS 転送は
ネイティブ側でも実装可能(prudynt のスナップショット/録画機能、または
RTSP を受けた Elixir 側での保存)。

## 実機調査の結果(2026-08-03 追記): 必要な部品はすべて確認済み

ベンダーランタイム稼働中の実機で、スクラッチ実装に必要な資産を確認した。

**センサーは GC2053 で確定**(`sensor_gc2053_t31` がロード済み)。
thingino の Wyze v3 と同一センサーであり、同プロジェクトの設定・知見が
直接流用できる。

カメラ関連でロードされていたモジュール(すべて `/atom/system/driver/` に
.ko として存在):

| モジュール | 役割 |
| --- | --- |
| `tx_isp_t31`(770KB) | ISP 本体 |
| `sensor_gc2053_t31` | イメージセンサー |
| `avpu` | ハードウェアエンコーダ |
| `audio` | 音声入出力(ALSA 非依存) |
| `sinfo` / `speaker_ctl` / `sample_pwm_*` | センサー情報 / スピーカー / LED・IRカット |

ユーザー空間ライブラリ(`/atom/system/lib/`): **`libimp.so`(986KB)、
`libalog.so`、`libsysutils.so`** — prudynt-t がリンクする標準の 3 点が揃っている。

ISP チューニングデータ(`/atom/system/etc/sensor/`):
**`gc2053-t31.bin` / `gc2053-t31-cust.bin`** — 画質を決める校正ファイルも
デバイス上にある。

つまりフェーズ 1 の前提はすべて成立しており、残る検証は「ベンダーランタイムを
止めた状態で、これらを自前の順序でロードしてストリームを取得できるか」のみ。

## フェーズ 1 の進捗(2026-08-03): PoC バイナリのビルドに成功

**libimp を使う実行ファイルを Nerves のツールチェーンでビルドできた。**
スクラッチ実装の最大の技術的関門は突破している。

### ビルド構成

- ソース: Ingenic の `sample-Encoder-h264`(atomcam_tools の
  `ingenic_samples` に含まれる libimp サンプル)
- ライブラリ: [gtxaspec/ingenic-lib](https://github.com/gtxaspec/ingenic-lib)
  の **T31 / 1.1.1 / uclibc / 5.4.0** の静的ライブラリ
  (`libimp.a` / `libalog.a` / `libsysutils.a`)
- コンパイラ: 本システムの `mipsel-nerves-linux-musl-gcc`
- 成果物: 静的リンク、MIPS32 rel2、約 1.0MB

**実機の `libimp.so` はバージョン 1.1.1** で、ingenic-lib の 1.1.1 と一致した。
版数不整合のリスクは消えている。

### 解決した 3 つの問題

| 問題 | 内容 | 対処 |
| --- | --- | --- |
| musl と uclibc の非互換 | `__assert`、`__pthread_register_cancel`、`__pthread_unregister_cancel` が未解決 | 互換シム(`shims.c`)を自作 |
| GC2053 の定義がない | サンプルは GC2053 に未対応 | `sample-common.h` に定義を追加(I2C `0x37`、1920×1080) |
| SDK 1.1.1 に無い API | `IMP_ISP_Tuning_SetWDRAttr` が 1.1.1 に存在しない | シムでスタブ化(サンプルは WDR 無効化にしか使わない) |
| float ABI 不一致 | ライブラリは hard-float、既定は soft-float | 全オブジェクトを `-mhard-float` で統一 |

### 得られた知見: 実機への転送はメモリを空けてから

ベンダーカメラと RTSP が稼働した状態で 1MB のバイナリを `scp` したところ、
**転送が中断しユーザー空間が応答不能になった**。この機体では常用時の
`MemFree` が 2MB 前後しかないため、大きめの転送はそれ自体が負荷になる。

**SD カードの FAT パーティション経由で配置するのが確実**。FAT は
`fmask=0000` でマウントされるためホスト側から書き込め、デバイス上では
`/media/mmc` として実行可能な状態で見える。

### 実機実行の結果: float ABI の非互換で Bus error

実機(ベンダーランタイム停止、空きメモリ 21MB)で実行したところ、
**`Bus error`(SIGBUS、rc=138)で即座にクラッシュ**した。

前提条件はすべて満たされていた。

- カメラモジュールは `/atom/system/driver/` から手動ロード成功
  (`tx_isp_t31`、`sensor_gc2053_t31`、`avpu` が Live)
- デバイスノードも生成済み(`/dev/tx-isp`、`/dev/isp-m0`、`/dev/avpu`、
  `/dev/framechan0-2`)
- ベンダープロセスは 1 つも残っていない

原因は ELF 属性の照合で確定した。

| 対象 | FP ABI |
| --- | --- |
| ベンダー `libimp.so` | **Hard float(倍精度)** |
| 本システムの musl sysroot(`crt1.o`) | **Soft float** |

**本システムの musl は soft-float でビルドされており、hard-float の libimp と
ABI が非互換**である。浮動小数点引数のレジスタ割り当てが異なるため、
リンクは通っても実行時に破綻する。リンク時に
「`crt1.o` は soft-float、オブジェクトは hard-float」という警告が出ていたのを
軽視したのが判断の誤りだった。

既存の `libcompat-shim.so` が `-mhard-float` で問題なく動いているのは、
`-nostdlib` で crt を含まず、浮動小数点を一切使わないため。

#### 選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A** | **uclibc でビルドし、ベンダー chroot 内で実行** | 確実。ベンダーと同じ ABI。ただし chroot は残る。それでも `iCamera_app` を排除して自前パイプラインを持つ利点は失われない |
| B | musl sysroot を hard-float で再ビルド | system 全体のビルド構成に影響。Erlang/OTP や既存パッケージすべてに波及するため大きい |
| C | libimp を hard-float から soft-float でリビルド | 不可能(バイナリ配布のみ) |

**案 A を推奨**。当初の「chroot なしでネイティブ統合」という理想は
soft-float の制約により断念するが、**ブラックボックスのベンダーアプリを
排除して映像パイプラインを自前で制御する**という本来の目的は達成できる。
これは提案書に記載していたフォールバック経路そのものである。

案 B は、将来 system をメジャー更新する機会があれば検討に値する。
hard-float 化できれば真のネイティブ統合が可能になる。

### フェーズ 1 の実行手順(準備済み)

SD カードに配置済み:

- `/media/mmc/sample-encoder` — PoC バイナリ
- `/media/mmc/poc-native-camera.sh` — 検証スクリプト(ベンダープロセスの
  残留確認、モジュール状態、空きメモリ、エンコーダ実行、出力確認を一括で行う)

実機での手順:

```elixir
cmd("atomcam2-vendor-camera stop")      # ISP を解放する
cmd("sh /media/mmc/poc-native-camera.sh")
```

ベンダーランタイムは ISP とエンコーダを専有するため、**停止しないと
PoC は成立しない**。停止後の再開にはリブートが必要(既知の制約)。

## 段階計画

### フェーズ 1: PoC(ハード成立性の確認)

1. ベンダーランタイム停止状態で、ベンダーの ISP/センサー .ko を手動 insmod
   (モジュール一覧は上記のとおり実機で確認済み。依存順は PoC で確定)
2. Ingenic サンプル(`sample-Encoder-video` 相当)または prudynt-t を
   ターゲットへ持ち込み、**1 本の H.264 ストリームが取得できること**を確認
3. 画質(ベンダーのチューニングデータ適用)と CPU/メモリを実測

### フェーズ 2: prudynt-t の Buildroot パッケージ化

- `package/prudynt-t`(+ ingenic-lib、libconfig 等の依存)を追加
- モジュールロードスクリプト(`atomcam2-camera-native`)を
  wifi-driver / eth-driver の流儀で追加(FAT へ診断報告)

### フェーズ 3: 統合

- `CameraNative` GenServer(排他制御、ヘルス監視、自動再起動)
- ベンダーモードとの切り替え設定、precheck 拡張、文書化

## リスクと検証項目

| リスク | 内容 | 対応 |
| --- | --- | --- |
| libimp と .ko の版数整合 | libimp はカーネルモジュール(tx-isp/avpu)と版数が合う必要がある | まずベンダー機の .ko + ベンダーの libimp の組で PoC。musl 版 ingenic-lib は同世代(T31 1.1.6 系)を選定 |
| musl 版 libimp の動作 | ベンダー .ko との組み合わせは未検証 | PoC で不成立なら、prudynt-t を uclibc でビルドし chroot 実行に後退(それでも iCamera_app 排除の利点は残る) |
| ISP チューニング | 校正なしでは画質が大きく劣る | ベンダーの校正データ(`/atom` 領域)を読み込む。thingino の Wyze v3 用設定も参考 |
| メモリ | prudynt + live555 の実フットプリント | v4l2rtspserver の実測(RSS 2.3MB)から数 MB 級と予想。PoC で実測。iCamera_app(18MB)が消える分、収支は改善方向 |
| 音声 | 本カーネルは ALSA なし | libimp の AI(音声入力)API はALSA 非依存のため成立の可能性あり。PoC で確認。不成立なら映像のみで開始 |
| ライセンス | ベンダー .ko / libimp / 校正データの扱い | **再配布しない**。デバイス上の `/atom` 領域から実行時に読む(現行のベンダーモードと同じ整理)。prudynt-t / thingino は MIT |
