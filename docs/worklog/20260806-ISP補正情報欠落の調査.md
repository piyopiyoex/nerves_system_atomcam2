# 2026-08-06 ISP 補正情報欠落の調査

## 文書情報

- 日付: 2026-08-06
- 種別: 技術調査
- 状態: 調査完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

camd(方式B のネイティブ実装)が、シーンによって画面全体が**マゼンタ/紫色**
になる不具合を実機 2 台で確認し、原因を **ISP キャリブレーションファイル
(`/etc/sensor/gc2053-t31.bin`)が Nerves rootfs に存在しないこと**まで
特定・修正した記録。[RTSP と Web ダッシュボード競合の調査](20260806-RTSPと状態画面の競合調査.md)
の続きで、同日中に別件として発覚したもの。

## 結論(TL;DR)

- **原因**: T31 の libimp は `IMP_ISP_EnableTuning()` 系の内部処理で
  `/etc/sensor/gc2053-t31.bin`(センサ+SoC 向けの ISP キャリブレーション
  データ、159,736 バイト)を直接 open する。Nerves 側の rootfs にはこの
  パスが存在せず(`ISP: open /etc/sensor/gc2053-t31.bin file for isp
  calibrate read failed` が毎回ログに出ていたが、無害と誤認していた)、
  ISP の AWB が基準を失って **一部シーンで画面全体がマゼンタ/紫色**に
  なる。
- **確定的な証拠**: カナリヤ機の Nerves SD を抜いてメーカー純正ファーム
  (内蔵フラッシュ)で起動し、純正モバイルアプリで映像を見たところ
  **自然な発色**だった。同一の物理ハードウェア(センサ・レンズ・IR-cut)
  で発色が変わったことから、**ハードウェア故障ではなくソフトウェア
  (calibration 未読込)側の問題**と確定した。
- **修正**: 実機の `/atom/system/etc/sensor/gc2053-t31.bin`(vendor
  パーティション)から取得したファイルを、`atomcam2-camera` パッケージが
  `$(TARGET_DIR)/etc/sensor/gc2053-t31.bin` へインストールするようにした
  (camd VERSION 34)。**2 台の実機で bit-for-bit 一致**(SHA256
  `68f12813686112ea5579bfa746e1bca40a0628f2be8bf10340d0b9aea7e184c2`)を
  確認済みで、機種(gc2053+T31)共通データであり個体別ではない。
  投入後、両機とも通常の reboot で自然な色に復帰した。
- **最終確認**: 修正後に §1 で撤回したフル解像度(1920x1080)JPEG も
  camd VERSION 35 で再度有効化し、両機とも紫化せず正常に動作することを
  確認した(§5)。フル解像度化自体は無罪だったと実証された。

---

## 1. 発端: フル解像度 JPEG 化での紫かぶり(誤ったリード)

[20260806-JPEGとH264の経路分離.md](20260806-JPEGとH264の経路分離.md)
の実装後、ユーザ要望でスナップショット JPEG チャンネルを 640x360 から
フル解像度(1920x1080、VERSION 31)に変更したところ、**2 台の実機で
即座に画面全体が紫化**した。当初「フル解像度チャンネルが ISP/メモリ
帯域を圧迫し AWB を乱している」という仮説を立て、640x360 へ戻す
(VERSION 32)ことで**紫は大幅に改善**した。

しかし **1.32(カナリヤ機)だけ 640x360 に戻しても紫が残った**。この
時点でユーザから「簡単にハードウェア故障と結論づけるな、複数台展開の
ための機材選別をしている」との指摘があり、調査を継続した。

## 2. 決定的な切り分け: 純正ファームでは正常

ユーザが 1.32 の Nerves SD カードを物理的に抜き、内蔵フラッシュの
メーカー純正ファームで起動、純正モバイルアプリで映像を確認したところ
**自然な発色**だった。SD を戻すと(=Nerves/camd に戻すと)再び紫に
なった。

**この 1 点で「物理的なセンサ/レンズ/IR-cut の故障」という可能性は
排除される**(同一ハードウェアで発色が変わっているため)。原因は
Nerves 側のソフトウェアスタック(camd の ISP 初期化)にあると確定した。

## 3. 原因の特定: キャリブレーションファイル欠落

- 以前から `dmesg`/RingLogger に
  `ISP: open /etc/sensor/gc2053-t31.bin file for isp calibrate read
  failed` というログが毎回出ており、**2 台とも同一に出るので無害な
  既知ログ**として扱ってきた([[atomcam2-rtsp-stability]] 参照)。
- しかし `/atom/system/etc/sensor/gc2053-t31.bin` と
  `/atom/etc/sensor/gc2053-t31.bin` には**実際にファイルが存在する**
  (vendor パーティション上)。Nerves の `/etc` はこの内容を持たない
  独自の rootfs であり、パスが違うだけで中身が無いわけではなかった。
- camd.c 自体はこのファイルを直接読んでいない(libimp 内部の隠れた
  デフォルトパス探索)。よって camd.c から明示パスを渡す API は無く、
  **ファイルを `/etc/sensor/gc2053-t31.bin` に置くこと自体が対策**に
  なる。

### 3.1 診断用 WB コマンド(camd VERSION 33)

再ビルドせずに `IMP_ISP_Tuning_{Get,Set}WB` を叩けるよう、`camd.ctl` に
以下を追加した(`echo '...' > /tmp/camd.ctl`):

```
wb get                  -- 現在の mode/rgain/bgain をログに出す
wb auto|daylight|cloudy|shade
wb manual <rgain> <bgain>
```

- `wb get`(AUTO 時): `mode=0 rgain=0 bgain=0` — AUTO 実行中でも
  意味のある値が取れず、AWB が事実上機能していないことを示唆。
- `wb daylight`(rgain=bgain=384 固定): **緑がかる**(紫の逆方向)。
- `wb manual 256 256`(等倍): **より強い緑**。
- `wb manual 500 500`: **紫に戻る**。
- `wb manual 430 430`: まだ紫寄り。

→ **対称な r=b ゲインでは中立点に収束しない**(実際に必要な補正は
r/b で非対称)。手動チューニングでは実用的な解に届かず、対症療法と
判断。本命はキャリブレーションファイルの復元と確定した。

### 3.2 ライブ検証(再ビルド無し)

`/etc` が読み取り専用 squashfs のため直接ファイルは置けないが、以下の
手順で**再起動無しに**仮説を検証した:

```sh
mkdir -p /tmp/etc-overlay
cp -a /etc/. /tmp/etc-overlay/
mkdir -p /tmp/etc-overlay/sensor
cp /atom/system/etc/sensor/gc2053-t31.bin /tmp/etc-overlay/sensor/
mount --bind /tmp/etc-overlay /etc
# camd に SIGTERM → MuonTrap が再起動 → 新しい /etc から calibration を読む
```

(SSH 認証は `/data/nerves_ssh` 等にあり `/etc` に依存しないことを事前に
確認してから実施。`/etc` を丸ごと差し替えるため一時的措置。)

**結果: 自然な色に復帰**。これで原因を確定し、恒久対応(パッケージ化)
に進んだ。

## 4. 恒久修正

`package/atomcam2-camera/gc2053-t31.bin` としてファイルをリポジトリに
追加し、`atomcam2-camera.mk` の `INSTALL_TARGET_CMDS` で
`$(TARGET_DIR)/etc/sensor/gc2053-t31.bin` にインストールするようにした
(camd VERSION 34)。ファームビルド・投入後、両機とも**通常の reboot
だけで**(ライブパッチ不要)キャリブレーションが読み込まれ、
`ISP: open ... failed` ログが消え、色が正常化した。

## 5. フル解像度 JPEG の再検証(camd VERSION 35)

キャリブレーションファイルが真因だったことを確定させるため、§1 で
一度撤回したフル解像度(1920x1080)JPEG チャンネルを camd VERSION 35 で
**再度有効化**し、実機 2 台に投入した。

- `Encoder_CreateChn(jpeg) = 0`(rmem クラッシュ無し、§1 と同じ)
- スナップショットは 111~120KB(640x360 時の 6~7 倍、フル解像度相当)
- **両機とも自然な発色**(紫化の再現なし)

これにより「フル解像度化そのものは無害で、真因は一貫してキャリブレー
ション欠落だった」ことが実証された。現在は camd VERSION 35(フル解像度
JPEG + キャリブレーションファイル同梱)が両機の稼働バージョン。

## 6. 教訓

- **「両機で同じ無害そうなログが出ている」は「無害」の証明にならない**。
  今回は 2 台とも同じ calibrate エラーが出ていたため長らく無害と誤認
  していたが、実際は両機とも同じ不具合を抱えていた。
- **ハードウェア故障を早合点しない**。ソフト/ハードの切り分けが付かない
  時は、可能なら「同じハードウェアで別のソフトスタックを動かして比較
  する」(今回は純正ファーム起動)のが最も確実。
- **crash-free ≠ 正しい**。VERSION 31 のフル解像度化は「クラッシュしない」
  ことは確認したが、色という別の品質軸を壊していた。変更の影響範囲を
  narrow に見積もらない。
- 対称な手動ゲイン探索(r=b)のような**次元を減らした場当たり的な調整は
  収束しないことがある**。可能なら本来のデータ(今回は vendor
  パーティションの calibration file)を使う方が早い。
