# 2026-08-05 RTSP 修正後の再生回帰調査

## 文書情報

- 日付: 2026-08-05
- 種別: 技術調査
- 状態: 調査完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

RTSP の SDP に sprop-parameter-sets が間欠的に入らない不具合(問題C)を
直すため camd を改修したところ、**改修後のファームで VLC 表示が出なく
なった**(2 台のクライアントで確認、旧ファームへ戻すと表示可)。
一方で **改修後のストリームは、正常表示できる別個体のストリームと
ffmpeg 上ほぼ同一に見える**という矛盾がある。原因の切り分けについて
独立した意見を求める。

各項目は **観測事実 / 有力仮説 / 未解明事項** に分ける。

対象: AtomCam2(Ingenic T31 + GC2053)、Nerves(BEAM)+ native `camd`
(C, uClibc, libimp 1.1.1)。パイプライン:
センサ → ISP → FrameSource → OSD → H.264 エンコーダ → v4l2loopback
(`/dev/video0`)→ `v4l2rtspserver`(LIVE555)。GOP=25(1 秒毎 IDR)、
Main profile、1920x1080、25fps、VBR。

関連: [問題C 技術相談](20260805-RTSP初期情報欠落の調査.md)、
[問題B 技術相談](20260805-再起動後の映像停止調査.md)。

- 個体A = 192.168.1.77 : **旧 camd(改修前)**。VLC 表示 OK。
- 個体B = 192.168.31.31 : **新 camd(改修後 V8〜V14)**。VLC 表示 NG。

---

## 1. 改修内容(問題C対策として入れたもの)

1. **各 IDR の前に SPS/PPS を in-band で prepend**(late-join 対策=案A)。
   - SPS/PPS を個別にキャッシュ(この encoder は SPS を起動時 1 回、PPS は
     各 IDR 前に出すため、単一キャッシュだと SPS が PPS で上書きされる)。
   - IDR を含むフレームが SPS を欠く場合、キャッシュした SPS を prepend。
   - assemble 先を `asm_buf + HDR_MAX` にし、前方 256B を prepend 用に確保。
2. **READY 生成タイミング**: 一旦「最初の IDR 書き込み後」に遅延させたが
   **デッドロックした(§3-2)ため、元の「loopback S_FMT 直後」に戻した**。
3. **SIGTERM/SIGINT ハンドラ追加**(問題B対策)。ハンドラは
   `volatile sig_atomic_t` を立てるだけ、teardown は main ループで実行。
4. 起動直後の `IMP_Encoder_RequestIDR` は**入れて外した**(H.264 が停止
   したため。ただし後述のとおり別バグ(ENOTTY)との交絡が疑われる)。

---

## 2. 観測事実(核心の矛盾)

### 2-1. 改修後(個体B)は VLC で表示できない
- 2 台の異なるクライアントで確認。旧ファームに戻すと表示可 → **クライアント
  側の問題ではなく、改修が表示を壊した回帰**(利用者の確認)。

### 2-2. しかしストリームは正常個体とほぼ同一に見える
`ffmpeg -rtsp_transport tcp -c copy -f h264`(4 秒)で両個体を採取し比較:

| | 個体A 1.77(表示OK) | 個体B 31.31(表示NG) |
| --- | --- | --- |
| 解像度/profile | 1920x1080 Main | 1920x1080 Main |
| SDP `sprop-parameter-sets` | あり(`J00A…,KO48gA==`) | あり(**同一値**) |
| in-band NAL(4 秒) | SPS0 PPS4 IDR4 P76 | SPS0 PPS4 IDR4 P89 |
| 先頭 NAL 列 | `[8,5,1,1,…]`(PPS,IDR,P…) | `[8,5,1,1,…]`(同一) |

- **両者とも in-band に SPS(type7)が出ていない**(SPS0)。つまり正常な
  個体A も in-band SPS を流しておらず、**VLC は SDP の sprop でデコード
  している**と考えられる。
- SDP も NAL 構造も実質同一。**なぜ A は映って B は映らないのかが最大の謎**。

### 2-3. デコード検証環境の制約
- 開発ホストの ffmpeg / VLC は **h264 デコーダが無効**(`--disable-decoder`、
  libopenh264 でデコード不可)。**ホスト側でピクセルまでのデコード検証が
  できない**。ffmpeg `-c copy` は demux のみで実デコードしないため、
  「demux は通るが decode で落ちる」差異を検出できていない可能性が高い。

---

## 3. 診断で判明したこと(改修中に踏んだ地雷)

### 3-1. camd の書き込み先頭が P フレームになることがある
- クリーン再起動後の fresh camd: frame1 = `7/41 8/8 5/88478`(SPS/PPS/IDR)。
- dirty 再起動(teardown 無しの kill 後など)の camd: frame1〜5 が type1(P)
  = **GOP 途中から書き始め、SPS を一度も捕捉できない**。
- → dirty 起動だと SPS キャッシュが空 → prepend も効かず、rtspserver も
  起動時 SPS を拾えず sprop 空になり得る(問題C の間欠性の一因)。

### 3-2. READY を遅延させると write が ENOTTY で失敗(デッドロック)
- READY を「最初のフレーム書き込み後」に遅延させたところ、loopback への
  `write()` が **errno 25(ENOTTY)** で失敗し続け、got=0 に。
- 原因: この v4l2loopback は **リーダー(rtspserver)未接続だと write が
  ENOTTY**。「write にはリーダー、リーダーには READY、READY には write 成功」
  の循環デッドロック。→ READY を S_FMT 直後生成(旧動作)に戻して解消。

### 3-3. prepend の in-band SPS が capture に出ない
- SPS/PPS を個別キャッシュし IDR 前に prepend する実装にしたが、
  RTP capture では **SPS0 のまま**(prepend が RTP に現れない)。
- 解釈候補: (a) v4l2rtspserver が in-band パラメータセットを除去し SDP に
  集約している、(b) prepend が dirty 起動でキャッシュ空のため発火して
  いない、のいずれか(未確定)。

---

## 4. 有力仮説(表示回帰の原因候補)

ストリームが ffmpeg 上「同一」なのに VLC 表示だけ壊れる、という事実から、
**demux は通るが decode を壊す微妙な差異**が改修に含まれるはず。候補:

1. **prepend が挿入する SPS/PPS が不正/重複で VLC デコーダが弾く**
   (最有力)。ffmpeg `-c copy` は寛容だが VLC decoder は厳格。ただし
   2-2 で in-band SPS が capture に出ていない点と整合しないため、
   「rtspserver が prepend を検出して RTP 構成を変える」等の二次作用も疑う。
2. **SIGTERM/SIGINT ハンドラが libimp の内部シグナル運用に干渉**し、
   エンコード出力が微妙に破綻(SIGINT 使用の SDK 実装があり得る)。
   個体A(ハンドラ無し)は正常、個体B(ハンドラ有り)は NG、と表面的には
   整合。
3. **OSD デバッグ表示のデフォルト ON**(改修で既定 ON にした)。大きな
   オーバーレイ領域が IPU/エンコーダに影響してフレームを破綻させる可能性。
   → **現在ランタイムで OSD を OFF にして切り分け中**(結果は未確定)。
4. 起動時に camd が **dirty 起動(GOP 途中開始)**で SPS を欠く経路に入り、
   個体B ではその状態でクライアントが掴んでいる(個体A は clean 起動)。

  「SDP 不整合」かを大きく絞れる。
- 開発ホストで **decode 検証ができない**(h264 デコーダ無効)。別環境での
  実デコード確認が必要。
- prepend が RTP に出ない理由(rtspserver の in-band 除去挙動か、発火せず

- 上記 4 候補のうちどれが真因か、**一度に複数を変えてしまい交絡**して
  いる(反省点)。1 要素ずつの bisection が未実施。

## 6. 相談したい論点

1. **ffmpeg `-c copy` で同一に見えるストリームが、VLC でだけ decode 不能に
   なる**典型的な原因は何か(重複/不正パラメータセット、VUI/タイミング、
   RTP マーカビット、AU 境界、SEI 等)。切り分けの定石は。
2. **v4l2rtspserver(LIVE555)は in-band SPS/PPS をどう扱うか**
   (除去して SDP sprop に集約するのか、そのまま RTP へ流すのか)。
   in-band prepend は有効か、むしろ有害か。
3. libimp 環境で **SIGINT/SIGTERM ハンドラ導入がエンコードに影響**する
   可能性はあるか(内部スレッドのシグナル運用)。安全な導入法
   (sigaction + SA_RESTART、特定シグナルの回避等)。
4. **problem C(間欠 sprop 欠落)を、ストリームを一切変えずに直す**方法は
   あるか。例: rtspserver 起動後に SDP を検査し sprop 未検出なら
   rtspserver を再起動する(Elixir 側)/ camd はストリームを触らない、等。
5. 起動を常に **clean(fresh encoder で frame1=SPS/PPS/IDR)**に保てば、
   prepend 無しでも sprop は安定するか。そのための確実な方法
   (clean teardown の担保、RequestIDR の是非)。

## 7. 制約と前提

- H.264 RTSP 配信は既存の主機能。**回帰厳禁**(今回それを踏んだ)。
- `camd` は libimp を叩く単一スレッド C デーモン。libimp はスレッド
  セーフ非保証。
- メモリ厳しい(RAM 85MB、rmem 予約 36MB)。
- 開発ホストで h264 decode 不可(検証は実機 VLC 依存)。
- 現状: 個体A(1.77)= 旧 camd・表示OK / 個体B(31.31)= 新 camd・表示NG。
  ffmpeg 上のストリーム/SDP は両者ほぼ同一。旧に戻すと個体B も表示可。

## 8. 求める結論

「ffmpeg で同一に見えるのに VLC 表示だけ壊れる」原因の切り分け方針と、
problem C を**回帰なく**直すための安全な実装方針(ストリームを変えない
アプローチを含む)についての意見。

## 9. セカンドオピニオン回答(2026-08-05)と方針確定

### 是正・要点
- **prepend 内容が犯人という証拠は弱い**。RTP capture に prepend した SPS が
  出ていない以上、LIVE555 / v4l2rtspserver 側で吸収・無視されているか、
  そもそも prepend 経路が未発火の可能性。**ビットストリーム内容ではなく
  「RTP 化・encoder 状態の運び方」の差**を疑うべき。
- **`ffmpeg -c copy` は demux のみ**。VLC が見る **RTP Marker bit /
  timestamp / FU-A 組み立て / AU 境界 / シーケンス番号**は比較できない。
  1080p の IDR はほぼ FU-A になるため、ここの破綻は「VLC だけ死ぬ」典型。
- 原因可能性(第三者評価): ①RTP packetization/AU 境界の破綻(高)、
  ②IDR 開始タイミング・encoder 状態差(高)、③dirty encoder 開始(中)、
  ④SIGTERM ハンドラ(低)、⑤OSD(低)、⑥prepend 内容そのもの(低)。
- **problem C の根本は「encoder が fresh でない」**(dirty 起動で frame1 が
  P になる)。ここを直せば sprop 問題はほぼ消える見込み。§3-1 が本資料で
  最も価値のある観測、との評価。
- SIGTERM: `sig_atomic_t` のみなので低リスク。ただし `signal()` ではなく
  **`sigaction` + `SA_RESTART`** にすべき(`read`/`ioctl` の EINTR 回避)。
- RequestIDR は GOP 途中には効くが **encoder 内部状態は初期化しない**。
  fresh 化は **Stop→Destroy→Create→Start** を優先。

### 確定した方針(回帰を最優先で解消)
1. **camd はストリームを一切書き換えない**方針に戻す(prepend / body オフ
   セットを撤去し、出力を旧・正常個体と byte 等価にする)。→ VLC 表示回帰を
   まず解消。
2. **encoder を必ず fresh 起動**(clean teardown を担保、restart 時も
   Destroy→Create)で frame1 = SPS/PPS/IDR を保証。
3. **problem C 対策はストリーム非改変で**: rtspserver 起動後に SDP を検査し
   `sprop` 未生成なら rtspserver(必要なら camd)を再起動する監視を
   **Elixir 側(CameraNative)**に入れる。
4. SIGTERM ハンドラは `sigaction`+`SA_RESTART` に。
5. 機能追加は**1 項目ずつ戻し入れして二分探索**(今回の交絡の反省)。
6. RTP 層の確証が要るときは **tcpdump→Wireshark の RTP Stream Analysis**
   で正常個体と比較(Marker/timestamp/FU-A)。

---

## 10. 解決(2026-08-05 結論)

**この「VLC 表示回帰」は誤診だった。真因は VPN/RTP 経路**で、camd の変更は
無関係。決め手は **リバート版(前日動いた版)でも VLC で映らなかった**こと。

- **ffmpeg `-c copy` で同じに見えるのに VLC で映らない理由**: テストは VPN
  経由で、ffmpeg は `-rtsp_transport tcp`(RTP を TCP 多重化)で通っていた。
  VLC 既定の **UDP RTP** が届いていなかっただけ。ストリーム内容の差ではない。
- **RTP が届かない理由**: LIVE555 は接続元 IP を RTP の `destination` にする。
  **IPSec 単体**では実 IP(別サブネット)が宛先になり戻り UDP が消失。
  **L2TP/IPSec**は仮想 IP がカメラ側サブネットに乗るので届く(前日 OK)。
- **確認**: カメラを直結(同一 L2)にしたら UDP RTP 到達・**VLC 表示 OK**。

**sprop 間欠欠落そのもの**は、prepend(ストリーム書換)ではなく
**GO ハンドシェイク**(rtspserver が読み始めてから camd が StartRecvPic)で
解決。frame1 の SPS/PPS が ENOTTY で消えていたのが原因だった。ストリームは
非改変(v4l2rtspserver 既定の「IDR 前 config 繰り返し」で sprop は載る)。
