# 2026-08-05 RTSP 初期情報欠落の調査

## 文書情報

- 日付: 2026-08-05
- 種別: 技術調査
- 状態: 調査完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

native カメラ(`camd` + v4l2loopback + `v4l2rtspserver`)で、**起動によって
RTSP の SDP に `sprop-parameter-sets`(SPS/PPS)が入らず、プレイヤーが
デコードできない**不具合(従来の「問題C」)について、独立した第三者の
意見を求めるための状況整理。今回、**正常機との対照で「間欠性」を実測**し、
camd 側に**設計上のレース**を特定できたため、対策方針の妥当性を問う。

各項目は **観測事実 / 有力仮説 / 未解明事項** に分けて記す(再現・観測と
推論を混同しないため)。

対象: AtomCam2(Ingenic T31 + GC2053)、Nerves(BEAM)+ native `camd`
(C, uClibc, libimp 1.1.1)。パイプラインは
1 センサ → ISP → FrameSource → OSD → H.264 エンコーダ → v4l2loopback
(`/dev/video0`)→ `v4l2rtspserver`(LIVE555)で RTSP 配信。

関連: [native カメラ不具合 技術相談](20260804-ネイティブカメラ不具合の調査.md)
の問題C。本書はその問題Cに絞り、実測比較と修正方針を追加したもの。

## 1. 観測事実

### 1-1. 同一ファームの 2 台で SDP だけが違う(間欠性の実証)

同じファーム・同じ camd・同じ v4l2rtspserver を焼いた 2 台で、
RTSP `DESCRIBE` の SDP を比較した。

**正常機(192.168.1.77、VLC 表示可):**
```
a=rtpmap:96 H264/90000
a=fmtp:96 profile-level-id=4d0033;sprop-parameter-sets=J00AM+dAPAET8s1AQEB8AAADAAQAAAMAyMkAAehIAAtxt//wKA==,KO48gA==
a=x-dimensions:1920,1080
```

**異常機(192.168.31.31、VLC 表示不可):**
```
a=rtpmap:96 H264/90000
a=fmtp:96
a=x-dimensions:1920,1080
```

- 違いは **`sprop-parameter-sets` の有無だけ**(`profile-level-id` も
  正常機のみ)。`x-dimensions` は両機とも 1920×1080(v4l2rtspserver が
  デバイスの S_FMT から得るため、NAL 解析とは独立)。
- 異常機で ffmpeg も `Video: h264, none ... unspecified size` /
  「codec parameters が見つからない」で失敗。SPS(画面サイズを含む)が
  クライアントへ届いていない。

### 1-2. v4l2rtspserver 単独再起動では回復しない

異常機で `v4l2rtspserver` プロセスのみ kill → 監督プロセス
(MuonTrap.Daemon)が再起動 → 再 `DESCRIBE` しても **`fmtp` は空のまま**。
= 現在 camd がループバックへ流すストリームに **SPS/PPS が乗っておらず**、
後から開いた rtspserver では拾えない(起動直後に一度出るだけ)。

### 1-3. camd はフレーム書き込みより前に READY を立てている

`camd.c`(抜粋、行番号は現行):

```c
int lfd = loopback_open(dev);      // 623: VIDIOC_S_FMT + STREAMON
step("loopback ready", 0);
{                                  // 626-629: ここで READY を作成
    int rfd = open(READY_PATH, O_WRONLY|O_CREAT|O_TRUNC, 0644);
    if (rfd >= 0) close(rfd);
}
IMP_Encoder_StartRecvPic(CHN);     // 631: エンコード開始(READY の後)
...
for (i=0; i<frames; i++) {
    rc = IMP_Encoder_PollingStream(CHN, 1000);
    IMP_Encoder_GetStream(CHN, &stream, 1);
    ...assemble packs into asm_buf...
    write(lfd, asm_buf, len);      // 668: ループバックへ書き込み
}
```

- `/tmp/camd.ready` は **S_FMT 直後・`StartRecvPic` より前・最初の
  `write()` より前**に作られる。
- Nerves 側(`CameraNative`)は `/tmp/camd.ready` を待って
  `v4l2rtspserver` を起動する。したがって **rtspserver は SPS/PPS/IDR が
  1 バイトも書かれる前にループバックを開いて読み始められる**。

### 1-4. 最初に書き出すフレームが P フレーム

以前の NAL 診断ログ(`write()` 直前の `asm_buf` を解析、frame≤3)で、
**最初に書き出す 3 フレームが NAL type 1(非 IDR=P)**で、SPS(7)/PPS(8)/
IDR(5) を含まない、と観測した起動があった(`frame 1/2/3 nals: 1`)。
※この観測を取った起動では sprop は「あった」(=競合に勝った)。

### 1-5. エンコーダは SPS/PPS を周期挿入していない

現状 camd は `IMP_Encoder_RequestIDR` も、SPS/PPS の周期挿入設定も
行っていない(既定のまま)。SPS/PPS はストリーム冒頭でしか出ない前提。

---

## 2. 有力仮説

**根本原因は「SPS/PPS をストリーム冒頭で一度しか流さない = Late Join に
耐えない設計」**。READY レースは**それを顕在化させるトリガー**であって、
本質ではない(セカンドオピニオンと一致、§6)。

- SPS/PPS が各 IDR で繰り返されないため、rtspserver / クライアントが
  冒頭を過ぎて開くと以後 P/IDR しか見えず、LIVE555 は SPS/PPS を見た
  ときだけ `sprop-parameter-sets` を生成するので `fmtp` が空になる。
  → **1-2(rtspserver 再起動でも復旧しない)を最も自然に説明する**。
  周期送出さえあれば「次の IDR で SPS/PPS/IDR が再び来る」ため late-join
  で必ず復元でき、致命傷にならないはず。
- READY を書き込み前に立てている(1-3)ことは、rtspserver が冒頭を
  取り逃す確率を上げる**増幅要因**。捕捉できれば sprop あり(1.77)、
  取り逃せば空(31.31)という間欠性を説明する。
- 1-4 の「先頭が P」は、「初期の SPS/PPS/IDR が rtspserver 接続前に
  流れて消えた」とも読めるが、そもそも**エンコーダ最初の `GetStream` が
  SPS+PPS+IDR を返しているのか自体が疑わしい**(§3、断定しない)。

## 3. 未解明事項

- **1-4 の「最初の書き込みが P フレーム」の説明が未確定**。新規エンコーダの
  最初の `GetStream` は本来 SPS+PPS+IDR のはず。なぜ camd が最初に書く
  `asm_buf` が P で始まるのか(GetStream が IDR を別 pack で返している/
  診断スキャンの粒度/StartRecvPic 前後の取りこぼし等)は切り分け未了。
- **pack 単位ログが未取得**(次の最優先診断): `GetStream` が返す
  `stream.pack[0..packCount-1]` の **type と length を全 pack 分**出す。
  frame0 が `pack0=SPS, pack1=PPS, pack2=IDR` なのか、`pack0=IDR` だけで
  SPS/PPS が別フレームなのか、あるいは本当に P で始まるのかで話が変わる。
  現行診断は `asm_buf` を結合後にスキャンしており、pack 構造が潰れている。
- **3〜4 段 NAL 比較が未実施**: (a) `GetStream` 直後の pack 列、
  (b) `asm_buf`(結合後)、(c) `/dev/video0` を直読みした NAL 列、
  (d) rtspserver が RTP で流す NAL 列。どこで SPS/PPS が失われる/欠けるかは、
  これで 100% 特定できる。
- T31 libimp 1.1.1 で **各 IDR ごとに SPS/PPS を繰り返す設定/API** が
  あるか未確認(`IMP_Encoder_SetChnAttr` の gop/rc 属性、あるいは
  H.264 プロファイル属性のフラグ等)。
- v4l2loopback の読み手セマンティクス未確認: 新規オープンした reader は
  「最後に書かれたバッファ」を受け取るのか、オープン後の書き込みだけか。
  これにより「ヘッダ周期挿入だけで late-join を救えるか」が決まる。

## 4. 検討中の対策と、相談したい論点

安定起動の肝はここだと考えている。以下の方針の妥当性・優先順位について
意見を求めたい。

### 案A: SPS/PPS を各 IDR で繰り返す(根本対策)
- 最初の `GetStream` で得た SPS(7)/PPS(8) を camd 内にキャッシュし、
  以後 **IDR を書く直前に毎回 SPS+PPS を prepend** してループバックへ
  書く。または libimp に周期挿入設定があればそれを使う。
- 利点: late-join(rtspserver / クライアントがいつ開いても)で必ず復元。
  間欠性が原理的に消える。
- **論点(1)**: T31 libimp 1.1.1 に「IDR ごとに SPS/PPS を再送」する
  正規の設定/APIはあるか。無ければ camd 手動 prepend で問題ないか
  (pack 境界・タイムスタンプ・v4l2loopback への書き方の注意点)。

### 案B: READY を「最初の SPS/PPS/IDR を書いた後」に立てる(レース低減)
- READY 作成を `StartRecvPic` 後に移し、**先頭の書き込みが
  SPS+PPS+IDR で始まるまで**(=最初の IDR まで P を捨てる)待ってから
  READY を作る。rtspserver は必ずヘッダ付き先頭から読む。
- **論点(2)**: これ単独で十分か。v4l2loopback の読み手が「オープン後の
  書き込みのみ」を見るなら、rtspserver 起動の僅かな遅延で再び頭を
  取り逃す恐れがあり、案A併用が要ると考えるが妥当か。

### 案C: 起動時に IDR を強制 + 先頭 P を捨てる
- `IMP_Encoder_RequestIDR()` を開始直後に呼び、最初に書く NAL 列を
  SPS/PPS/IDR に揃える。案B の前段として。
- **論点(3)**: 1-4(先頭が P)の真因が RequestIDR 欠如なのか、それとも
  取りこぼしなのか。まず 3 段 NAL 比較(3節)で確定すべきか、対策を
  先に入れて経験的に潰すべきか。

### その他の論点
- **論点(4)**: 既存の主機能(H.264 RTSP 配信)を**回帰させない**のが最優先。
  上記いずれも camd(C)改修 + クロスビルド + Buildroot バージョン更新を
  伴う。案A手動 prepend が最小侵襲か、案B/Cの順序変更の方が安全か。
- **論点(5)**: メモリ制約(Linux から見える RAM 85MB、rmem 予約 36MB、
  単一スレッド C デーモン、libimp はスレッドセーフ非保証)下で、
  ヘッダキャッシュ+prepend が現実的か。

## 5. 制約と前提

- H.264 の RTSP 配信は既存の主機能。**回帰厳禁**。スナップショット/
  ナイトビジョンは付加機能。
- `camd` は libimp を叩く単一スレッド C デーモン。libimp はスレッド
  セーフでない可能性が高い(ロック順序非公開)。
- ソフト再起動での復旧は不安定(別途「問題B」: 反復 kill/再起動後に
  映像 HW が wedge、電源断で復旧)。安定起動をソフトのみで担保したい。
- 現状 2 台構成: 192.168.1.77(sprop あり・正常)、192.168.31.31
  (sprop 空・異常)。同一ファーム。良い対照サンプルが取れている。

## 6. セカンドオピニオン回答(2026-08-05)と方針確定

第三者レビューの結論を反映。**根本原因は「READY レース単独」ではなく
「SPS/PPS を一度しか流さない = Late Join に耐えないストリーム設計」**。
READY レースは発生確率を上げるトリガーであり、周期送出があれば致命傷に
ならない、との評価(§2 に反映済み)。

主要な論点への回答:

- **1-2(rtspserver 再起動でも空)は「SPS/PPS を一回しか送っていない」
  ことの強い証拠**。周期送出があれば次の IDR で必ず復元できるはず。
- **案A(周期送出)= 第一候補・根本対策**。H.264 では一般的
  (x264/openh264/NVENC 等も設定可能)。手動 prepend は安全:
  Annex-B で `00000001 SPS / 00000001 PPS / 00000001 IDR` を IDR の前に
  書くだけ。SPS/PPS は PTS を持たず、IDR と同 timestamp で可。
  サイズは 1080p でも SPS+PPS 合計 100byte 未満、85MB RAM では無視できる。
- **案B(READY 遅延)単独では不十分**。rtspserver 起動〜open の
  100〜200ms で冒頭が流れれば再び取り逃す。案A併用が前提。
- **案C(RequestIDR)は補助**。RequestIDR は「次を IDR に」の依頼で、
  SPS まで付くかは libimp 実装依存(IDR だけの実装もある)。単独では
  SPS を保証しない。
- **1-4(先頭 P)は依然不自然で、GetStream を鵜呑みにしない**。
  pack 単位ログ(§3)で `pack0/1/2` の type/length を確認してから
  結論を出すべき。
- **libimp の "repeat sequence header" 相当の設定は調査価値が高い**。
  もし存在すれば手動 prepend より優先(エンコーダ生成ストリームと
  完全整合し、将来のプロファイル/VUI 変更にも追従して保守が楽)。

### 確定した実装順序(回帰リスク最小)

1. **libimp に SPS/PPS 再送設定があるか確認**(`IMP_Encoder_SetChnAttr`
   の gop/rc 属性、H.264 プロファイル属性のフラグ、SDK サンプル)。
2. 無ければ **手動 prepend を実装**(最有力・根本対策)。IDR を書く直前に
   キャッシュ済み SPS/PPS を毎回 prepend。
3. **READY を最初の IDR を書いた後へ移動**(起動レース低減)。
4. **開始時に RequestIDR を追加**(補助、先頭を IDR に揃える)。
5. **pack 単位ログ + 3〜4 段 NAL 比較で検証**(1-4 の真因確認と、
   どの段でも SPS/PPS が消えないことの確認)。

> 総合評価は「技術相談書として完成度が高い(90〜95 点)」。唯一の改善は
> 案A を "本命" ではなく **"根本対策"** と位置づけ、READY レースを
> トリガー、Late Join 非対応の設計を本質、と整理すること(本節・§2 で反映)。
