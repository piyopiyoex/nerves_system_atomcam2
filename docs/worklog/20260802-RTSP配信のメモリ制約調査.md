## 相談の要点

Atom Cam 2(Ingenic T31、RAM 87MB)で、ベンダー製カメラランタイムが生成する
エンコード済み映像を RTSP で配信する仕組みを実装した。

- **640×360 H.265 は成功**(安定動作を実機で確認)
- **1920×1080 H.264 は失敗**(RTSP サーバー起動直後にメモリ枯渇し、
  ユーザー空間全体が応答不能になる)

1080p H.264 での配信を成立させる方法、あるいは「この構成では不可能」という
判断の妥当性について助言をいただきたい。

## 1. システム構成

### ハードウェア

| 項目 | 値 |
| --- | --- |
| SoC | Ingenic T31(MIPS32、リトルエンディアン、シングルコア) |
| RAM | 物理 128MB のうち Linux に 92MB を割り当て |
| カーネル起動引数 | `mem=92M@0x0 rmem=36M@0x5c00000` |
| `MemTotal` | 87,700 kB |
| ストレージ | MicroSD(SquashFS の A/B スロット + ext2 のデータ領域) |
| スワップ | なし |

`rmem=36M` はカメラの ISP/エンコーダが使う予約領域で、Linux の
`MemTotal` には含まれない。

### ソフトウェア

| 項目 | 値 |
| --- | --- |
| カーネル | Linux 3.10.14(`3.10.14__isvp_swan_1.0__`、ベンダー提供の検証済みバイナリ。差し替え不可) |
| ユーザー空間 | Nerves(Buildroot + Erlang/OTP 29 + Elixir リリース、musl) |
| ベンダーランタイム | uClibc バイナリを chroot 内で実行(`iCamera_app`、`assis`、`hl_client`) |
| v4l2loopback | commit `a6d8228`(3.10 で動作する版に固定)+ atomcam_tools の OOM パッチ |
| v4l2rtspserver | commit `ce80891` + live555 2025.10.13(映像のみ、音声機能は未ビルド) |

## 2. 実装アーキテクチャ

再エンコードは行わず、ベンダーがすでにハードウェアエンコードした
ストリームをそのまま配信する。

```text
iCamera_app（ベンダー、chroot 内、uClibc）
  │  local_sdk_video_set_encode_frame_callback() でコールバック登録
  ▼
libvideo-hook.so（LD_PRELOAD、自作、libc 非依存）
  │  登録を横取りし、フレームを write(2) で流し込む
  ▼
/dev/videoN（v4l2loopback、仮想デバイス）
  │
  ▼
v4l2rtspserver（Nerves 側 rootfs、musl）
  │
  ▼
RTSP クライアント（ホストの VLC など）
```

ベンダーのエンコードチャンネル構成:

| ベンダー ch | 解像度 | コーデック |
| --- | --- | --- |
| 0 | 1920×1080 | H.264 |
| 1 | 640×360 | H.265 |
| 3 | 1920×1080 | H.265 |

フックは該当チャンネルのフレームを対応する `/dev/videoN` に書き込んだ後、
ベンダー本来のコールバックをそのまま呼び出す。

## 3. 成功している構成(640×360 H.265)

v4l2loopback を `devices=1 video_nr=1 max_buffers=2` でロードし、
`/dev/video1` のみを作成。

```sh
v4l2rtspserver -P 8554 /dev/video1
```

実測結果:

- URL: `rtsp://<camera>:8554/video1_unicast`
- SDP: `H265/90000`、`x-dimensions:640,360`、有効な sprop-vps/sps/pps
- 15 秒受信して 326KB(約 174 kbps)
- HEVC の NAL 解析: IDR 15 枚 + 非 IDR スライス 268 枚 =
  約 283 フレーム(約 19 fps)、毎秒 1 キーフレーム
- 配信中もベンダーランタイムは正常(`result=running`、エンコーダエラー 0 件)
- **長時間安定**

## 4. 失敗している構成(1920×1080 H.264)

同じ手順で `video_nr=0` として `/dev/video0` を作成し、
`v4l2rtspserver -Q 2 -P 8554 /dev/video0` を実行。

- ベンダーランタイムは**正常に起動**(`iCamera_app` 稼働、
  エンコーダエラー 0 件)。つまり**フックとフレーム供給は成立している**
- v4l2rtspserver のプロセスも起動する
- **その直後にユーザー空間全体が応答不能になる**
  - ICMP には応答するが、SSH のバナーが返らない(Erlang VM が事実上停止)
  - RTSP ポート(8554)は開かない
  - 一度は約 20 分後に自然回復した(何かが OOM で落ちたと推測)
  - カーネルパニックではなく、再起動もしない

## 5. 実測メモリ(単位 kB、`MemTotal` = 87,700)

| 状態 | MemFree | Cached | 備考 |
| --- | --- | --- | --- |
| 起動直後(ベンダー停止) | 約 22,000〜23,000 | — | 余裕あり |
| ベンダー起動後(640×360 構成) | 1,688 | 26,356 | 再利用可能 約 29,600 |
| **+ RTSP 配信中(640×360)** | 1,768 | 26,260 | **安定** |
| ベンダー起動後(1080p 構成) | 1,528〜1,648 | 未取得 | ここまでは正常 |
| + RTSP 起動(1080p) | 測定不能 | — | **応答不能** |

注: カーネル 3.10 のため `MemAvailable` は存在しない。
`MemFree` は小さいが `Cached` が大半を占めており、640×360 構成では
再利用可能メモリを約 29MB 維持できている。

## 6. すでに試した対策

| 対策 | 結果 |
| --- | --- |
| v4l2rtspserver のフレームキューを既定 5 → `-Q 2` に削減 | 効果なし(失敗) |
| v4l2loopback を `devices=1` にして仮想デバイスを 1 本のみ作成 | 3 本(うち 2 本が 1080p)では**システムごと再起動**していたのが、1 本なら起動までは到達するよう改善 |
| フックが `VIDIOC_S_FMT` で `sizeimage` を明示(1080p=512KB、640×360=192KB)。従来は 0 のままで、v4l2loopback が生の解像度からバッファを算出していた | **`MemFree` はほぼ変化せず**(1,648 → 1,528)、失敗は解消しなかった |

3 番目の対策で改善しなかったことから、**ボトルネックは v4l2loopback の
バッファではなく v4l2rtspserver 側**にあると推測しているが、確証はない。

## 6.5 追記(2026-08-02): 原因をソース解析で特定した

助言を受けて live555 と v4l2rtspserver のソースを確認したところ、
**メモリ消費の主因を特定できた**。

### 連鎖の構造

v4l2rtspserver は V4L2 デバイスのバッファサイズを、そのまま live555 の
`OutPacketBuffer::maxSize` に代入している([DeviceSourceFactory.h](https://github.com/mpromonet/v4l2rtspserver/blob/master/inc/DeviceSourceFactory.h)):

```cpp
// extend buffer size if needed
if (devCapture->getBufferSize() > OutPacketBuffer::maxSize)
{
    OutPacketBuffer::maxSize = devCapture->getBufferSize();
}
```

live555 の既定値は 60,000 バイトだが(`MediaSink.cpp:113`)、上記により
V4L2 デバイス側の値へ引き上げられる。

そして v4l2loopback は、**圧縮フォーマットに対しても解像度から
`sizeimage` を機械的に算出する**(`pix_format_set_size()`):

```c
} else if (fmt->flags & FORMAT_FLAGS_COMPRESSED) {
        /* doesn't make sense for compressed formats */
        f->bytesperline = 0;
        f->sizeimage = (width * height * fmt->depth) >> 3;
}
```

H.264 / H.265 はいずれも `depth = 32` と定義されている
(`v4l2loopback_formats.h`)ため、`sizeimage = 幅 × 高さ × 4` となる。

### 算出されるバッファサイズ

| 構成 | 計算式 | sizeimage | 結果 |
| --- | --- | --- | --- |
| 1920×1080 H.264 | 1920×1080×4 | **8,294,400 バイト(7.91 MB)** | 失敗 |
| 640×360 H.265 | 640×360×4 | **921,600 バイト(0.88 MB)** | 成功 |

**約 9 倍の差**があり、成否の分かれ目と完全に一致する。実際の圧縮フレームは
数十〜数百 KB(実測ビットレート 174 kbps)なので、1080p では
**実需要の 20〜80 倍を確保している**ことになる。

さらにこの値は 2 か所で効く。

1. v4l2loopback 自身のバッファ: `buffer_size × max_buffers` = 7.91MB × 2 = **約 16MB**
2. live555 の `OutPacketBuffer`: 各 sink / filter が maxSize 分を確保
   (`AddH26xMarkerFilter` も `m_bufferSize = OutPacketBuffer::maxSize`)

再利用可能メモリが約 28MB しかない環境では、これだけで枯渇する。

### 先に試した `sizeimage` 明示が効かなかった理由も判明

フック側で `VIDIOC_S_FMT` に `sizeimage` を設定したが、v4l2loopback の
`vidioc_try_fmt_out()` は**呼び出し側の `sizeimage` を無視して
`pix_format_set_size()` で必ず再計算する**ため、指定値は捨てられていた。
`MemFree` が変化しなかったのはこのためで、対策自体が届いていなかった。

### 想定している修正

v4l2loopback にパッチを当て、圧縮フォーマットでは呼び出し側が指定した
`sizeimage` を尊重する(またはより現実的な既定値にする)のが、
1 か所の修正で loopback と live555 の双方に効くため最も筋が良いと考えている。
この方針の妥当性についても意見をいただきたい。

## 7. 質問したいこと

1. **1080p H.264 を成立させる現実的な手段はあるか。**
   v4l2rtspserver / live555 側で、1080p ストリームを扱う際のメモリ使用量を
   大きく削減できるオプションや実装上の工夫はあるか
   (`-Q` 以外に効くパラメータ、live555 の `OutPacketBuffer::maxSize`
   相当の調整、read インターフェース `-r` の効果など)

2. **切り分けの方法。**
   BEAM ごと応答不能になるためターゲット上での観測が難しい。
   この状況で「どのプロセスがどれだけ確保したか」を確実に記録する手段
   (OOM killer のログ取得、`/proc/*/smaps` の定期採取、
   シリアルコンソール経由の観測など)の定石を知りたい

3. **設計上の判断。**
   87MB でベンダーランタイム(実測で大半を消費)と 1080p RTSP を共存させるのは
   そもそも無理筋で、640×360 H.265 での運用に確定するのが妥当か。
   それとも見落としている選択肢があるか

4. **H.264 を優先する場合の代替。**
   ベンダー ch0 は 1080p 固定に見えるが、ベンダー設定で解像度を下げる、
   あるいは H.265(640×360)を H.264 にトランスコードせず
   クライアント互換性を確保する方法(ブラウザ再生など)について助言があれば

5. **軽量な代替 RTSP サーバー。**
   live555 ベースの v4l2rtspserver 以外に、この規模の機器で
   「エンコード済み H.264 の V4L2 デバイスをそのまま RTSP 配信する」用途に
   適した、よりメモリ効率の良い実装はあるか

## 8. 補足情報

- 参考にした先行実装: [mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools)。
  同一ハードで v4l2loopback + v4l2rtspserver による RTSP 配信を実現している。
  ただし同プロジェクトはベンダーのファームウェア上で動作しており、

- 本件は Nerves(Erlang/OTP)がユーザー空間全体を管理しており、

  差し替えると U-Boot が起動できなくなるため、
  カーネル設定の変更(例: `mem=` の拡大)は不可

## 10. 解決結果(2026-08-02)

### 適用した修正

v4l2loopback の `vidioc_try_fmt_out()` にパッチを当て、**圧縮フォーマットに
限り、呼び出し側が指定した `sizeimage` が算出値より小さい場合はそれを尊重する**
ようにした(`package/atomcam2-v4l2loopback/0002-honour-compressed-sizeimage.patch`)。
`sizeimage` を 0 のままにする既存の利用者には影響しない。

これにより 1080p H.264 のバッファ上限は **7.91MB → 512KB**(フック側の指定値)
となり、v4l2loopback のバッファと live555 の `OutPacketBuffer::maxSize` の
双方が同時に縮小される。

### 実測結果(1920×1080 H.264)

| 項目 | 値 |
| --- | --- |
| URL | `rtsp://<camera>:8554/video0_unicast` |
| SDP | `H264/90000`、`profile-level-id=4d0029`、`x-dimensions:1920,1080` |
| 受信量 | 15 秒で 1.78MB、30 秒で 3.85MB(約 952 kbps) |
| フレーム | IDR 14 枚 + 非 IDR 262 枚 = 276 枚 / 15 秒 = **約 18.4 fps** |
| ベンダーランタイム | 30 秒連続受信後も `result=running`、エンコーダエラー 0 件 |

### プロセス別 RSS(助言に従い追加。全構成同時稼働時)

| プロセス | VmRSS | 備考 |
| --- | --- | --- |
| `beam.smp`(Erlang VM) | **30,556 kB** | 最大の消費者。Nerves の本体 |
| `iCamera_app`(ベンダー) | 20,528 kB | VSZ は 764MB だが実 RSS はこの程度 |
| `v4l2rtspserver` | **4,204 kB** | パッチ後。修正前は起動しきれなかった |
| システム全体 | MemFree 1,552 kB / Cached 23,540 kB | 再利用可能 約 25MB |

**BEAM が 30MB を占めている**点は、いただいた仮説⑨(atomcam_tools との差は
BEAM の常駐分)を裏付けている。ただし今回の失敗の直接原因は総量不足ではなく、
上記の過大なバッファ確保だった。パッチ後は v4l2rtspserver の RSS が 4MB に
収まり、3 プロセス同時稼働が成立している。

### いただいた助言のうち採用した点・不要になった点

| 助言 | 結果 |
| --- | --- |
| ① live555 のバッファが主因 | **的中**。ただし live555 の既定値(60,000)ではなく、v4l2rtspserver が V4L2 のバッファサイズで上書きしていたことが原因 |
| ② `-Q` が効かない理由 | **的中**。capture queue しか減らないため無効だった |
| ③ `sizeimage` 変更が効かない理由 | 指摘とは別の理由だった。v4l2loopback が呼び出し側の `sizeimage` を**無視して再計算**していたため、そもそも設定が届いていなかった。これを可能にするパッチが解決策になった |
| ④ direct reclaim の可能性 | 未検証。パッチで問題が解消したため OOM / reclaim の判別は不要になった |
| ⑩ BEAM 停止での切り分け実験 | 実施不要になった。原因が定量的に特定できたため |
| RSS の追加(文書改善の指摘) | **採用**。上表のとおり追加 |

助言のおかげで「live555 側のバッファ」に焦点を絞れたことが、
`DeviceSourceFactory.h` の `OutPacketBuffer::maxSize` 上書きを見つける
決め手になった。
