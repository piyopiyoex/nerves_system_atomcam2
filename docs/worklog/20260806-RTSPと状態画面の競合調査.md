# 2026-08-06 RTSP と状態画面の競合調査

## 文書情報

- 日付: 2026-08-06
- 種別: 技術調査
- 状態: 調査完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

## 結論(TL;DR)

- **競合は実在し、コード上に根拠がある**。ダッシュボードの「映像」タブは
  `/snapshot.jpg` を **1 秒間隔**でポーリングし、`CameraNative.snapshot/1`
  経由で camd の **JPEG エンコーダを起動**する。このチャンネルは
  **H.264(RTSP)チャンネルとバッファを共有**しており
  (`camera_native.ex` のコメントに明記)、頻繁な capture がエンコーダに
  ストレスを与える。**サーバ側で 1.5 秒のレート制限が既に入っている**
  ことから、開発時点でこの問題は認識・部分対策済みだったと分かる。
  さらに UI には「スナップ表示 ON/OFF」という**A/B テスト用トグルが
  既に実装されており**、コード中のコメントで
  「for A/B testing whether the snapshot load affects the RTSP stream」
  と明記されている。
- **192.168.1.77 の無出力(wedge)からの復旧は、ダッシュボードを止めてから
  reboot した後に成功した**。この順序を再現するため、ダッシュボードを
  無効化した状態で 192.168.1.77 に対し **10 回連続 reboot** を行い、
  camd のフレーム生成(RTSP 配信の実体)が毎回成立するかを検証した。
  **10/10 全て成功**、フレーム生成までの時間もばらつきなく安定していた
  (後述)。
- **真の A/B 比較も実施済み**。同一機・同一手順でダッシュボードを
  **有効化**した状態で 10 回 reboot を試みたところ、**1〜3 回目が
  3 回連続で無出力(wedge)** となり、サーキットブレーカーで自動停止
  した(10 回目まで到達できず)。**ダッシュボード無効化: 10/10 成功
  vs 有効化: 3/3 失敗**という明確な対比が得られ、当初の相関的な仮説は
  **因果関係として強く裏付けられた**(§3.4)。
- 追加で **参考実装 [mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools)
  の Web サーバー構成を調査**した結果、同種の競合が構造的に起きない
  設計だと判明した。vendor の iCamera_app をフルで動かし続け、独立した
  JPEG チャンネル(常駐コマンドソケット経由)をライブビューに使って
  いるため、頻繁なポーリングが H.264/RTSP チャンネルと衝突しない。
  本プロジェクトの camd は**メモリ制約から意図的に JPEG と H.264 の
  バッファを共有**する設計であり、これが競合の根本原因だと分かった
  (§5)。

---

## 1. 発端

2026-08-06、192.168.1.77 で「camd・v4l2rtspserver とも生存しているのに
snap 要求(`/tmp/camd.snap` touch)を出しても `/tmp/camd.jpg` が一切
生成されない」状態を確認(dmesg 上は他の稼働機と同一パターンで、ISP
初期化ログに異常な差分なし)。`Nerves.Runtime.reboot()` で復旧したが、
ユーザから「復旧した理由は、WEB ダッシュボードを止めた後にリブートした
ことだ。ダッシュボードと RTSP 配信に何らかの競合が見られる」との指摘が
あった。

この症状は [[atomcam2-rtsp-stability]] に記録済みの「camd init は
`=0` で全成功と報告するのに sensor/ISP が無出力になる wedge」パターンと
一致する。従来はこの wedge を `killall -9` や過剰な reboot による
churning が原因と整理していたが ([[atomcam2-device-handling]])、
**ダッシュボードの定期ポーリングも同種の wedge を誘発しうる**という
新しい仮説が浮上した。

## 2. コード上の競合ポイント

### 2.1 ライブ映像タブ: 1 秒間隔の JPEG capture

`examples/atomcam2_nerves_app/lib/atomcam2_nerves_app/dashboard/view.ex`
(94-118 行):

```js
// Live snapshot on/off (for A/B testing whether the snapshot load
// affects the RTSP stream). Persisted; default on.
...
setInterval(function () {
  if (!snapEnabled) return;
  var img = document.getElementById('snap');
  ...
  img.src = '/snapshot.jpg?' + Date.now();
}, 1000);
```

- 「映像」タブを開いている間、ブラウザは **1 秒ごとに `/snapshot.jpg`
  を取得**する。
- コードコメントに **「スナップ表示が RTSP ストリームに影響するかを
  A/B テストするため」** と明記されており、実装者自身がこの競合を
  疑っていたことが分かる。**default on**(=デフォルトで毎秒 capture
  が走る)。

### 2.2 `/snapshot.jpg` → camd の JPEG エンコーダチャンネル

`dashboard/router.ex` (50-61 行) は `/snapshot.jpg` を
`CameraNative.snapshot()` に委譲する。

`camera_native.ex` (117-143 行) のコメント:

```
# Minimum spacing between real captures. Each capture drives camd's JPEG
# encoder channel (which shares the H.264 channel's buffer), so frequent
# captures stress the encoder. Requests inside this window are served the
# cached JPEG instead of triggering a new capture, capping the rate no
# matter how fast the dashboard refreshes the live image (every 1 s).
@snapshot_min_interval_ms 1_500
```

- **camd の JPEG エンコーダチャンネルは H.264(RTSP)チャンネルと
  バッファを共有**しており、頻繁な capture はエンコーダにストレスを
  与えると明記。
- 対策として **1.5 秒のレート制限(キャッシュ)** が既に実装されている
  ため、ブラウザが 1 秒間隔で要求しても実際に camd を叩くのは
  最大でも 1.5 秒に 1 回に抑えられている。**ただし完全に無効化して
  いるわけではない**。

### 2.3 状態パネル: 2 秒間隔で CameraNative の GenServer を呼ぶ

`view.ex` (119-128 行) は「状態」「ログ」パネルを **2 秒間隔**で
`fetch('/')` により再取得する。`/` のレンダリングは
`Dashboard.Collector.collect()` を呼び、その中の `camera_status/0`
(`dashboard/collector.ex` 120-124 行) が

```elixir
GenServer.call(Atomcam2NervesApp.CameraNative, :status, @call_timeout_ms)
```

を実行する(`@call_timeout_ms = 200`)。`CameraNative` は camd/rtsp の
起動シーケンス・GO ハンドシェイク・RTSP ヘルスチェックなど**タイミング
に敏感な状態遷移を単一の GenServer プロセスで処理**しており
([[atomcam2-rtsp]] の「sprop 捕捉は確率的レース」参照)、そこに 2 秒
間隔で `:status` 呼び出しのメッセージが割り込む。個々の呼び出しは
軽量だが、**起動直後の GO ハンドシェイク窓と重なった場合の影響は
未検証**。

### 2.4 まとめ: 疑わしい経路

```
ブラウザ(映像タブ表示中)
  → 1秒ごとに GET /snapshot.jpg
    → CameraNative.snapshot()
      → camd へ /tmp/camd.snap 書き込み(JPEGチャンネル起動)
        → H.264チャンネルとバッファ共有 → エンコーダにストレス
          → 起動直後(GOハンドシェイク中)に重なると
            camd init は成功するが sensor/ISP が無出力になる wedge
```

## 3. 実機検証: ダッシュボード無効化 + 10 回連続 reboot(192.168.1.77)

### 3.1 手順

1. `Atomcam2NervesApp.Dashboard.enable(false)` を実行(設定は
   `/data/atomcam2-dashboard/enabled.conf` に永続化され、以後の
   reboot でも維持される)。
2. `Nerves.Runtime.reboot()` を 10 回連続実行し、各サイクルで
   以下を計測:
   - `ping` 応答までの時間
   - `camd` / `v4l2rtspserver` プロセス出現までの時間
   - `/tmp/camd.snap` touch → `/tmp/camd.jpg` 生成(フレーム生成の
     実証)までの時間・サイズ
3. 3 回連続失敗した場合は自動停止(過剰な reboot 連打による VPU
   再 wedge を避けるサーキットブレーカー、[[atomcam2-device-handling]]
   の教訓を反映)。各サイクル間に 8 秒のインターバルを設けた。

### 3.2 結果

| iter | ping | process | frame | size | status |
|---|---|---|---|---|---|
| 1 | 37s | 45s | 47s | 93,628B | OK |
| 2 | 38s | 46s | 48s | 94,843B | OK |
| 3 | 37s | 45s | 47s | 99,618B | OK |
| 4 | 37s | 46s | 47s | 92,791B | OK |
| 5 | 38s | 46s | 48s | 91,457B | OK |
| 6 | 37s | 46s | 47s | 96,668B | OK |
| 7 | 38s | 46s | 48s | 98,677B | OK |
| 8 | 37s | 45s | 47s | 99,843B | OK |
| 9 | 38s | 46s | 48s | 98,804B | OK |
| 10 | 37s | 45s | 47s | 89,174B | OK |

- **10/10 全て成功**、失敗ゼロ。
- タイミングも極めて安定(ping 37-38s、process 45-46s、frame
  47-48s)。ばらつきが小さいことは、**wedge のような確率的な失敗が
  この条件では発生していない**ことを示唆する。
- 参考: 過去 1 回だけ観測した「無出力」インシデントは
  ダッシュボード有効時だった(本ドキュメント §1)。

### 3.3 §3.1〜3.2 検証の限界(解消済み)

当初はダッシュボード**無効化のみ**の 10 回で、「有効化状態と比較しない
限り相関に過ぎない」という限界があった。この限界は §3.4 の真の A/B に
より解消済み。

## 3.4 実機検証(真の A/B): ダッシュボード有効化 + 10 回連続 reboot

### 3.4.1 手順

§3.1 と全く同じ手順・同じサーキットブレーカー設定で、事前に
`Atomcam2NervesApp.Dashboard.enable(true)` を実行してから 10 回連続
reboot した(192.168.1.77)。

### 3.4.2 結果

| iter | ping | process | frame | status |
|---|---|---|---|---|
| 1 | 36s | 46s | TIMEOUT(30s) | **FAIL(no_frame/wedge)** |
| 2 | 37s | 45s | TIMEOUT(30s) | **FAIL(no_frame/wedge)** |
| 3 | 36s | 46s | TIMEOUT(30s) | **FAIL(no_frame/wedge)** |
| — | — | — | — | サーキットブレーカー発動(3 回連続失敗)、以降中断 |

- **3/3 全て失敗**。ping・プロセス起動(camd/v4l2rtspserver とも生存)
  までは §3.2 の成功ケースとほぼ同タイミング(36-37s / 45-46s)だが、
  **フレームは 30 秒待っても一切生成されず**、サーキットブレーカーが
  作動して 10 回に到達する前に自動中断した。
- §3.2(無効化・10/10 成功)と条件を揃えた直接対比により、
  **「ダッシュボード有効化 → 無出力 wedge」の因果関係が強く裏付け
  られた**。camd・rtspserver のプロセス自体は正常起動するのに
  sensor/ISP が無出力になる、という [[atomcam2-rtsp-stability]] に
  記録済みの wedge パターンと完全に一致する。

§3.4 後にダッシュボードを再度無効化し(`enable(false)`)、§3.1 と同一
手順で reboot を再試行した。目的は §3.2 の「10/10 成功」がたまたま
ではなく再現するかどうかの確認。

| 4 | 38s | 46s | 48s | 90,909B | OK |
| 5 | 37s | 45s | 47s | 91,204B | OK |
| 6 | 38s | 46s | 48s | 91,112B | OK |
| 7 | 37s | 45s | 47s | 91,717B | OK |
| 8 | 36s | 44s | 46s | 91,026B | OK |
| 9 | 38s | 46s | 48s | 91,836B | OK |

- **10/10 全て成功**、§3.2 と同様のタイミング(ping 36-38s /

- 通算: **ダッシュボード無効化 20/20 成功(§3.2 + §3.5)、有効化
  3/3 失敗(§3.4)**。因果関係の裏付けとしては十分な強度と判断する。

## 4. 推奨アクション

1. ~~次の検証: ダッシュボード有効化状態での同条件 10 回検証~~ →
   §3.4 で実施済み。**ダッシュボード無効化 20/20 成功(§3.2+§3.5)
   vs 有効化 3/3 失敗(§3.4)**という明確な対比が得られた。
2. **恒久対策の候補**(優先度順、§5 の atomcam_tools 調査結果を反映):
   - **最有力**: camd の JPEG チャンネルを H.264 チャンネルと**独立
     したバッファ**にする(atomcam_tools が採用する「別チャンネルで
     JPEG を持つ」設計に倣う)。メモリ制約([[atomcam2-approach-b]])
     との兼ね合いが必要だが、根本原因を直接解消できる。
   - 次善策: 起動直後(GO ハンドシェイク完了・`phase: :running` に
     なるまで)は `/snapshot.jpg` を意図的に 503 で拒否し、camd の
     JPEG チャンネル起動を抑制する。
   - `@snapshot_min_interval_ms` を起動直後だけ延長する、または
     `CameraNative` の `phase` を見て capture を抑制する(部分対策。
     現状の 1.5 秒レート制限だけでは §3.4 の wedge を防げなかった
     ことに注意)。
3. **運用上の暫定策**: 実機の切り分け作業時は、映像タブを開いた
   ブラウザを閉じる(またはダッシュボードを無効化する)してから
   reboot する運用を当面継続する(§3.4 の結果によりこの運用の妥当性が
   裏付けられた)。

## 5. 参考実装との比較: atomcam_tools の Web サーバー構成

[mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools)(同じ
ISVP/T31 系カメラ向けの成熟した OSS ファーム改造プロジェクト)の Web
サーバー実装を調査し、**同種の競合が構造的に起きない設計**であることを
確認した。

### 5.1 構成

- **lighttpd**(静的ファイル配信 + CGI ディスパッチのみ、digest 認証)
  が Vue.js 製 SPA と `cgi-bin/` を配信する。動画処理は一切行わない。
- **`/var/www/cgi-bin/cmd.cgi`**: POST された JSON の `exec` を
  `/var/run/webcmd` という**名前付きパイプ**に書き込むだけの薄い
  ブリッジ。実際のコマンド処理は `webcmd.sh`(常駐シェルループ)が
  `/scripts/cmd` 経由で vendor の iCamera_app に委譲する。

### 5.2 ライブ映像(スナップショット)取得: `get_jpeg.cgi`

```sh
#!/bin/sh
echo jpeg | /usr/bin/nc localhost 4000
```

- vendor の iCamera_app が **localhost:4000 で待ち受ける常駐コマンド
  ソケット**に `jpeg` と送るだけの 1 行スクリプト。
- **go2rtc(WebRTC 配信)の video0 ソースもこの `get_jpeg.cgi` そのもの**
  に設定されており(`rtspserver.sh` 内の go2rtc config で
  `streams: video0: - http://localhost/cgi-bin/get_jpeg.cgi`)、go2rtc は
  可能な限り高頻度でこれをポーリングして疑似ライブ映像を構築している。
  つまり atomcam_tools は**むしろ本プロジェクトより高頻度**に同種の
  エンドポイントを叩いているが、RTSP と競合しない。

### 5.3 本プロジェクトとの決定的な違い

atomcam_tools は **vendor の iCamera_app をフルで動かし続けたまま**、
その既存の JPEG チャンネル(vendor 設計で H.264 チャンネルとは
**独立したバッファ**を持つ、複数 IMP チャンネル構成)を叩いている
だけなので、高頻度ポーリングしても H.264(RTSP)と競合しない。

一方、本プロジェクトの `camd`(iCamera_app 非依存のスクラッチ実装、
[[atomcam2-approach-b]])は**メモリ制約から意図的に JPEG と H.264 の
バッファを共有**する設計を選んでいる(§2.2 のコード引用参照)。
**この設計選択自体が今回の競合の根本原因**であり、vendor アプリを
使い続けるアーキテクチャなら本質的に発生しない問題だと分かった。
これは §4 の恒久対策の優先順位付けに反映済み。

## 追記: その後の経緯

本調査で導入した JPEG チャンネル分離(camd VERSION 30)は
[JPEG/H.264 チャンネル分離 提案書](20260806-JPEGとH264の経路分離.md)
として提案・実装され、本ドキュメント §3.4/3.5 のとおり実証された。
その後フル解像度化を巡って発覚した別件(ISP キャリブレーションファイル
欠落による紫化)は
[ISP キャリブレーション欠落 技術相談](20260806-ISP補正情報欠落の調査.md)
にまとめてある。**2026-08-06 終了時点の稼働バージョンは camd VERSION 35**
(JPEG/H.264 チャンネル分離 + フル解像度 + ISP キャリブレーション同梱)。
