カメラの状態をブラウザから確認できる Web 画面(ダッシュボード)の提案。
現状の確認手段は SSH(IEx)経由のみで、`VendorCamera.status()` などを
打てる人しか状態を見られない。ブラウザ(PC・スマホ)で一目で確認できる
画面を、本機の厳しいメモリ制約の中で成立する最小構成で追加する。

関連: [平常時メモリ削減 提案書](20260803-平常時メモリ削減の検討.md)、
[RTSP 配信 提案書](20260802-RTSP配信方式の検討.md)、
[長時間動作 記録](20260802-長時間動作の検証.md)。
参考実装: `~/nerves_examples/hello_usbcam_rtsp` のダッシュボード
(Router/Collector/View 分割の閲覧専用ページ。詳細は後述)

改訂: 2026-08-04 レビューを反映(status.json の正規 API 化、Collector の
責務分割、非目標の明記、データ取得優先順位、タイムアウト数値化ほか)。
なお当面の状態確認は OSD デバッグパネル
([2026-08-04 作業記録](20260804-起動安定化と状態画面の作業記録.md) §1)で代替しており、本提案の
実装は「camd 停止時も見たい」「機械可読 API が欲しい」需要が出た時点で行う。

## 背景と目的

- 稼働確認のたびに SSH + IEx が必要で、家族や離れた場所からの
  「動いているか」の確認ができない
- RTSP の映像が止まったとき、原因(camd 停止か、loopback 書き出し停止か、
  サーバ停止か)の切り分けに毎回コマンドを打っている。フレーム心拍や
  各 GenServer の status は既にあるので、見せる場所だけが無い
- 長期運用ではメモリ残量・稼働時間・ファーム状態の推移を気軽に見たい

## 非目標(Out of Scope)

本提案は「状態を見る」ことだけを対象とする。以下は対象外:

- 録画機能・映像配信・ライブビュー(映像は RTSP + VLC の既存経路)
- 設定変更 UI・OTA 更新 UI(SSH / `mix upload` の既存経路)
- ログ検索(直近数行の表示のみ。全文は RingLogger を SSH で)
- 認証・ユーザー管理の仕組みづくり(Phase 2 の最小限の認証のみ)

## 前提と制約(メモリが最優先)

**本提案は `iCamera_app`(vendor カメラ)を使用しない前提で書く。**
vendor 三点(約 25MB)はメモリ容量の問題で起動できず、カメラは方式 B の
ネイティブスタック(camd 約 1.5MB + v4l2rtspserver 約 13MB)のみで運用
する。ダッシュボードに vendor 関連の表示・操作は持たない。

[平常時メモリ削減 提案書](20260803-平常時メモリ削減の検討.md) のとおり
メモリ余裕は乏しく、ダッシュボード自体も同じ制約に従う:

- **Phoenix / LiveView / Plug + Bandit は不採用**。依存追加だけで code が
  数 MB 増え、本末転倒
- **OTP 標準の `:inets` httpd を使う**。`mix.exs` の applications に
  `:inets` は既に入っており(fwup 用)、**新規依存ゼロ・追加コードは
  自前モジュール 1 つ**で済む
- ページは**サーバレンダリングの静的 HTML 1 枚**。JS フレームワーク無し、
  自動更新は `<meta http-equiv="refresh" content="10">` で行う
- 画像・CSS などのアセットは持たない(インライン CSS のみ)

## 表示する情報とデータソース

すべて既存の API / ファイルから読むだけで、新たな計測プロセスは持たない。

データ取得の優先順位は **OTP API → /proc → sysfs → 外部コマンド** とし、
`System.cmd/3` の実行は最小限にする(現状 df 相当のみ。ps 相当は
`/proc/<pid>/status` で代替する)。

カメラ状態は Stage 5 で導入する `CameraNative` GenServer(camd の監督)の
status を正とする。`CameraNative` が入るまでの暫定は camd プロセスの直接
参照で同じ欄を埋める。

| 区分 | 項目 | データソース |
| --- | --- | --- |
| カメラ | **native カメラ(camd)の稼働**・PID・RSS・再起動回数 | `CameraNative.status/0`(暫定: `ps` / `/proc/<pid>/status` + `/data/camd.ctl`) |
| カメラ | camd の直近ログ(数行) | `/data/camd.log` の tail |
| RTSP | サーバ状態・**フレーム心拍**・stall ストライク | `RtspServer.status/0`(native 経路の心拍に接続) |
| RTSP | 接続 URL(`rtsp://<ip>:8554/...`) | `Debug.ip/0` から組み立て |
| NAS | エクスポート状態・最終転送 | `NasExporter.status/0` |
| 時刻 | NTP 同期状態・現在時刻 | `TimeSync` / `NervesTime` |
| ネットワーク | wlan0 / eth0 の IP・SSID・接続状態 | `Debug.wifi/0` `Debug.ip/0` / VintageNet property |
| メモリ | MemFree / MemAvailable / beam RSS | `/proc/meminfo`、`/proc/self/status` |
| ファーム | バージョン・スロット(A/B)・validated | `Nerves.Runtime.KV` |
| 稼働 | uptime・再起動回数 | `/proc/uptime`、`FirmwareHealth` |
| ストレージ | /data・SD の使用量 | `:disksup` は使わず `df` 相当を都度実行 |
| 稼働 | loadavg・CPU クロック | `/proc/loadavg`、`cpufreq` sysfs(あれば) |
| ログ | BEAM ログの直近数行 | Logger バックエンド経由で取得(現状は RingLogger。利用できない場合は `unavailable` 表示) |

## 参考実装: hello_usbcam_rtsp のダッシュボード

`~/nerves_examples/hello_usbcam_rtsp` の閲覧専用ダッシュボードを設計の
下敷きにする。持ち込むもの:

- **モジュール分割**: `Router`(ルーティング)/ `Collector`(情報収集)/
  `View`(サーバレンダリング HTML)。収集とレンダリングが分離されている
  ため JSON 出力も同じ Collector で済む
- **閲覧専用 + `GET /healthz`**(死活確認、`ok` を返す)という構成
- meta refresh による自動更新
- 「応答しない情報源があっても欄を `unavailable` にしてページは返す」方針

持ち込まないもの(本機の制約による差分):

- **Bandit + Plug は使わない**。usbcam 側は RPi 系でメモリに余裕がある。
  本機は依存追加そのものが重いので、同じモジュール分割を
  **`:inets` httpd(標準ライブラリ)** の上で行う
- **`/fragment`(表部分だけ返すエンドポイント)は持ち込まない**。JS で
  差し替えるための仕組みであり、JS を書かない本機では meta refresh で
  `/` を丸ごと更新すれば足りる
- **ffmpeg スナップショット**(配信中の RTSP から 1 フレームだけ JPEG 化)
  は本機ではデバイス上に ffmpeg が無く CPU/メモリ余裕も無いため見送り
  (Phase 3 参照)

## 提案する実装

### Phase 1: 状態 API + 読み取り専用ページ(本提案の主対象)

`Atomcam2NervesApp.Dashboard.{Router,Collector,View}` を追加する
(構成は hello_usbcam_rtsp を踏襲、HTTP サーバだけ `:inets` httpd)。
ルートは 3 本だが、Phase 2 で POST(操作)を足す前提があるため
`Router` の名を維持する(読み取り専用で確定なら `Dashboard.HTTP` 程度で
足りる)。

**`status.json` を正規の状態取得 API と位置付け、HTML はその表示に
過ぎない**ものとして設計する。さらに **Collector は内部データ(Map)
だけを返し、JSON / HTML への変換は別層**とする:

```
Collector → 内部データ(Map)─┬→ JSON エンコード → status.json(正規 API)
                              └→ HTML レンダリング → GET /
```

将来 Home Assistant・Grafana・Prometheus exporter・自作監視などが読むのは
`status.json` であり、HTML の都合で JSON の形を変えない。表現層を分離して
おくことで、将来 MQTT・CLI・CSV などの出力を足しても **Collector は一切
変更不要**になる。

レスポンス例(トップレベルは Collector のカテゴリそのまま):

```json
{
  "camera":   { "phase": "running", "camd_pid": 506, "rss_kb": 3072 },
  "rtsp":     { "server": "running", "url": "rtsp://192.168.1.77:8554/video0_unicast" },
  "memory":   { "total_mb": 85, "free_mb": 2, "avail_mb": 41, "beam_total_mb": 25 },
  "network":  { "eth0": "192.168.1.77", "wlan0": "192.168.91.77" },
  "firmware": { "version": "0.4.0", "slot": "A", "validated": true },
  "storage":  { "data_used_mb": 903, "data_size_mb": 57955 },
  "logs":     { "tail": ["...", "..."] }
}
```

状態を表す文字列は**固定の列挙値**とし、表記揺れ(`RUNNING` / `Run` /
`OK` など)を作らない。例: `camera.phase` は `CameraNative` の phase を
そのまま使う — `not_checked | disabled | waiting | starting | running |
degraded`。新しい値の追加は可、既存値の改名は不可(API の互換性)。

パスは LAN 限定・後方互換の要件が無いため `/status.json` のままとする
(将来 LAN 外や複数バージョン共存が必要になった時点で `/api/v1/status` 化
を検討)。

- **IEx から ON/OFF できる**こと(OSD デバッグパネルと同じ運用):

  ```elixir
  Atomcam2NervesApp.Dashboard.enable(true)   # 起動(数秒で有効)
  Atomcam2NervesApp.Dashboard.enable(false)  # 停止
  ```

  - `Dashboard` は **Facade**(公開 API はこの 1 モジュール)とし、
    実体の起動・停止は `Dashboard.Supervisor` が担う
  - 設定は `/data/atomcam2-dashboard/enabled.conf` に永続化し、再起動後も
    維持する。**既定は OFF**(運用時はダッシュボード無し)。設定項目が
    増えたら(port・refresh 間隔など)`dashboard.config` 1 ファイルへの
    統合を検討する(現状は enabled のみなので単純なままにする)
  - **OFF のときはダッシュボードの全機能が停止する**: httpd リスナを
    terminate してポートを閉じ(接続拒否)、Collector の呼び出しも一切
    行わない。OFF 時の常駐メモリ増・CPU 消費・攻撃面は**ゼロ**
  - 実装は supervision tree 上で httpd を独立 child とし、ON/OFF は
    child の start/terminate で行う(プロセスごと消えるので「機能の
    一部が残る」状態が構造的に起きない)
- `:inets` の `:httpd` を supervision tree に追加。ポートは**既定 80**、
  `config.exs`(`config :atomcam2_nerves_app, :dashboard, port: ...`)で
  変更可能にする
- ルート
  - `GET /status.json` — Collector の結果をそのまま JSON で返す(正規 API)
  - `GET /` — status.json と同じデータの HTML 表示(10 秒ごと自動リフレッシュ)
  - `GET /healthz` — 死活確認(`ok`)
- **Collector は集約のみ**を責務とし、カテゴリ毎の関数に分割する
  (肥大化防止。各関数は独立してテスト・失敗できる):

  ```elixir
  defmodule Dashboard.Collector do
    def collect do
      %{
        camera: camera(),      # CameraNative.status
        rtsp: rtsp(),          # サーバ状態・心拍
        memory: memory(),      # /proc/meminfo + :erlang.memory
        network: network(),    # ifaddrs / VintageNet
        firmware: firmware(),  # Nerves.Runtime.KV
        storage: storage(),    # /data・SD 使用量
        logs: logs()           # RingLogger tail
      }
    end
    # camera/0, rtsp/0, ... は各 30〜50 行に収める
  end
  ```
- レンダリングは EEx をコンパイル時展開(実行時テンプレートエンジン無し)
- 各 status 呼び出しは **タイムアウト 200ms**(`GenServer.call(..., 200)`)
  を目安とし、応答しない GenServer があってもページ全体は返す(該当欄に
  `unavailable` を出す)。カテゴリ取得は当面逐次で足りるが、応答時間が
  問題になれば `Task.async_stream` による並列取得の余地を残す(Collector
  がカテゴリ関数分割になっているため、変更は collect/0 内に閉じる)

メモリ見積もり: httpd はリスナ + リクエスト毎の短命プロセスのみ。
**ON 時の増分 1MB 未満を目標とし、実測で評価する**(数百 KB 程度と
見込むが根拠は実測で得る)。**OFF 時(既定)はゼロ**。実装後に
before/after を
[平常時メモリ削減 提案書](20260803-平常時メモリ削減の検討.md) の
ベースラインへ追記する。

### Phase 2(任意): 操作ボタン

読み取りで運用が回ってから、POST 限定で最小限の操作を足す:

- 再起動(`Nerves.Runtime.reboot/0`、確認ダイアログ付き)
- テスト発声(`atomcam2-aoplay` 呼び出し)

vendor カメラの起動操作は**提供しない**。メモリ容量の問題で起動は不可能
であり、ボタンがあると誤操作でメモリ飽和を誘発するだけのため。

誤操作・いたずら対策として、Phase 2 に入る時点で最低限の認証を必須にする。
方針を先に決めておく:

- **GET(読み取り)は匿名のまま**(Phase 1 と同じ)
- **POST(操作)のみ認証**(httpd の Basic 認証 or 合言葉トークン)
- CSRF 対策は不要(読み取りは副作用なし、操作は認証必須のため。
  ブラウザからの誤送信対策として POST は確認ダイアログを挟む)

### Phase 3(研究): 静止画プレビュー

ダッシュボードに現在の映像の静止画を出す案。hello_usbcam_rtsp は
「配信中の RTSP を ffmpeg で 1 フレームだけデコードして JPEG 化」する
非干渉な方式で実現しているが、本機はデバイス上に ffmpeg が無く、
CPU・メモリの余裕も無いため**デバイス上でのデコードは見送り**。

代替案(いずれもデバイス外):

- RTSP URL の表示 + VLC で開く手順の記載に留める(当面はこれ)
- LAN 内の別ホスト(NAS・常時稼働 PC)が RTSP から定期的に JPEG を
  作り、ダッシュボードはその URL を `<img>` で参照する(デバイス負荷
  ゼロ。将来 NAS エクスポートと同居させる案)

## セキュリティの考え方

- LAN 内限定の読み取り専用ページとして開始(Phase 1 は操作を持たない)
- 表示内容に秘匿情報(パスフレーズ・鍵)は含めない。SSID は表示するが
  パスフレーズは出さない
- 操作(Phase 2)を足す時点で認証を導入。インターネット公開はしない

## リスクと検証項目

| リスク | 検証 |
| --- | --- |
| メモリ増で常用時の余裕をさらに削る | 既定 OFF(増分ゼロ)。ON 時は native カメラ(camd)+ RTSP 稼働状態で MemFree / beam RSS を before/after 実測。増分が 1MB を超えるなら設計を見直す |
| OFF にしたのに機能の一部が残る | httpd を独立 child とし ON/OFF は child の start/terminate で行う。OFF 後にポート接続拒否・プロセス消滅を確認 |
| status 呼び出しがカメラ動作へ干渉 | 全て既存の読み取り API。ページアクセス連打(10 req/s)でも RTSP 心拍が乱れないことを確認 |
| httpd プロセスの異常でアプリ全体が巻き込まれる | supervision tree で独立 child にし、restart しても他へ影響しないことを確認 |
| ポート 80 が他機能と衝突 | 現状 80 は未使用(RTSP は 8554、SSH は 22)。既定 80、config.exs で変更可能 |
| Collector の肥大化 | collect/0 は集約のみ、カテゴリ関数分割を規約とする(上記) |

## 将来拡張(status.json を正規 API とする理由)

実装はしないが、以下の連携先を想定して JSON の形を保つ:

- Home Assistant(RESTful sensor で status.json を直接読める)
- Prometheus exporter / Grafana(status.json → メトリクス変換)
- Node-RED・自作監視スクリプト(curl + jq)
- MQTT ブリッジ(status.json を定期 publish する外部プロセス)

いずれもデバイス側の変更なしに status.json の消費側として追加できる。
