## 1. ビルド環境

シェルのデフォルトはグローバル mise 設定の Elixir 1.19.4-otp-28 だが、
system v0.3.0 のターゲットは OTP 29 のため、そのままでは
`mix firmware` がバージョン不一致で失敗する。リポジトリの `.tool-versions`
は非対話シェルでは自動適用されない。

**確定した手順**: リポジトリ内では常に `mise exec -- mix ...` を使う。

```sh
cd examples/atomcam2_nerves_app
export MIX_TARGET=atomcam2 MIX_ENV=prod
mise exec -- mix setup
mise exec -- mix firmware
```

`Enum.__in__/2 is undefined` が出た場合は Hex アーカイブの Elixir
バージョン不一致なので、`mix local.hex --force` と
`mix archive.install hex nerves_bootstrap --force` で入れ直す。

### system をソースからビルドする場合

```sh
export ATOMCAM2_SYSTEM_SOURCE=local
export ATOMCAM2_KERNEL_IMAGE=<repo>/target/atomcam2-control/factory_t31_ZMC6tiIDQN
export NERVES_WIFI_SSID=... NERVES_WIFI_PASSPHRASE=...
export ATOMCAM2_AUTHORIZED_KEYS="$HOME/.ssh/id_rsa.pub"
mise exec -- mix firmware
```

**Wi-Fi と SSH 鍵の環境変数を必ず渡すこと。** ローカルビルドでは
`post-image.sh` が `nerves-provisioning.conf` と `authorized_keys` を
環境変数から作り直すため、渡さないと空になり Wi-Fi にも SSH にも
つながらなくなる。

ツールチェーンアーカイブは初回のみ用意が必要。

```sh
NERVES_TOOLCHAIN=~/.nerves/artifacts/nerves_toolchain_atomcam2-linux_x86_64-0.3.0 \
  ./scripts/prepare-toolchain-archive.sh
```

## 2. 有線 LAN 対応

[mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools) を参考に、
USB Ethernet アダプタ経由の有線接続を実装した。

- カーネル defconfig に USB NIC ドライバ 6 種を `=m` で追加
- `atomcam2-eth-driver` を新設し、`atomcam2-pre-run` から Wi-Fi より先に実行
- アプリに `vintage_net_ethernet` を追加し `eth0` を常時 DHCP 構成

実機検証: Realtek RTL8152(`0bda:8152`)で `eth0` が DHCP 取得、
デフォルトルートは有線優先(eth0 metric 10 < wlan0 metric 20)。

想定と違った点は次の 3 つ。

- atomcam_tools の `devmem` による GPIO 初期化は**不要**だった。同じレジスタは
  Wi-Fi 用 SDIO ピン初期化と同一で、本システムでは既に実施済み
- r8152 のバックポートは**不要**。Wyze/Ingenic カーネルツリーに含まれていた
- SD 再書き込みは**不要**。モジュールの vermagic が既存の制御カーネルと
  一致するため `mix upload` だけで有効になった

## 3. RTSP 配信

ベンダーランタイムがハードウェアエンコードした映像を、再エンコードせずに
配信する。

```text
iCamera_app → libvideo-hook.so（LD_PRELOAD）→ v4l2loopback → v4l2rtspserver
```

- 新規パッケージ 4 つ: `atomcam2-video-hook`、`atomcam2-v4l2loopback`、
  `v4l2cpp`、`v4l2rtspserver`(映像のみ。本カーネルは ALSA 非搭載)
- 新規スクリプト 2 つ: `atomcam2-video-loopback`(起動時ロード)、
  `atomcam2-rtsp-server`(起動・停止・状態)
- `RtspServer` GenServer: `/data/atomcam2-rtsp/auto-start.conf` で有効化し、
  カメラ互換ランタイムに追従して起動・停止する

実機検証: 1920×1080 H.264 を約 18 fps・約 950 kbps で配信
(`rtsp://<camera>:8554/video0_unicast`)。640×360 H.265 も確認済み。
起動時の自動起動と、ベンダーランタイム停止時の自動停止も確認した。

同時稼働時の RSS は BEAM 30.5MB、`iCamera_app` 20.5MB、
`v4l2rtspserver` 4.2MB(全 87.7MB)。

## 4. 得られた知見(再発防止)

### 制御カーネルは差し替えてはいけない

有線 LAN 対応の作業中、Buildroot がビルドしたカーネルを制御カーネルとして
採用し `scripts/post-image.sh` の SHA ピンを更新したところ、**カメラが
Nerves を起動しなくなった**。U-Boot が SD から起動できず、内蔵フラッシュの
純正ファームで立ち上がる。

U-Boot が読める `factory_t31_ZMC6tiIDQN` は検証済みの純正互換バイナリだけで、
`post-image.sh` は Buildroot 版をこのバイナリで上書きする作りになっている。
SHA ピンはまさにこの差し替えを防ぐガードだった。Buildroot のカーネルビルドは
**vermagic が一致するモジュールを得るため**に存在する。

- **失敗のサイン**: SD に `atomcam2-*.env` が一切残らず、代わりに純正アプリの
  `log/`、`record/`、`time.ini` が生成される
- **復旧元**: `~/.nerves/dl/nerves_system_atomcam2-portable-0.3.0-*.tar.gz` の
  `images/uImage.lzma`(`sha256 b50658ea…`)

教訓として、ガードに阻まれたときは回避する前に「なぜ守られているのか」を
確認する。

### 圧縮フォーマットのバッファサイズ

v4l2loopback は圧縮フォーマットに対しても解像度から `sizeimage` を算出する
(`幅 × 高さ × 32 / 8`)。1080p では **7.91MB/バッファ**となり、実際の
フレーム(数十〜数百 KB)の 20〜80 倍を確保していた。

この値は 2 か所で効く。v4l2loopback 自身のバッファ(`× max_buffers`)と、
v4l2rtspserver が live555 の `OutPacketBuffer::maxSize` へ代入する分
(各 sink / filter が確保)。87MB の本機ではこれだけで枯渇し、RTSP サーバー
起動と同時にユーザー空間全体が応答不能になっていた。

`sizeimage` を尊重するパッチを v4l2loopback に当てて解決した。

### LD_PRELOAD ライブラリのシンボル解決

コンストラクタ内で `dlopen` してもシンボルを解決できない(動的リンカの
初期化前に走るため)。**遅延解決 + `RTLD_NEXT`** を使う。

解決に失敗するとベンダーのコールバック登録が失敗し、全エンコーダチャンネルが
止まる(`IMP_Enc_PollingStream fail` が連発したらこのサイン)。

### この環境に `pidof` はない

busybox が `pidof` を含まないため、プロセス検出は `/proc/[0-9]*/status` の
`Name:` を走査する(`atomcam2-vendor-camera` の `process_running` と同じ方式)。

### mix upload の後は確定を待つ

`mix upload` はファームを非アクティブスロットへ書いて再起動し、その後
ヘルスチェックの安定化(30 秒)を経てスロットを確定する。**確定前に再起動すると
ロールバックする。** `Nerves.Runtime.firmware_validation_status()` が
`:validated` を返してから次の操作に進む。

また、メモリに余裕がない状態(ベンダーランタイム稼働中など)では
アップロードが途中で切断されることがある。事前にベンダーランタイムを
停止しておくと確実。

### IP アドレスは固定しておく

この日の作業中だけでカメラの IP は `.64` → `.65` → `.66` と変わり、そのたびに
到達できず、サブネット全体を走査して MAC から探し直す作業が発生した。
`mix upload` の宛先や RTSP の URL も指定し直しになる。

**ルーターの DHCP 予約(MAC に対する固定割り当て)を最初に設定しておくこと。**
カメラ側の設定変更は不要で、これがもっとも確実である。

無線と有線は別の MAC であり、**有線側は USB アダプタ固有**なのでアダプタを
交換すると変わる(実際この日の作業中に交換して変わった)。両方使うなら 2 件
とも予約する。

`nerves.local` の mDNS でも接続できるが、ホスト側に avahi がない環境では
解決できないため、IP 固定のほうが確実。

### 同一エンコーダチャンネルの競合

RTSP 配信中にモバイルアプリでライブ映像を **HD に切り替える**と、RTSP の映像が
止まる。HD ライブはチャンネル 0(1080p H.264)を使い、RTSP が横取りしている
チャンネルと同一のため。SD 視聴中は競合しない。

**障害ではない**。`v4l2rtspserver` も `iCamera_app` も生きたままで、メモリも
枯渇しておらず、アプリを終了すれば自動的に復旧する。

競合回避のため ch3(1080p H.265)へ退避する案を検証したが不採用とした。
H.265 は検証に使った VLC 3.0.x でデコードできず、さらにモバイルアプリ側の
再生まで停止した(ch3 はベンダーがクラウド配信や録画に使っている可能性が
ある)。**ch0 の競合を避けようとして別の競合を作る結果**になった。

なお `ATOMCAM2_VIDEO_LOOPBACK_VIDEO_NR` を変えると RTSP のパスも
`video<N>_unicast` に変わる。クライアント側の URL 更新を忘れると、
サーバー故障と区別がつかない症状になる(実際に混乱した)。VLC は履歴から
古い URL を再利用するため、履歴から選ばず入力し直すこと。

#### 追記: HD/SD 切り替えの繰り返しでパイプライン全体が停止する

23 時台に再発した停止は、SD カードの `/data` に残った記録から次のことが
確定した(電源断の瞬間までサンプラーが 30 秒ごとに記録を続けていた)。

- **メモリは最後まで正常**(BEAM 31.6MB、`v4l2rtspserver` 2.2MB、横ばい)。
  BEAM は生きてサンプラーを回し続けていたのに SSH バナーが返らなかった。
  これは**メモリではなく CPU 枯渇**のパターン
- ベンダーログ 146,487 行のうち、**`IMP_Enc_PollingStream fail` 336 件が
  すべて末尾 10% に集中**し、同じ領域にアプリの HD/SD 解像度切り替えが
  9 件記録されていた。失敗は**全 3 チャンネル**(chn0/1/3)に及ぶ
- ベンダー内部の exec メッセージキューも同時に失敗(`msgque ret:[-1]`)

つまり、単発の HD 切り替えで起きる「RTSP だけ止まり自動復旧する」競合とは
別に、**VLC + アプリ同時利用中に HD/SD を繰り返すと、ベンダーの
エンコーダパイプライン全体が停止して自動復旧しない**状態に陥る。ベンダーの
スレッドがポーリング再試行でシングルコア CPU を食い潰し、ユーザー空間全体
(SSH、RTSP、アプリ配信)が飢餓する。カーネル(ping)と BEAM の低頻度処理は
生き残るため、外からはメモリ枯渇と区別しにくい。

**自動復旧しない理由**: heart は BEAM が生きている限り watchdog を養い続け、
ベンダーの watchdog 呼び出しはシムが吸収している。エンコーダ停止を検知して
再起動する仕組みが存在しない。**改善候補**: フレーム供給の健全性(フックの
書き込みカウンタ等)を監視し、停止が続いたら意図的に再起動する仕組みを
FirmwareHealth の流儀で追加する。

**当面の運用**: RTSP 配信中はアプリの HD/SD 切り替えを繰り返さない。
停止したら電源再投入で復旧する(今回 SD の構造破損はなく、再投入だけで
戻る状態だった)。

副次的な発見として、ベンダーは毎分の録画ファイル移動後に
`echo 1 > /proc/sys/vm/drop_caches` を実行しようとするが、**隔離環境の
ケーパビリティ剥奪により失敗している**(exit 1)。87MB 機でページキャッシュを
毎分捨てられると致命的なので、この遮断は結果的に正しく働いている。

### メモリリークはなかった

`/proc/meminfo` と主要プロセスの `VmRSS` を 30 秒間隔で記録した結果、
`beam.smp` 約 30〜32MB、`v4l2rtspserver` 約 2.3〜2.4MB、`iCamera_app`
16.5〜18.5MB でいずれも横ばいだった。`MemFree` の増減は `Cached` と逆相関して
おり、ページキャッシュの正常な挙動である。

当初「メモリリークによる停止」を疑ったが、実際の停止要因は上記のチャンネル
競合と、MicroSD の構造破損だった。**症状から原因を推測せず、計測してから
判断すること。**

サンプラーは BEAM 内で動かした(`/data/sampler.exs`)。シェルスクリプトを
`setsid` で起動しても SSH 切断で落ちたため、VM 内のプロセスにするのが確実。
VM が落ちればサンプラーも止まるが、それは観測したい事象そのものであり、
それまでのログは `/data` に残る。`smaps` はこの機体には重すぎるので
`/proc/<pid>/status` だけを読む。

### `/data` を作り直したらベンダーカメラの `prepare` が必要

MicroSD を再書き込みするとデータ領域が初期化され、ベンダー設定の私有コピーが
消える。この状態では自動起動が `{:command_failed, 2}` で失敗する
(`precheck` が「私有設定が未準備」の gate で止まるため)。

`atomcam2-vendor-camera prepare` を一度実行すれば解決する。

### MicroSD の構造破損と、その切り分け方

19:29 に実機が停止した。**ping には応答するが SSH ポートが閉じ、モバイル
アプリの配信だけは正常**という状態で、カメラはこのサブネットから消えていた。

SD カードを PC で調べたところ、**パーティションテーブルが消失し、カード全体が
ext2 `ATOMCAM2_DATA` として検出される**状態だった(`Structure needs cleaning`、
`A block group is missing an inode table`)。ブートに必要な FAT
パーティションが失われていたため SD から起動できず、内蔵フラッシュの純正
ファームで立ち上がっていた。モバイルアプリだけ動いていたのはこのためである。

#### 我々のコードによる全体フォーマットではない

`ATOMCAM2_DATA` は [atomcam2-pre-run](../../rootfs_overlay/usr/bin/atomcam2-pre-run)
の `mkfs.ext2 -L ATOMCAM2_DATA` だけが付けるラベルのため一度は自作コードを
疑ったが、`dumpe2fs` が示したブロック数は 7,438,080 × 4096 = **28.37 GiB** で、
**旧パーティション 4 と同一サイズ**だった。カード全体(29.13 GiB)を
フォーマットしたのなら容量いっぱいになるはずで、これはパーティション 4 として
正しく作られたファイルシステムである。コード上もフォーマット対象は常に
`${root_disk}p4` で、ディスク全体を指す経路はない。

#### 再書き込みで正常に復旧した

`fwup -t complete` で書き直したところ、パーティション 4 個が復元され、
**書き込んだ内容が SHA 一致で読み返せた**(制御カーネル `b50658ea…`、
ブートマネージャー `74e776d9…`)。したがって「カードが恒久的に故障している」
という当初の見立ては誤りで、少なくとも現時点では正常に読み書きできる。

#### fwup が消さない領域があることに注意

再書き込み後も、デバイス先頭に ext2 署名(パーティション 4 と同一 UUID)が
残っていた。**fwup はセクタ 0 と 2048 以降を書くが、その間のセクタ 1〜2031 は
消去しない**ため、そこにある古い署名は残り続ける。また
**データ領域(パーティション 4)もフォーマットしない**ので、壊れた
ファイルシステムがそのまま残る。

同様の破損から復旧するときは、再書き込み後に次を実行しておくとクリーンな
状態から始められる。

```sh
sudo wipefs -a /dev/sdX4                                   # 壊れた /data を除去
sudo dd if=/dev/zero of=/dev/sdX bs=512 seek=1 count=2031 conv=fsync  # 残留署名を除去
```

後者は MBR(セクタ 0)、ブートメタデータ(セクタ 2032〜2047)、各
パーティションには触れない。

#### 電源断は原因ではない

Nerves は読み取り専用 squashfs と A/B スロットで電源断に耐える設計であり、
書き込み可能なのは `/data` の ext2 だけで、起動時に `e2fsck` で自動修復する。
電源断で `/data` が汚れることはあっても、パーティションテーブルが消えるのは
ファイルシステム層の事象ではない。**電源断を避けるという対策は Nerves の
採用理由に反するため取らない。**

原因は未特定のまま。再発した場合はカード個体の問題を疑う。

## 5. 未解決・保留

- **USB Ethernet アダプタの接続が不安定。** ケーブル交換で一度は正常認識
  (`0bda:8152`、`error -88` が解消)したが、その後の起動で再発した。
  カーネルログの `device descriptor read/64, error -88` は USB の信号品質の
  問題を示すため、ケーブルまたは給電側の課題と考えている。現在アダプタは
  取り外している
- **音声は未対応。** 本カーネルは OSS のみで ALSA が無効。有効化には
  カーネル変更(= SHA ピン更新)を伴うため、RTSP 配信のフェーズ 3 として分離
- **1080p 以外の同時配信は不可。** 仮想デバイスは配信するチャンネルの分だけ
  作成すること。3 系統作るとメモリが枯渇する
- **19:29 の停止は MicroSD の構造破損が主因と考えられる。** その後のメモリ監視で
  リークは否定されたため、当初疑っていたメモリ枯渇ではない。ただし破損に至った
  経緯そのものは特定できていない
- **RTSP 配信中の `MemFree` は 1.5〜2MB と小さい。** ただし `Cached` が 24MB 前後
  あり、数時間の監視では枯渇の兆候はなかった。それでも余裕は乏しいので、
  仮想デバイスを増やすなどの追加負荷はかけないこと
- **チャンネル競合の機構は未特定。** コールバックの再登録なのかチャンネルの
  再設定なのかは外部からは判別できない。特定するにはフックに計測(書き込み
  回数、`write()` のエラー、登録回数)を仕込む必要がある
