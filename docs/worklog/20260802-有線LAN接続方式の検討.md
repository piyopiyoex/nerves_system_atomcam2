## 文書情報

- 日付: 2026-08-02
- 種別: 設計検討
- 状態: 検討完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

Atom Cam 2 を USB-Ethernet アダプタ経由で有線 LAN に接続するための調査結果と
実装提案。[mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools) の
実装分析に基づく。

## 背景と目的

Atom Cam 2 には Ethernet ポートがなく、標準では 2.4GHz Wi-Fi のみ。
Wi-Fi の電波状況に依存しない安定した接続(録画の NAS 転送、リモート更新)の
ため、有線 LAN 接続を実現したい。

## 調査結果

### 1. ハードウェアの前提

- Atom Cam 2 の microUSB ポートは給電用だが、SoC(Ingenic T31)の USB OTG が
  配線されており、**USB ホストとして USB-Ethernet アダプタを接続できる**
  (honeylab 氏が 2021 年に実証済み)
- ただし付属の電源ケーブルは電源線のみ結線のため、**データ線を含む OTG
  ケーブル + 給電の分岐**が必要。屋外設置では防水も課題
- 実績のあるアダプタチップ:
  - **ASIX AX88772**: honeylab 氏の実証で使用。stock カーネルにもドライバが
    組み込まれており最も実績がある
  - **Realtek RTL8152**: 小型で加工しやすい Amazon ベーシックアダプタ等。
    pirosap 氏の PoE 運用例あり
- **純正品の選択肢**: Soracom「ATOM Cam 2 専用 LANアダプター(AC2LAN)」
  (2,530 円、10/100BASE-TX、分岐ケーブルで給電、PoE 非サポート)。
  ケーブル加工と防水の問題を回避できる。搭載チップは非公表のため
  **実機で `lsusb` による確認が必要**(stock ファーム対応品なので
  AX88772 系の可能性が高い)

### 2. atomcam_tools(mnakada 版)の実装分析

有線 LAN 対応の核心は 2 か所:

**カーネル設定**(`configs/kernel.config`)— 同じ Ingenic 3.10.14 カーネルで
USB NIC ドライバをモジュールとして有効化している:

```text
CONFIG_USB_RTL8152=m
CONFIG_USB_USBNET=m
CONFIG_USB_NET_AX8817X=m        # AX88772 系
CONFIG_USB_NET_AX88179_178A=m
CONFIG_USB_NET_CDCETHER=m
CONFIG_USB_NET_RNDIS_HOST=m
```

**起動スクリプト**(`overlay_rootfs/scripts/network_init.sh`)— 起動時に:

1. `devmem` で T31 の GPIO レジスタを 3 か所設定(USB ホスト用の
   ピン初期化と推定):
   ```sh
   devmem 0x10011110 32 0x6e094800
   devmem 0x10011138 32 0x300
   devmem 0x10011134 32 0x300
   ```
2. `lsusb` で USB デバイスを検出したら `r8152 → asix → ax88179_178a →
   cdc_ether` の順に modprobe し、`eth0` が現れたら `udhcpc` で IP 取得
3. **有線で IP が取れたら Wi-Fi を起動せず終了**(有線優先)。取れなければ
   モジュールを外して次のドライバへ、全滅なら Wi-Fi にフォールバック

### 3. 本リポジトリ側の現状(適合性)

好条件が揃っている:

| 項目 | 現状 |
| --- | --- |
| 制御カーネル | Wyze Cam v3 GPL カーネル 3.10.14 を**自前ビルド**([nerves_defconfig:36-44](../../nerves_defconfig#L36-L44))。atomcam_tools と同系統のソースなので同じ変更を適用可能 |
| USB ホスト | **既に有効**: `CONFIG_USB=y`, `CONFIG_USB_JZ_DWC2=y`, `CONFIG_USB_DWC2_HOST_ONLY=y` |
| モジュール機構 | `CONFIG_MODULES=y`, `CONFIG_MII=y` 有効 |
| USB NIC ドライバ | **全て無効**(`CONFIG_USB_USBNET` ほか)← 追加が必要 |
| ネットワーク管理 | VintageNet。`vintage_net_ethernet` を追加すれば有線対応。VintageNet は有線を Wi-Fi より優先ルーティングするため、フォールバック処理を自作する必要がない |
| 制約 | カーネル変更で `uImage.lzma` の SHA-256 が変わるため [scripts/post-image.sh](../../scripts/post-image.sh) のピン更新と、`ATOMCAM2_SYSTEM_SOURCE=local` での system フルビルド(Buildroot)が必要 |

## 実装方式の提案

### 方式比較

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A(推奨)** | defconfig に USB NIC ドライバを `=m` で追加し、system に組み込む | atomcam_tools と同構成で実績あり。必要時のみロード。リポジトリで再現可能 | カーネル SHA 更新と system フルビルドが必要 |
| B | ドライバを `=y`(ビルトイン)で追加 | モジュール配布・ロード処理が不要 | カーネルサイズ増(U-Boot のロード上限の検証が必要)。柔軟性がない |
| C | system は変更せず、モジュールだけ別ビルドしてアプリの rootfs_overlay で配布 | カーネル SHA 据え置き。system リリース不要 | vermagic 一致の管理が手作業になり再現性・保守性が低い |

**案 A を推奨。** 理由: atomcam_tools が同一カーネル系統で長期運用している
構成であり、この system の「検証済みカーネルを SHA でピン留めする」方針とも
両立する(新しい SHA を検証してピンを更新すればよい)。

### 実装タスク(案 A)

1. **カーネル** — [linux-3.10.14.defconfig](../../linux-3.10.14.defconfig) に追加:

   ```text
   CONFIG_USB_USBNET=m
   CONFIG_USB_NET_AX8817X=m
   CONFIG_USB_NET_AX88179_178A=m
   CONFIG_USB_RTL8152=m
   CONFIG_USB_NET_CDCETHER=m
   ```

2. **system** — [scripts/post-image.sh](../../scripts/post-image.sh) の
   `expected_kernel_sha256` を新カーネルの値へ更新。`VERSION` を bump

3. **ドライバロードスクリプト** — `rootfs_overlay/usr/bin/atomcam2-eth-driver`
   を新規作成(既存の
   [atomcam2-wifi-driver](../../rootfs_overlay/usr/bin/atomcam2-wifi-driver)
   と同じ作法で FAT へ `atomcam2-eth-driver.env` を報告):
   - devmem による GPIO 初期化(atomcam_tools と同値。実機検証で要否確認)
   - USB デバイス検出 → `usbnet` + 各ドライバを順に insmod → `eth0` 出現確認
   - [atomcam2-pre-run](../../rootfs_overlay/usr/bin/atomcam2-pre-run) から
     wifi-driver と同様に呼び出し(`ATOMCAM2_PRE_RUN_ETH_DRIVER` で無効化可)

4. **アプリ** — `examples/atomcam2_nerves_app`:
   - `mix.exs` に `{:vintage_net_ethernet, "~> 0.11", targets: @all_targets}`
   - `config/runtime.exs` で `"eth0"` を DHCP 設定に追加
     (VintageNet が有線を自動優先。Wi-Fi 設定はそのまま残しフォールバックに)
   - 任意: `nerves-provisioning.conf` に `NERVES_WIRED_ONLY=true` を追加し、
     有線専用運用(Wi-Fi 無効)を選べるようにする

5. **ビルドと検証**:

   ```sh
   cd examples/atomcam2_nerves_app
   export MIX_TARGET=atomcam2 MIX_ENV=prod
   export ATOMCAM2_SYSTEM_SOURCE=local        # system をソースからビルド
   mise exec -- mix deps.get
   mise exec -- mix firmware
   ```

## 段階的な進め方

### フェーズ 1: PoC(ハード検証)— 推奨最初の一歩

現行ファームのまま、ターゲットの IEx から USB ホストとアダプタの認識だけを
先に確認する(カーネル変更前にハードの成立性を切り分ける):

```elixir
cmd("devmem 0x10011110 32 0x6e094800")
cmd("devmem 0x10011138 32 0x300")
cmd("devmem 0x10011134 32 0x300")
cmd("ls /sys/bus/usb/devices/")     # アダプタが見えるか
cmd("cat /sys/kernel/debug/usb/devices 2>/dev/null || lsusb")
```

デバイスが列挙されれば USB ホストは生きており、残りはドライバの問題だけに
なる。ここで Soracom アダプタのチップ(VID/PID)も確定できる。

### フェーズ 2: 本実装

上記タスク 1〜5 を実施し、有線での起動 → DHCP → SSH → `mix upload` までを
確認。Wi-Fi との優先順位(ケーブル抜去時のフォールバック)も検証する。

## リスクと検証項目

| リスク | 内容 | 対応 |
| --- | --- | --- |
| devmem 初期化の要否 | atomcam_tools の 3 レジスタ設定の意味が未解明(ピンムクス/ドライブ設定と推定) | フェーズ 1 で有無両方を試す |
| カーネルサイズ増 | 現在の `uImage.lzma` は約 1.93MB。`=m` なら本体はほぼ増えない | モジュールは rootfs 側に入るため影響小 |
| 給電 | ホスト動作時も microUSB から給電が必要(分岐ケーブル/OTG Y 字) | Soracom 純正なら同梱分岐ケーブルで解決 |
| アダプタ相性 | Soracom AC2LAN のチップ非公表 | フェーズ 1 の `lsusb` で確定。AX88772/RTL8152 は実績あり |
| 防水 | 自作ケーブルの屋外運用 | 屋内運用から開始、屋外は純正アダプタ推奨 |
| フルビルド環境 | ローカル Buildroot ビルドが未実施 | 初回のみ時間がかかる(数十分〜)。`scripts/check-prereqs.sh` で事前確認 |

## 実施結果(2026-08-02 追記)

同日中に案 A を実装し、実機で有線 LAN 接続を確認した。

### 検証結果

- アダプタ: Realtek RTL8152(VID `0bda` / PID `8152`)
- `r8152.ko` がバインドし、`eth0` が DHCP で IP を取得(192.168.222.65)
- デフォルトルートは有線優先(eth0 metric 10、wlan0 metric 20)、
  有線 IP への SSH 接続も成功
- 更新ファームはヘルスチェックに合格しスロット確定(ロールバックなし)

### 提案時の想定との差分

| 想定 | 実際 |
| --- | --- |
| devmem による GPIO 初期化が必要な可能性 | **不要**。該当レジスタは Wi-Fi 用 SDIO ピン初期化と同一で、USB ホストは無初期化で動作(フェーズ 1 で確認) |
| r8152 は 3.10 へのバックポートが必要な可能性 | **不要**。Wyze/Ingenic ツリーに r8152 が含まれていた(atomcam_tools も無パッチ) |
| カーネル差し替えのため SD 再書き込みが必要 | **不要**。モジュールの vermagic が既存制御カーネルと一致し、`mix upload` のみで有効化できた |
| CDC ECM(cdc_ether)でバインドする想定 | 実機では **r8152 がバインド**(性能面ではむしろ好ましい) |

### 反映済みの変更

- `linux-3.10.14.defconfig`: USB NIC ドライバ 6 種を `=m` で追加
- `rootfs_overlay/usr/bin/atomcam2-eth-driver`: 新規(pre-run から Wi-Fi より
  先に実行、FAT へ `atomcam2-eth-driver.env` を報告、
  `ATOMCAM2_PRE_RUN_ETH_DRIVER=0` で無効化可)
- `scripts/post-image.sh`: 変更なし。制御カーネルは検証済みバイナリのまま
  (下記の注意を参照)
- アプリ: `vintage_net_ethernet` 追加、`eth0` を常時 DHCP 構成
- 文書: README、構成.md、サンプルアプリ README、CHANGELOG(Unreleased)

### 注意: 制御カーネルは差し替えてはいけない

作業中に一度、Buildroot がビルドしたカーネルを制御カーネルとして採用し、
`scripts/post-image.sh` の `expected_kernel_sha256` を更新して SD へ書き込んだ
ところ、**カメラが Nerves を起動しなくなった**(U-Boot が SD から起動できず、
内蔵フラッシュの純正ファームで起動した)。SD には Nerves の起動痕跡が
まったく残らず、代わりに純正アプリの `log/` や `time.ini` が生成される。

U-Boot が読み込める `factory_t31_ZMC6tiIDQN` は検証済みの純正互換バイナリだけ
である。post-image.sh は Buildroot 版カーネルをこの検証済みバイナリで
上書きしており、SHA ピンはまさにこの差し替えを防ぐガードだった。

Buildroot のカーネルビルドは、**制御カーネルと vermagic が一致するモジュールを
得るため**に存在する。したがって USB NIC ドライバのようなモジュール追加では、
カーネルイメージも SHA ピンも変更してはならない。復旧に必要な検証済みカーネルは
`~/.nerves/dl/nerves_system_atomcam2-portable-0.3.0-*.tar.gz` の
`images/uImage.lzma`(`sha256 b50658ea…`)から取り出せる。
