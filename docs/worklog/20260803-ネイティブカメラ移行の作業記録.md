## 1. RTSP 実装方針の決定

RTSP 配信に 3 方式が並存する状態になったため、期待値
(成功確率 × 価値 ÷ 工数)で評価し、方針を決めた。

| 方式 | 内容 | 位置づけ |
| --- | --- | --- |
| A | ベンダーアプリの出力を LD_PRELOAD で横取り(現行) | 製品路線 |
| C | 方式 A のまま監視層を強化 | **最優先開発** |
| B | libimp を直接叩く自前実装 | 研究テーマ |

**方式 A+C を「暫定版」ではなく完成形とみなす。** 無人運用の IP カメラで
重要なのは「リブートが起きないこと」ではなく「人手なしで復帰できること」。
市販の NAS・ルーター・監視カメラも「内部異常 → 自動再起動」で復帰する設計は
一般的で、ウォッチドッグ復帰の方がむしろ信頼性が高い。

方式 B は成功すれば価値が大きい(ブラックボックス排除、`iCamera_app` の
RSS 18MB 削減、解像度・fps の自由)が、停止箇所が `IMP_System_Init`
(カーネル/ISP 境界)で成否・工数が読めず、期待値が低い。

## 2. フレーム心拍による停止の可視化(方式 C 第一段階)

### 動機

[長時間動作 記録](20260802-長時間動作の検証.md)のインシデント B で判明した
「プロセスは running のままフレームだけが枯れる」停止を、監視層が検知できる
ようにする。ループバックにフレームカウンタが無く、ベンダーが running と
偽るこの環境では、フレーム供給の健全性を測る独自の手段が要る。

### 実装

- **video-hook**: 転送フレームごとに心拍ファイル
  (chroot 内 `/tmp/atomcam2-video-hook.beat`)を更新。供給が止まれば
  mtime が凍る
- **RtspServer**: 稼働中に心拍の mtime を監視し、停止が続けば `status` と
  警告ログで可視化(既定で約 1 分後)。テスト 3 件追加(全 52 件通過)

### 重要な設計判断: 素朴な 3 段階復旧は誤り

実装中に、想定していた「RTSP 再起動 → ベンダー再起動 → reboot」が
このシステムでは正しくないと判明した。

- **RTSP 再起動は無効**。停止原因はフレーム供給元(ベンダーのエンコーダ)の
  上流にあり、v4l2rtspserver を再起動してもフレームの来ないループバックに
  繋ぎ直すだけ
- **ベンダー再起動も無効**。ベンダーランタイムは停止後の再開にリブートが
  必要という制約を持つ
- したがって供給停止への実効的な復旧は **reboot のみ**

さらに **reboot はモバイルアプリの正当な HD 視聴と衝突する**。HD ライブ視聴中は
ch0 のフレームが RTSP 側に来なくなる(競合)が、これは異常ではなく、アプリを
閉じれば復旧する。フレーム不在だけを見て reboot すると、視聴中のユーザーを
巻き込む。「回復不能な停止」と「正当な HD 視聴」を安全に区別するには
loadavg など二次シグナルが要る。実機検証を経てから入れるべきなので、
**自動 reboot は後工程に分離**し、まず可視化までを入れた。

### 実機検証で見つけた 2 つのバグ(ユニットテストでは出ない)

心拍はユニットテストでは `frame_health` をモックするため通るが、実機では
心拍ファイルが生成されなかった。「フレームは流れているのに心拍が無い」
(VLC で 739KB 受信・ループバックのフォーマット設定済み・`PollingStream`
失敗ゼロ)という観測から、次の 2 点を特定・修正した。

1. **MIPS の `open()` フラグ値が汎用と違う**。`O_CREAT` を汎用値 `0100`
   (0x40)で定義していたが、**MIPS は `O_CREAT = 0x100`**。誤った値では
   新規作成にならず `ENOENT` で失敗していた
2. **chroot のパス不一致**。フックはベンダー chroot 内で動くため、その `/tmp` は
   Nerves から見て `/atom/tmp`。RtspServer の読み取りパスをそちらに合わせた

修正後、実機で心拍の mtime が前進すること(`…855 → …862`)、RtspServer が
`stall_strikes: 0` で認識することを確認した。

## 3. ネイティブ実装(方式 B)の調査

### 到達点

Ingenic 公式サンプル `sample-Encoder-h264` をクロスビルドして実機で動かした。

- **float ABI 不一致を解消**。本システムの musl は soft-float、libimp は
  hard-float。同一プロセスに同居できず `Bus error` になっていた。Bootlin の
  hard-float glibc ツールチェーンでビルドし直して解消
- ただし **`IMP_System_Init` 付近で初期化が進まず停止**する
  (RSS 420KB・単一スレッド・CPU 100%)

### 判明した最有力原因

質問書作成中に、**リンクしたライブラリと実機のライブラリでビルド系統が
異なる**ことに気づいた。

| 対象 | libc | コンパイラ |
| --- | --- | --- |
| 実機の `libimp.so` | uClibc 0.9.33.2 | GCC 4.7.2 |
| 試したもの | glibc | GCC 5.4.0 |

Ingenic 系 SDK は OEM ごとに libimp・tx-isp・センサドライバが改変されており、
SDK 番号(1.1.1)が同じでも互換とは限らない。セカンドオピニオンの助言も
「実機の libimp.so をそのまま使え」で一致。実機の uClibc ランタイムは
`/atom/lib/` に一式存在することを確認済み。

### 副次的な発見

- 実機にセンサー `sensor_gc2053_t31`、ISP `tx_isp_t31`、エンコーダ `avpu`、
  libimp 3 点セット、ISP チューニング `gc2053-t31*.bin` がすべて存在。
  スクラッチ実装の部品は揃っている
- ベンダーに live555 ベースの RTSP サーバー `/atom/system/bin/rtsp`(51KB)が
  同梱されているが、libimp を直接使わず `iCamera_app` からフレームを受ける
  構成のため、ベンダー依存は消えず今回の目的には使えない
- GC2053 の I2C アドレスは `0x37`(Wyze v3 / thingino / OpenIPC と一致)

### 位置づけ

方針決定に従い研究テーマとして保留。実機の libimp.so を使う uclibc ビルドが
次の一手だが、方式決定を優先してツールチェーン取得は保留した。

## 5. 得られた知見(再発防止)

- **MIPS の `open()` フラグは汎用値と違う**。freestanding コードで
  `O_CREAT`/`O_TRUNC` 等を自前定義するときは MIPS 値(`O_CREAT=0x100`、
  `O_TRUNC=0x200`)を使う
- **chroot 内で動くフックのファイル出力は、Nerves 側からは `/atom/` 配下に
  見える**。フックとアプリでパスの視点が違う
- **ユニットテストが緑でも実機で動くとは限らない**。心拍は 52 件のテストが
  通っていたが、モックが実機の 2 バグを隠していた。フレーム経路のような
  外部依存は実機検証が要る
- **Ingenic SDK は SDK 番号が同じでも OEM 改変で別物**。libimp の差し替えは
  バージョン文字列だけで判断しない
- **素朴な段階的復旧が常に正しいとは限らない**。復旧手段が実効性を持つか
  (再起動で本当に直るか)を、失敗モードの構造から検証する

## 6.5 有線のみ構成でベンダーカメラが起動しない問題(追記)

最新ファームを新品 SD に書き込んで有線 LAN(192.168.1.77)で起動したところ、
RTSP が自動起動しなかった。原因は **ベンダーカメラ連携が wlan0 前提のまま**
だったこと。有線 LAN 対応を追加した際の取りこぼし。

3 箇所が wlan0 に固定されていた。

1. `VendorCamera` の readiness が `["interface", "wlan0", "connection"]` を見て
   いた → wlan0 が `:disconnected` だと永久に `internet_connection` 待ち
2. `atomcam2-vendor-camera` の起動処理が wlan0 の IPv4 アドレスを必須にして
   いた(ベンダーの network-status 報告用にファイルへ書く)→ 有線のみだと
   `wlan0 has no usable IPv4 address` で失敗
3. `TimeSync` も同じ wlan0 依存で、有線のみだと時刻同期が走らない

### 恒久対策

- readiness と TimeSync の接続プロパティを `["connection"]`(全インターフェース
  横断の総合接続状態)に変更。VintageNet はこれを公開しており、実機で
  `:internet` を返すことを確認済み
- `atomcam2-vendor-camera` の IPv4 取得を wlan0 → eth0 のフォールバックに
- precheck のインターフェース健全性チェックを eth0(operstate=up)でも通るように

### 実機検証

恒久対策を入れたファーム(`era-fossil`)を配信し、有線のみのカメラ
(192.168.1.77、wlan0 は `:disconnected`)を再起動したところ、
**ダミー IP 無しでベンダーカメラと RTSP が自動起動**した。
`wlan0` の IPv4 アドレスは 0 件のまま `result=running`、RTSP は
H.264 1080p を配信(VLC で受信確認)、再起動ループもなし(uptime 継続増加)。

### 暫定回避策(恒久対策の投入まで使ったもの)

(旧回避策は恒久対策の投入により不要になった。以下は記録)
リンクの無い wlan0 にダミー IP(`ip addr add`)を割り当てると起動の
wlan0 IPv4 チェックを通せる。wlan0 は未接続なので実通信に影響しない。
ただし再起動で消え、readiness の wlan0 依存は解消しないため手動起動が必要。
恒久対策の投入で不要になる。

## 6.6 複数拠点の Wi-Fi 対応(追記)

単一 SSID を焼き込む作りだったため、カメラを別拠点へ移すと wlan0 が
`:disconnected` になっていた(6.5 の遠因でもある)。**VintageNet は
`networks:` リストで複数ネットワークを持て、電波が届く AP に自動接続する**ため、
provisioning ファイルから複数 SSID を読めるようにするだけで対応できる。

### 実装

- `nerves-provisioning.conf` の形式を後方互換で拡張。番号なしの組が拠点 1、
  `_2`、`_3` … を足して拠点を増やす:

  ```text
  NERVES_WIFI_SSID=home
  NERVES_WIFI_PASSPHRASE=home-secret
  NERVES_WIFI_SSID_2=office
  NERVES_WIFI_PASSPHRASE_2=office-secret
  ```

- 解析は純関数 `Atomcam2NervesApp.WifiProvisioning.networks/1` に切り出し、
  ユニットテスト 7 件(後方互換・オープンネットワーク・番号飛び・順序・
  空白除去)を追加。`runtime.exs` は `MOTDLogo` と同じ流儀でこれを呼ぶ
- **再ビルド不要**。FAT の `nerves-provisioning.conf` を編集して拠点を追加する。
  パスフレーズを空にするとオープンネットワーク扱い

これは system ではなくアプリ(例アプリ)側の変更のため、フルビルドは不要で
`mix upload` だけで配れる。

### 実機検証

2 拠点の設定を投入して再起動したところ、VintageNet の wlan0 設定に
2 ネットワーク(`["<自宅SSID>", "<会社SSID>"]`)が反映されることを
確認した(パスフレーズ未所持のため 2 つ目への実接続は未検証だが、
provisioning → runtime.exs → WifiProvisioning → VintageNet の経路が
複数ネットワークを正しく構成することは実機で確認できた)。

## 9. 方式B スパイク: Stage 2/3 を実機で GO

[方式B推進判断](20260803-ネイティブ方式採用の判断.md) の Stage 1(`IMP_System_Init`
単体 GO)に続き、実機 192.168.1.77 で ISP〜H.264 エンコードまでを実証した。

### Stage 2(ISP + センサ登録)= GO
`IMP_ISP_Open → AddSensor → EnableSensor → System_Init → EnableTuning` が
全て戻り値 0。GC2053 センサが通電し `FPGA board is ready / Board UID 30AB6E51`
を出力。スタンドアロンプロセスでセンサ登録が通ることを確認。

### Stage 3(FrameSource → H.264 エンコード)= GO
FrameSource(1920x1080 NV12)→ H.264 エンコーダを結線し、**60/60 フレーム・
441,956 バイト**を取得。先頭が **SPS(NAL7)→ PPS(NAL8)→ IDR(NAL5)** の
正しい H.264 GOP であることを手元で検証。**iCamera_app 非依存で映像が撮れる**
ことを端から端まで実証した。

### Stage 4(v4l2loopback → RTSP 配信)= GO
エンコード出力を `/dev/video0`(v4l2loopback)へ、フック(video-hook.c)と同じ
作法(`VIDIOC_S_FMT` で H264/1080p/sizeimage → `VIDIOC_STREAMON` → フレーム毎
`write`)で書き出し、既存の `v4l2rtspserver` で配信した。手元から RTSP DESCRIBE
すると `200 OK` + `m=video H264/90000` + **native エンコーダが生成した実際の
`sprop-parameter-sets`(SPS/PPS、Main profile L5.1)** が返り、**iCamera_app 非依存
のフル RTSP パイプライン(センサ→ISP→FrameSource→H.264→loopback→RTSP)が
端から端まで成立**した。
- ハマり: vendor カメラ停止後も**旧 `v4l2rtspserver` が 8554 を掴んだまま**で、
  新サーバがバインドできず `log level:500` だけ出して即終了する。既存の
  rtspserver を先に kill し、writer が S_FMT した後に rtspserver を起動する順序を
  守ると配信できた。

### 途中で解決した最大の難所: エンコーダ API の ABI 不一致
- デバイスの libimp は **T31 1.1.1 の新エンコーダ API**。atomcam_tools の
  サンプルヘッダは旧 API(`encAttr`/`rcAttr` 直接指定)で、構造体レイアウトが
  違い `invalid resolution(0x0)` になった。ISP/センサ/FrameSource 系の
  ヘッダは新旧互換だったため Stage 2 は通り、**エンコーダだけ非互換**だった。
- 正しいヘッダを GitHub `cgrrty/Ingenic-SDK-T31-1.1.1-20200508` の
  `include/imp/` から取得し、`IMP_Encoder_SetDefaultParam(...)` +
  `IMP_Encoder_CreateChn` 方式に修正。ストリーム取得は `IMPEncoderPack` が
  絶対アドレスでなく **`offset`** を持つため、`stream.virAddr + pack.offset`
  で読み、リング折り返し(`offset+length > streamSize`)を処理して解決。
- `IMP_ISP_Tuning_SetWDRAttr` はデバイス libimp に存在せず(リンク不可)、
  呼び出しを外した。

### 実機運用で判明した制約
- **`/tmp` は noexec** → バイナリは `/data` から実行。
- 依存 lib は **`/atom/system/lib`**(libimp/libalog/libsysutils)。
  interpreter は `/atom/lib/ld-uClibc.so.0`。
- **`iCamera_app` は stop すると reboot なしに再起動できない**
  (`stopped_reboot_required`)。ISP が空くのは iCamera_app 停止中だけなので、
  停止した窓でスパイクを回し、終了後に `Nerves.Runtime.reboot()` で復旧。
  reboot 後は自動でベンダーカメラ + RTSP が復帰(~100 秒)。各スパイク後に
  実機で VLC 再生の復帰を確認済み。

## 10. メモリ消費の改善状況

方式B の狙いの一つは、ブラックボックスの `iCamera_app` を軽量なネイティブ
プロセスへ置き換えて平常時メモリを削ることにある。今回の実測と見積もりは
[iCamera 非依存 RTSP 配信 提案書](20260803-iCamera非依存RTSP配信の検討.md)
の「構築内容とメモリ所要量の見積もり」を参照。

### 今回(2026-08-03)実測したベンダーモードの RSS(87MB 側)
`atomcam2-vendor-camera status` と `ps` で確認:

| プロセス | RSS |
| --- | --- |
| `iCamera_app` | 起動直後 17.4MB → 定常 約 22MB |
| `hl_client` | 0.6–1.0MB |
| `assis` | 1.8–2.1MB |
| ベンダー三点計 | **約 25MB** |
| `v4l2rtspserver`(方式A の配信) | 約 13MB |

`memory_reclaimable_kb` は約 26.7MB。フレームバッファは rmem(36MB 予約)側で
プロセス RSS には出ない([[atomcam2-rtsp]] 参照)。

### ネイティブモードの実測(Stage 4 で確定)
方式B ではベンダー三点(約 25MB)を、ネイティブのエンコーダ常駐プロセスへ
置き換える。Stage 4 の常駐形態(1080p H.264 を loopback へ連続書き出し)で
`/proc/self/status` の VmRSS を実測した:

| プロセス | RSS(実測/実装) |
| --- | --- |
| native エンコーダ(`enc-loopback`) | **初期化直後 1.36MB → 定常 1.55MB** |
| 置換されるベンダー三点(iCamera_app/hl_client/assis) | 約 25MB |
| 再利用する `v4l2rtspserver` | 約 13MB(両モード共通) |

native 常駐は事前見積もり(3–6MB)を下回る **約 1.5MB** で収まった。配信後段は
両モード共通のため、**ベンダー三点(約 25MB)→ native(約 1.5MB)の置換により
平常時 RSS を約 23MB 削減**できる見込み(v4l2rtspserver は据え置き)。フレーム
バッファは引き続き rmem(36MB 予約)側でプロセス RSS には出ない。

これは [平常時メモリ削減 提案書](20260803-平常時メモリ削減の検討.md) の各施策
(OTP アプリ削減・RingLogger・ERTS アロケータ等、合計数 MB 規模)と比べても
桁違いに大きい単一施策であり、87MB ボードの平常時余裕を大きく改善する。

## 11. 起動アナウンス(スピーカー発声 + 青 LED 点滅)

スピーカーから「起動しました。」を発声し、青 LED(GPIO 39)を 3 回点滅させて
点灯のまま残す起動アナウンスを実装した。

### スピーカー再生の実証(libimp IMP_AO 直叩き)

- `aoplay.c`(方式B スパイクの一部)で `IMP_AO_SetPubAttr → Enable →
  EnableChn → SetVol → SendFrame` の直叩き再生が native モードで動作。
  フォーマットは atomcam_tools issue #23 と同じ **16bit/mono/PCM/8kHz**。
- **ハマり(ノイズしか聞こえない)**: `IMP_AO_SendFrame` はリングバッファ
  (frmNum 分)に積むだけで即返る。短い音声はキュー投入が一瞬で終わり、直後の
  `DisableChn`/アンプ OFF が**再生冒頭を切断**して破裂音だけになる。送出後に
  **`IMP_AO_FlushChnBuf`(排出完了待ち)+ 300ms** を入れてから teardown する。
  atomcam_tools の `PlayPCM` も同じ順序(QueryChnStat ポーリング + 500ms)。
- アンプは `/dev/speakerctl` の open で有効化、`ioctl(fd, MODE)`(0〜4)で
  ゲイン段設定。音割れ対策で **gain 1 / SetVol 60** を既定にした。

### 再生ウィンドウの制約と組み込み位置

- vendor モードでは `iCamera_app` が IMPAudio のロックを握るため、稼働中は
  他プロセスから再生できない(atomcam_tools issue #23 の mnakada 氏の分析
  どおり)。また `audio.ko`/`speaker_ctl.ko` は [permanent] のため rmmod
  不可で、事前ロードは vendor start の「module already loaded」検査を壊す。
- 当初は vendor start 内(モジュールロード後〜iCamera 起動前)にフックを
  置いたが、**方針決定「iCamera_app は使用しない(メモリ容量の問題で
  vendor は起動不可)」**を受けて native 前提に組み替えた:
  - `atomcam2-boot-announce` が `audio.ko`(spk_gpio=-1)と
    `speaker_ctl.ko` を未ロードなら自分で insmod する(native では音声
    デバイスが常時空いているため、いつ呼んでも安全)
  - 呼び出し元は Elixir の `Atomcam2NervesApp.BootAnnounce`(Task、
    supervision tree の先頭)。アプリ起動時に一度だけ実行し、失敗しても
    ログのみで他へ影響しない
  - vendor-camera スクリプトのフックは削除。vendor 運用に戻す場合は
    モジュール事前ロードと start_prerequisites が衝突する点に注意

### 追加ファイル

| ファイル | 内容 |
| --- | --- |
| `rootfs_overlay/usr/bin/atomcam2-boot-announce` | 発声 + 青 LED 点滅(env で無効化・差し替え可) |
| `package/atomcam2-boot-announce/` | Buildroot パッケージ: `atomcam2-aoplay`(uClibc ビルド済みバイナリ + aoplay.c ソース)と `boot-announce.raw`(「起動しました。」8kHz/16bit/mono raw PCM)を `/usr/bin` と `/usr/share/atomcam2` に配置 |

### ビルドの注意(v0.4.0 タグ未発行)

`VERSION` は 0.4.0 だが **v0.4.0 の git タグと GitHub リリースは未発行**。
ローカルビルドではツールチェーンのアーティファクト解決が
`nerves_toolchain_atomcam2 …-0.4.0` を要求して失敗する。ツールチェーンの
チェックサム(977999C)は v0.1.0〜v0.3.0 で不変(内容が同一)のため、
`~/.nerves/artifacts/nerves_toolchain_atomcam2-linux_x86_64-0.3.0` を
`…-0.4.0` に複製して解決した。システム側は `…-portable-0.4.0` の新規
ビルドツリーでフル Buildroot ビルドになる。

## 12. native カメラの自動起動(Stage 5 の第一片)

「iCamera_app は使用しない」方針を受け、native スタック(camd +
v4l2rtspserver)を起動時に自動で立ち上げる `CameraNative` GenServer を
実装し、実機で OTA → 再起動 → 起動 51 秒で配信開始を確認した。

- **モジュールロードから面倒を見る**: vendor 無効化により誰もカメラ系
  モジュールをロードしなくなったため、`CameraNative` が
  `tx_isp_t31(isp_clk=100000000)` → `sensor_gc2053_t31(data_interface=1)`
  → `avpu` → `sinfo` を未ロードなら insmod する
- **camd のフレーム数上限**: camd は第 1 引数がフレーム数上限(既定
  100000 ≈ 83 分で終了)。自動起動では 2000000000 を渡し、終了時は
  MuonTrap のリンク + trap_exit で検知して再起動する
- **起動順序**: camd が S_FMT でフォーマットを確定してから
  v4l2rtspserver を起動する必要があるため、camd 起動の 8 秒後に RTSP を
  起動する
- **配信 URL は `rtsp://<ip>:8554/video0_unicast`**(v4l2rtspserver は
  デバイス名 + `_unicast` でストリームを命名する。`/unicast` ではない)
- camd バイナリは未パッケージで `/data/camd` のまま(Stage 5 残件)。
  `CameraNative` はバイナリと `/dev/video0` と libimp が揃うまで 5 秒毎に
  ポーリングして待つ
- 設定: `/data/atomcam2-native-camera/auto-start.conf`。**ファイル無し =
  有効**(native が唯一のカメラモードのため)、`enabled=false` で無効化

起動チェーン全体(実機確認済み):
電源 ON → pre-run(/atom マウント・loopback 作成)→ BEAM 起動 →
`BootAnnounce`(「起動しました。」+ 青 LED 点滅)→ `CameraNative`
(モジュールロード → camd → v4l2rtspserver)→ RTSP 配信(VLC 再生確認)

## 13. ステータス LED パターンと起動時ロゴ非表示

LED の状態表示仕様を実装した(`StatusLed` GenServer)。busybox の sleep は
整数秒のみで ms 精度の点滅ができないため、点滅タイミングは Elixir 側
(`Process.send_after`)で刻む。

| 状態 | LED | パターン(繰り返し) |
| --- | --- | --- |
| 起動中(RTSP 未配信) | 黄(GPIO 38) | 点灯 100ms → 消灯 200ms → 点灯 100ms → 消灯 600ms(1 秒周期) |
| 起動中(RTSP 未配信) | 青 | 消灯 |
| RTSP 配信中 | 黄 | 消灯 |
| RTSP 配信中 | 青(GPIO 39) | **ほぼ点灯**: 消灯 100ms → 点灯 200ms → 消灯 100ms → 点灯 4600ms(5 秒周期のダブルディップ) |

- 配信中かどうかは `CameraNative.status/0` の `phase == :running` を
  サイクル境界ごとに確認。配信が止まれば起動中パターンに戻る
- これに伴い `atomcam2-boot-announce` から LED 処理を撤去(音声のみに)
- **起動時ロゴ非表示**: camd は OSD ロゴを既定で表示する(`show=1`)ため、
  `CameraNative` が camd 起動のたびに `/data/camd.ctl` へ `logo off` を
  書き込む(camd はファイル内容を 1 コマンドとして処理しトランケート)。
  時計オーバーレイは表示のまま
- 実機確認: 配信中に GPIO 値を 100ms 間隔でサンプリングし、
  黄=常時 0、青=`…100100…`(ダブル点滅)を確認。`camd: ctl 'logo off'`
  の処理ログも確認
- **LED は黄(GPIO 38)・青(GPIO 39)とも active-low 配線**(実機確認、
  物理 Low で点灯)。当初 active-high を仮定して 0 を書いた結果、黄が
  点灯したまま・青は「ほぼ点灯で一瞬消える」逆パターンになっていた。
  両方 sysfs `active_low=1` を設定して論理 1=点灯 に統一
- BEAM 起動前(電源 ON 〜約 30 秒)は StatusLed が動いていないため、
  `atomcam2-pre-run` で両 LED を消灯に初期化(起動中に青が黄点滅と
  重ならないように)

## 14. 起動シーケンスの分離(fsck をクリティカルパスから外す)

電源断→再投入のコールドブートで「起動しました」まで約 3 分 25 秒かかる
問題を調査・改善した。

### 調査結果(Step 1)

- 遅さの正体は **/data(ext2)の e2fsck が約 165 秒**、かつそれが
  `nerves_runtime` の init_module(`FilesystemInit`)として**同期実行**され、
  shoehorn チェーン全体(vintage_net → nerves_ssh → アプリ)を
  ブロックしていたこと
- fsck は `e2fsck -p`(preen)を毎回実行しているが、**clean なら約 2 秒**で
  抜ける。165 秒かかるのは unclean(電源断)時の full check のみ
  → 「正常終了時はスキップ」は実質実装済みで、問題は配置だけ
- ext4 化は、実機で動くのが差し替え禁止の制御カーネル(対応 FS は
  **ext2 のみ**、`/proc/filesystems` で確認)のため、ext4.ko の vermagic
  一致ビルド以降の検証が必要な大きめの仕事 → 保留(方針どおり最後)

### 実装(Step 2: fsck 非同期化)

- `FilesystemInit` の check+mount を Task 化して即 return。
  early 段階で /data を触るものを排除:
  - **SSH ホスト鍵と user_dir** → `/media/mmc/nerves_ssh`(FAT、pre-run が
    BEAM 前にマウント)。既存鍵を実機でコピーしたのでホスト鍵は不変
  - **nerves_time の時刻ファイル** → `/media/mmc/.nerves_time`
  - 注意: これらは `config/runtime.exs` が起動時に上書きするため、
    **runtime.exs 側を変更する**こと(target.exs だけでは効かない)
- 非同期化に伴い umount に競合の可能性が生じるため、EBUSY リトライ
  (1 秒 × 5 回)を追加

### 実装(Step 3: camd の rootfs 化)

- `package/atomcam2-camera` を新設し、ビルド済み `atomcam2-camd` を
  `/usr/bin` に配置(`/data/camd` プレビルトを置き換え)
- camd の制御ファイルを `/data/camd.ctl` → **`/tmp/camd.ctl`** に変更して
  再ビルド(ソース同梱)。これでカメラ起動は /data に一切依存しない

### 実測

ソフト再起動(clean):

| イベント | 時刻(カーネル起動から) |
| --- | --- |
| 「起動しました」発声 | 約 38 秒 |
| RTSP 配信開始 | 約 44 秒 |
| /data fsck(clean preen、裏で実行) | 約 2 秒で完了 |

電源断→再投入(unclean、実機で確認):

| イベント | 時刻(カーネル起動から) |
| --- | --- |
| /data fsck 開始(バックグラウンド) | 27 秒 |
| **eth0 DHCP 取得(ping 応答開始)** | **29 秒** |
| camd 起動 | 40 秒 |
| **RTSP 配信開始** | **48 秒** |
| /data fsck 完了(約 108 秒)+ マウント | 135 秒 |

改善前はコールドブートで発声まで約 205 秒(全機能が fsck 待ち)だったのが、
ネットワーク 29 秒・配信 48 秒に短縮。fsck の所要時間は書き込み量により
変動する(今回 108 秒、前回 165 秒)。

### 既知の問題: コールドブートで発声が失敗する

電源断→再投入のブートでは「起動しました」が鳴らない(ソフト再起動では
毎回鳴る)。切り分け結果:

- モジュールロード順は正しい(tx_isp → audio)のに、audio ドライバの
  初期化が不完全になる: `jz_codec_register: probe() successful!` と
  CGU クロック設定までは出るが **devtmpfs に /dev/dsp が生成されず**、
  mknod で作っても **`IMP_AO_Enable = -1`** で再生できない
- camd 停止中でも失敗する → camd との資源競合ではない
- ソフト再起動(SoC ウォーム状態)では同じ手順で毎回成功する
- 仮説: コールド直後の早いタイミング(約 30 秒)での audio.ko ロードでは
  ハードウェアが未準備。vendor 運用時はモジュールロードが network 待ちの
  後(電源から約 100 秒)だったため顕在化しなかった可能性
- 次の一手: audio.ko のロードを遅らせる(または発声リトライを数十秒
  スパンで入れる)実験。要・電源断テストのため保留

## 15. RTSP 画面へのシステム情報表示とロゴ既定 OFF

- **ロゴの初期値を非表示**に変更。従来は camd が既定表示 → CameraNative が
  `logo off` を送る方式で、起動直後に一瞬ロゴが見えた。camd 側の既定を
  OFF(`gl.show = 0`)にして ctl 送信も廃止(`logo on` で表示は可能)
- **システム情報の OSD 表示**(左上、時計と同様の白文字):
  `info <text>` コマンドを camd に追加。既存フォント(sample の
  bgramapinfo)は数字 + 記号 3 種の 13 グリフしか無いため、Linux kbd の
  コンソールフォント **default8x16.psfu(パブリックドメイン)から
  ASCII 95 グリフの C ヘッダを生成**(`osd_font8x16.h`)し、2 倍拡大
  (16x32)で描画。printable ASCII 最大 40 文字
- 内容は `CameraNative` が **IP(eth0 優先)・FW バージョン・空きメモリ・
  CPU 使用率**を組み立てて **3 秒毎**に `/tmp/camd.ctl` へ送る(例:
  `192.168.222.66 v0.4.0 M:43M C:5%`)。空きメモリはカーネル 3.10 に
  `MemAvailable` が無いため MemFree + Buffers + Cached の近似、CPU は
  /proc/stat の busy 差分。ダッシュボードの代替としてのメモリコストは
  camd 内の静的バッファ約 80KB + Elixir 側ほぼゼロで、:inets httpd 案
  (数百 KB〜1MB)より軽い。ただし camd 停止時は表示も消えるため、
  障害診断用のダッシュボードとは補完関係
- **ハマり(重要)**: Buildroot の local パッケージはソースファイルを
  差し替えても**再ビルドされない**(初回ビルドの成果物が使われ続ける)。
  プレビルトバイナリを更新したら **`<PKG>_VERSION` を上げる**こと。
  今回は旧 camd が rootfs に残り `ctl unknown 'info …'` で発覚した
