## 実装中に判明したこと(提案書からの差分)

1. **OTP `:json` は Elixir の `nil` を文字列 `"nil"` にする**(JSON null は
   atom `:null`)。エンコード層(Router)で `nil → :null` の深い正規化を
   入れて解決。Collector は表現非依存のまま(提案書のアーキテクチャ
   どおり、変更はエンコード層に閉じた)
2. **`Dashboard.Supervisor` ではなく `Dashboard.Server`(GenServer)** に
   した。httpd は `:inets.start/stop` で管理する単一インスタンスであり、
   子プロセス群を監督する Supervisor よりも「所有する GenServer」が実態に
   合う。Facade(`Dashboard`)+ 実体、という提案書の責務分離は維持
3. **View は EEx ではなくヒアドキュメント補間**にした。テンプレートが
   1 枚で分岐も少なく、コンパイル時 EEx と実質同等(実行時テンプレート
   エンジン無しの意図は満たす)
4. カテゴリの実装差分:
   - `camera.camd_pid / rss` は **`camd_alive`(boolean)** に変更
     (MuonTrap 経由では OS PID を素直に取れないため。必要になれば
     `/proc` 走査で追加可能)
   - **NAS カテゴリは未実装**(NasExporter は vendor 録画前提で現在
     待機状態のため。native 録画が入った時点で追加)
   - **フレーム心拍・stall ストライクは未実装**(`RtspServer` は vendor
     経路用で native 心拍が未整備。残件の「心拍監視の native 対応」と
     同時に追加)
   - `rtsp.announce_history` を追加(起動アナウンス履歴の直近 3 行。
     ブート毎の成否がブラウザから見える)

## Phase 2 実装(2026-08-04 追記)

提案書の Phase 2(操作 + 認証)も実装・実機検証済み。

- 追加ルート: `POST /announce`(テスト発声 = 起動アナウンス再生)/
  `POST /reboot`(1 秒後に `Nerves.Runtime.reboot/0`。応答を返してから
  再起動)
- **認証は提案書の方針どおり**: GET は匿名のまま、**POST のみ HTTP Basic
  認証**(ユーザー `admin`)。パスワードは IEx から設定し
  (`Dashboard.set_password("...")`、`nil` で削除)、
  `/data/atomcam2-dashboard/password.conf`(0600)に永続化。
  **未設定の間は操作を全拒否**(安全側の既定)。比較は SHA-256 の
  定数時間比較
- HTML にボタン(`confirm()` ダイアログ付き)。CSRF 対策は入れない
  (読み取りは副作用なし・書き込みは認証必須、という提案書の判断どおり)
- 検証(実機): 未認証 POST=401、誤パスワード=401、正パスワードで発声・
  再起動が実行、パスワード削除後は再び 401

### ハマり: `WWW-Authenticate` ヘッダで 2 段バグ(PR #35)

ブラウザのボタンで「確認ダイアログ OK → unauthorized(本文表示)」となり、
**認証ダイアログが出ない**症状が出た。inets のレスポンスヘッダ表現に起因
する 2 段のバグだった:

1. ヘッダキーを **atom**(`www_authenticate:`)で渡すと、inets が
   `Www_authenticate`(アンダースコア)として送信 → 標準の
   `WWW-Authenticate` にならずブラウザが無視 → 401 本文が表示される
2. **Elixir 文字列(バイナリ)キー** `"WWW-Authenticate"` に変えると、
   inets の `transform/1` が atom/charlist しか受け付けず
   function_clause で **500** になる
3. 正解は **charlist キー** `~c"WWW-Authenticate"`。
   `WWW-Authenticate: Basic realm="atomcam2"` が正しく送られ、Firefox /
   Chrome が認証ダイアログを出す。実機の Firefox でボタン → 認証 → 発声・
   再起動を確認

教訓: inets httpd の任意ヘッダはキーを **charlist** で渡す。atom は名前が
崩れ、Elixir 文字列(バイナリ)は 500 になる。

## Phase 3 実装(静止画プレビュー)+ ナイトビジョン(2026-08-04 追記)

提案書 Phase 3 の静止画プレビューを**オンデバイスで実現**した。当初
「デバイス上に H.264 デコーダが無いのでデバイス外生成」としていたが、
atomcam_tools の Web UI(`get_jpeg.cgi` → libcallback)の実装を調査した
ところ、**T31 の JPEG エンコーダチャネルを使っており H.264 デコードは
不要**と判明した。同じ方式を native camd に移植した。

- camd に **JPEG エンコーダチャネル**を追加(H.264 と同一グループなので
  スナップショットにも OSD が乗る)。`/tmp/camd.snap` を touch すると 1 枚
  撮って `/tmp/camd.jpg` に出力。`CameraNative.snapshot/1` がパスを返す
- ダッシュボード: `GET /snapshot.jpg`(匿名 GET)+ ページ上部にインライン
  表示。実機で 1920×1080・約 86KB の正常 JPEG を確認
- **ハマり(この libimp 固有)**: JPEG チャネルは **チャネル番号 2**
  (1 だとクラッシュ)、**initialQP は正の値**(-1 は量子化テーブルで
  segfault)、**`IMP_Encoder_SetbufshareChn` で H.264 とバッファ共有**
  (別バッファ確保は rmem 不足で segfault)が揃って初めて CreateChn 成功
- あわせて**ナイトビジョン** `CameraNative.night_vision(:on|:off|:auto)`
  とダッシュボードボタンを実装(ISP RunningMode + IR-cut GPIO + IR LED)。
  実機で ON 時に IR LED 点灯・紫がかった夜間映像を確認
