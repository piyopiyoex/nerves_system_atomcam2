# 2026-08-02 RTSP 配信方式の検討

## 文書情報

- 状態: 検討完了

Atom Cam 2 のライブ映像を RTSP で配信するための調査結果と実装提案。
[mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools) の実装分析に
基づく。[有線 LAN 接続提案書](20260802-有線LAN接続方式の検討.md)の後続。

## 背景と目的

本システムは現在 RTSP 非対応(README に明記)。ライブ映像の閲覧手段は標準
Atom アプリ(ベンダー互換ランタイム経由)のみで、VLC・Home Assistant・
Frigate 等の標準的なクライアントから利用できない。録画の NAS 転送はあるが、
リアルタイム性が必要な用途に応えられない。有線 LAN 対応により帯域の安定した
配信経路が確保できたため、次の拡張として RTSP 配信を検討する。

## 調査結果

### 1. atomcam_tools の RTSP アーキテクチャ

データの流れは 4 段構成:

```text
iCamera_app(ベンダーアプリ、エンコード済みフレームを生成)
  -> libcallback.so(LD_PRELOAD フック)
       local_sdk_video_set_encode_frame_callback を横取りし
       エンコード済みフレームを取得
  -> v4l2loopback(カーネルモジュール、/dev/video0..2 の仮想デバイス)
  -> v4l2rtspserver + live555(RTSP :8554、RTSP over HTTP :8080)
```

要点:

- **フック**(`libcallback/video_callback.c`): ベンダー SDK のコールバック
  登録関数を dlsym で横取りし、**再エンコードなし**でエンコード済みフレームを
  得る。チャンネル構成は ch0: 1920x1080 H.264、ch1: 640x360 HEVC、ch2: 低解像度。
  取得フレームは V4L2 loopback デバイスへ書き込むだけ
- **注入方法**: `LD_PRELOAD=/tmp/system/lib/modules/libcallback.so
  /system/bin/iCamera_app`(`atom_init.sh`)
- **配信**: v4l2rtspserver が loopback を読み RTSP 配信。`RTSP_AUTH` で
  Basic 認証、`RTSP_OVER_HTTP` で :8080 の HTTP トンネルも選択可
- **音声**: ALSA aloop(カーネルパッチで追加)へ PCM を流し、
  v4l2rtspserver のパッチ(`0003-audio-any-fomat.patch`)で多形式対応。
  `hw:0,0` / `hw:2,0` / `hw:4,0` を映像とペアリング
- **任意機能**: go2rtc(Go 製単体バイナリ)で WebRTC(:8555)、RTMP、
  HomeKit に対応。RTSP だけなら不要
- **運用**: `hack.ini` で有効化・認証を設定、init スクリプトと watchdog で
  再起動管理

### 2. 本リポジトリ側の適合性

| 項目 | 現状 | 評価 |
| --- | --- | --- |
| V4L2 | `CONFIG_VIDEO_DEV=y` / `CONFIG_VIDEO_V4L2=y` 有効済み([linux-3.10.14.defconfig](../../linux-3.10.14.defconfig)) | v4l2loopback モジュールの追加だけでよい |
| LD_PRELOAD 注入 | **既存機構あり**。freestanding の `libcompat-shim.so`([package/atomcam2-vendor-compat-shim](../../package/atomcam2-vendor-compat-shim/))を vendor プロセス起動時に注入済み | 同じ流儀(`-nostdlib` の Buildroot パッケージ)で video フックを追加可能。uClibc の vendor プロセスでも libc 非依存で安全 |
| モジュール配布 | 有線 LAN 対応で確立済み: vermagic が一致すれば `mix upload` のみで配布可能 | v4l2loopback は out-of-tree なので**カーネルイメージ変更なし**(SHA ピン据え置き)で追加できる |
| RTSP サーバー | なし | v4l2rtspserver + live555 を Buildroot パッケージとして追加(atomcam_tools の custompackage とパッチを流用、musl でビルド) |
| 隔離境界(ADR 0008) | vendor chroot には選択したデバイスのみ公開、ネットワークは Nerves 所有 | フックは chroot 内から `/dev/videoN`(仮想デバイス)へ書くだけ。RTSP サーバーは **Nerves 側 rootfs** で動かすため、ネットワーク所有権の境界を保てる。chroot への loopback デバイス公開は ADR 追記が必要 |
| 音声 | カーネルは OSS のみ(`CONFIG_SND` 無効) | ALSA + aloop の有効化はカーネル変更(SHA ピン更新)を伴う → **フェーズ分離** |
| メモリ | カーネル `mem=92M`、Nerves + BEAM + vendor ランタイム稼働中 | v4l2rtspserver + live555 は数 MB 級で許容見込み(要実測)。go2rtc(Go ランタイム)は重く、初期スコープから除外 |

## 提案する実装方式

### 方式比較

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A(推奨)** | atomcam_tools 移植: v4l2loopback + 専用 video フック + v4l2rtspserver/live555 | 再エンコードなしで低負荷。実績のある構成。RTSP サーバーを Nerves 側に置けて隔離境界と両立 | フックの開発・検証が必要 |
| B | go2rtc 単体 | WebRTC/RTMP も一挙に対応 | Go ランタイムのメモリ負荷が 92MB 環境で懸念。フレーム取得には結局フックが必要 |
| C | Elixir(Membrane 等)で配信 | BEAM 監督下で完結 | mipsel/省メモリでの実績に乏しく、H.264 パススルーでも工数大。却下 |

**案 A を推奨。** go2rtc は将来 WebRTC が必要になった時の追加オプションとする。

### 実装タスク(案 A)

1. **Buildroot パッケージ追加**(atomcam_tools の custompackage を流用):
   - `v4l2loopback`(カーネル 3.10 互換バージョンに固定、モジュールのみ)
   - `live555` + `v4l2rtspserver`(musl ビルド、audio パッチは音声フェーズまで保留)
2. **`package/atomcam2-video-hook`** 新規: compat-shim と同じ freestanding 流儀の
   preload ライブラリ。`local_sdk_video_set_encode_frame_callback` をフックし、
   エンコード済みフレームを `/dev/videoN` へ書き込む
   (atomcam_tools `libcallback/video_callback.c` を参考、機能は映像のみに絞る)
3. **[atomcam2-vendor-camera](../../rootfs_overlay/usr/bin/atomcam2-vendor-camera)**:
   - `LD_PRELOAD` に video フックを追加(既存 shim と併記)
   - chroot へ `/dev/video0..2`(loopback 仮想デバイス)を公開
   - `precheck` に v4l2loopback ロード状態とデバイス存在の検査を追加
4. **アプリ**: `RtspServer` GenServer を追加(VendorCamera と同じ監督・設定の
   作法)。`/data/atomcam2-rtsp/enabled` で有効化、ポート 8554、認証設定は
   `/data` 配下。vendor camera 停止時は配信も停止
5. **ADR 追記**: loopback 仮想デバイスの chroot 公開と、その境界上の位置付け
6. **文書**: README(機能一覧)、architecture、サンプル README、CHANGELOG

## フェーズ 1 実施結果(2026-08-02 追記)

**RTSP 配信に成功した。** ホストから受信したストリームを解析し、実際の映像
フレームが流れていることを確認済み。

### 検証結果

- ストリーム URL: `rtsp://<camera>:8554/video1_unicast`
- SDP: `H265/90000`、`x-dimensions:640,360`、有効な sprop-vps/sps/pps
- 15 秒受信して 326KB(約 174 kbps)、HEVC の NAL 構造を解析した結果
  **IDR 15 枚 + 非 IDR スライス 268 枚 = 約 283 フレーム(約 19 fps)**、
  毎秒 1 枚のキーフレーム。再エンコードなしのパススルーで想定どおり
- 配信中もベンダーランタイムは `result=running`、エンコーダエラー 0 件

### 想定との差分および対処した問題

| 事象 | 内容と対処 |
| --- | --- |
| **フックのシンボル解決失敗** | コンストラクタ内の `dlopen` は動的リンカ初期化前に走るため失敗し、コールバック登録が `-1` を返してベンダーの全エンコーダが停止(`IMP_Enc_PollingStream fail` を連発)。**遅延解決 + `RTLD_NEXT`** に変更して解消(`dlopen` はフォールバック) |
| **メモリ不足** | loopback 3 デバイス(うち 2 本が 1080p)ではバッファ確保でシステムごと再起動。**640×360 の ch1 のみ 1 デバイス**に絞って解決。`ATOMCAM2_VIDEO_LOOPBACK_VIDEO_NR` で作成するノードを選択できるようにした |
| チャンネル対応 | ベンダーが使うのは 0 / 1 / 3。フックはこの 3 つのみ横取りする(それ以外は素通し) |
| ホスト側の再生 | 検証機の VLC に H.265 デコーダが無く映像表示は不可。ストリーム解析で内容を確認した。VLC の H.265 対応ビルドや Home Assistant 等では再生可能な想定 |

### メモリの実測値(全 87.7MB)

| 状態 | MemFree | Cached | 判定 |
| --- | --- | --- | --- |
| ベンダーカメラ停止 | 約 23MB | — | 余裕あり |
| + ベンダーカメラ稼働 | 約 1.7MB | 約 26MB | 再利用可能 約 30MB |
| + RTSP 配信中 | 約 1.8MB | 約 26MB | **安定動作** |

`MemFree` は小さいがページキャッシュが大半で、再利用可能メモリは約 30MB を
維持している。1080p チャンネルを使うとこの余裕が失われる。

### 長時間運転で分かったこと(追記)

#### メモリリークはない

`/proc/meminfo` と主要プロセスの `VmRSS` を 30 秒間隔で記録した結果
(`/data/mem-samples.log`)、**リークの兆候は確認されなかった**。

| プロセス | 推移 |
| --- | --- |
| `beam.smp` | 約 30〜32MB でほぼ横ばい(むしろ微減) |
| `v4l2rtspserver` | 約 2.3〜2.4MB で安定 |
| `iCamera_app` | 16.5〜18.5MB の範囲で変動 |

`MemFree` は 1.5〜8MB を上下するが `Cached` と逆相関しており、
ページキャッシュの正常な挙動である。

#### モバイルアプリの HD 視聴と競合することがある

**再現条件**: VLC で RTSP 再生中に、モバイルアプリでライブ映像を開いて
**HD に切り替える**(2 台目のアプリが加わるとさらに起こりやすい)。

このとき RTSP の映像が止まる。ただし
**`v4l2rtspserver` のプロセスも `iCamera_app` も生きたまま**で、
メモリも枯渇していない。アプリを終了すると自動的に復旧する。

ベンダーログには解像度とチャンネルの再設定が記録される。

```text
[property.c] (property_video_channel) type:2, value:1
[property.c] (property_video_resolution) type:2, value:1
[property.c] new resolution: 1
```

HD ライブはチャンネル 0(1920×1080 H.264)を使うと考えられ、
これは RTSP が横取りしているチャンネルと同一である。つまり
**同一エンコーダチャンネルの奪い合い**であり、こちらの実装や
メモリ管理の問題ではない。SD 視聴中は競合しない。

#### 別チャンネルへの退避は失敗した

競合回避のため ch3(`/dev/video2`、1920×1080 H.265)へ切り替えて検証したが、
**採用しない**。理由は 2 つ。

- **H.265 はクライアント互換性が低い。** 検証に使った VLC 3.0.x(ホスト側・
  利用者側とも)で H.265 をデコードできず、映像を表示できなかった
- **モバイルアプリの再生が停止した。** ch3 はベンダーがクラウド配信や録画に
  使っている可能性があり、横取りするとアプリ側に影響が出る

ch0 の競合を避けようとして別の競合を作る結果になった。**ch0(1080p H.264)を
使い、HD 視聴中の一時停止を許容する**のが現時点で最も実用的である。

#### 配信チャンネルを変えると URL が変わる

`ATOMCAM2_VIDEO_LOOPBACK_VIDEO_NR` を変更すると、RTSP のパスも
`video<N>_unicast` に変わる。切り替え時はクライアント側の URL 更新を忘れない
こと。VLC は履歴から古い URL を再利用するため、履歴からではなく貼り直す。

### 参考: 動作実績のある別実装から学べる設計(2026-08-03 追記)

同じ作者による [hello_usbcam_rtsp](https://github.com/kurokouji)
(NanoPi NEO + USB カメラ + Nerves、実機で H264 約 30fps 配信を確認済み)は、
本件と同じ「Elixir は薄い監視層、配信は v4l2rtspserver」という構成を採る。
本システムの `RtspServer` より優れている点があり、取り込む価値がある。

| 論点 | hello_usbcam_rtsp | 本システムの現状 |
| --- | --- | --- |
| プロセス起動 | **`MuonTrap.Daemon.start_link`**(GenServer にリンク) | シェルスクリプト + PID ファイル |
| 死活検知 | **`trap_exit` + `{:EXIT, pid, reason}`** で即座に検知 | 10 秒間隔のポーリング |
| 異常時の挙動 | daemon の EXIT を**リトライに変換**し、ノードは落とさない | 同左(ポーリングで再起動) |
| デバイス選択 | `v4l2-ctl` で **H264 を出すノードを動的検出**。USB 再列挙に追従 | 固定(`/dev/videoN`) |
| ヘルスチェック | 掴んでいるノードの消失を検知したら daemon を kill → 再検出 | なし |

特に重要なのが **`Process.flag(:trap_exit, true)` の意図**である。リンクした
daemon が即異常終了すると、EXIT がそのまま伝播して GenServer ごとクラッシュし、
Supervisor の再起動が短時間に連鎖して**アプリケーション停止 → ノード再起動**まで
波及する。exit をトラップしてメッセージとして受け、「再試行」に変換することで
これを断ち切っている。

#### 本システムへ取り込む際の注意

`MuonTrap` はそのままでは使えない可能性がある。`VendorCamera` には
「**MuonTrap の port helper が保護カーネル(3.10)上で `:epipe` で落ちる**」という
実測に基づくコメントがあり、そのため `System.cmd` を使っている。取り込む場合は
まず MuonTrap の動作可否を実機で確認する必要がある。

動かない場合でも、**`trap_exit` による即時検知**と**ヘルスチェックによる
掴み直し**という設計思想は、`Port.open` を直接使う形で再現できる。現状の
10 秒ポーリングより反応が速く、[長時間動作 記録](20260802-長時間動作の検証.md)で
課題として挙げた「フレーム供給停止の検知と自動再起動」にも素直につながる。

## リスクと検証項目

| リスク | 内容 | 対応 |
| --- | --- | --- |
| フックの SDK 依存 | `local_sdk_video_set_encode_frame_callback` のシグネチャはベンダーファーム版数に依存 | 対応済みファーム(Ver.4.58.x 系)は atomcam_tools が長期検証済み。precheck でシンボル存在を確認 |
| メモリ | 92MB 中で BEAM + vendor + RTSP が同居 | PoC で実測。バッファ数を絞る(v4l2loopback の `max_buffers`) |
| v4l2loopback の 3.10 互換 | 新しめのバージョンは古いカーネルで非対応 | atomcam_tools が使用するバージョン・パッチをそのまま踏襲 |
| HEVC ストリーム | ch1 は HEVC でクライアント互換が狭い | 主ストリームは H.264 の ch0。ch1/ch2 は任意 |
| 隔離境界の変更 | chroot へのデバイス公開が ADR 0008 の趣旨に触れる | 公開するのは**仮想** loopback のみ(実カメラデバイスは従来どおり非公開)。ADR に明記 |
| watchdog との干渉 | vendor 停止時に RTSP サーバーが loopback を掴んだままになる | RtspServer GenServer が VendorCamera の状態に追従して停止 |
