## ボードの前提

- RAM 合計 128MB のうち、Linux に見えるのは **MemTotal 85〜87MB**。
  残り約 36MB は **rmem(メディア用予約領域)**で、ISP のフレームバッファ
  や OSD リージョンはこちらから取られ、**Linux の MemFree には現れない**
- スワップなし。avail を使い切ると OOM killer 直行

## 現状の実測(native モード稼働時)

OSD デバッグパネル表示より(2026-08-04、192.168.1.77):

```
Mem: total 85M  free 2M  avail(approx) 41M
BEAM: total 25M  processes 11M  binary 0M  procs 209
```

| 指標 | 値 | 読み方 |
| --- | --- | --- |
| MemFree | **1〜2M** | 即時未使用分。**Linux は空きをページキャッシュに回す設計なので、常に数 MB なのが正常**。この値の小ささは問題ではない |
| avail(近似) | **約 41M** | MemFree + Buffers + Cached。「キャッシュを追い出せば即使える量」= **実質の余裕**。カーネル 3.10 に MemAvailable が無いための近似 |
| beam.smp RSS | 約 34M | 最大の常駐プロセス(BEAM 内部 total は約 25〜26M) |
| atomcam2-camd RSS | 約 3M | native カメラ(デバッグパネル使用後。未使用なら約 1.5M) |
| v4l2rtspserver RSS | 約 13M | RTSP 配信 |

## vendor 時代との比較

| 構成 | 実質余裕(reclaimable / avail) | カメラ系常駐 |
| --- | --- | --- |
| vendor + RTSP(2026-08-03 時点) | 約 26M | iCamera_app + hl_client + assis ≈ **25M** + rtspserver 13M |
| **native + RTSP(現在)** | **約 41M** | camd ≈ 1.5〜3M + rtspserver 13M |

方式 B(native 化)によりベンダー三点(約 25M)を camd(約 1.5M)へ置換した
効果がそのまま avail の +15M に表れている。**87MB ボードとしては健全な状態**。

## 危険水域の目安と監視

- 注意すべきは MemFree ではなく **avail**。目安として **10M を切る**と、
  カーネルドライバの瞬間的な確保失敗(atomic allocation)や断片化による
  大きな連続領域の確保失敗が起き得る
- 監視はデバッグパネル(`CameraNative.osd_debug(true)`)の avail 行で行う。
  長期トレンドが必要になれば履歴ファイル方式
  (`/data/boot-announce-history.log` と同様)を追加する

## さらに余裕を積む場合のレバー(未実施)

1. **BEAM の削減**(本命、[平常時メモリ削減 提案書](20260803-平常時メモリ削減の検討.md)):
   不要 OTP アプリの削除・RingLogger バッファ縮小など、合計数 MB 規模
2. `vm.min_free_kbytes` の引き上げ: カーネルの緊急予備を厚くし
   atomic 確保失敗に備える(その分 avail は減る)
3. `RtspServer`(vendor 用)・`VendorCamera` の削除整理(コード分の微減)

## 補足: OSD デバッグパネルのコスト

- camd 内の描画バッファ 573KB は BSS で、**パネルを一度も使わなければ
  常駐しない**(運用時の増加ゼロ)。使用後は camd 再起動まで常駐
- 表示用の OSD リージョン(573KB)は rmem 側なので avail に影響しない
- IPU は約 1MB 超の OSD リージョンを拒否するため 2 倍拡大描画は不可
  (詳細は [2026-08-04 作業記録](20260804-起動安定化と状態画面の作業記録.md))
