# 2026-08-06 JPEG と H.264 の経路分離

## 文書情報

- 日付: 2026-08-06
- 種別: 開発記録
- 状態: 完了
- 位置づけ: 当時の調査、実装、検証を残す記録。現在の仕様は上位文書を優先する。
- 現行資料: [構成](../構成.md) / [運用](../運用.md)

camd(方式B のネイティブ実装)の JPEG スナップショットチャンネルと
H.264(RTSP)チャンネルが**バッファを共有**しており、これが Web
ダッシュボードのライブ映像ポーリングと衝突して RTSP 配信が無出力に
なる(wedge する)ことが実機 A/B テストで実証された。本提案は
[mnakada/atomcam_tools](https://github.com/mnakada/atomcam_tools) の
参考実装に倣い、**JPEG チャンネルに独立した(小さい)バッファを持たせて
根本的に競合を解消する**方式を提案する。

関連: [RTSP と Web ダッシュボードの競合調査](20260806-RTSPと状態画面の競合調査.md)
(本提案の根拠となる実機実証データ)、[RTSP 配信 提案書](20260802-RTSP配信方式の検討.md)
(87MB 機のメモリ制約の全体像)、[ダッシュボード 提案書](20260803-状態画面の設計.md)。

## 背景

2026-08-06、192.168.1.77 で実機 A/B テストを実施し、以下を確認した
(詳細は上記の競合調査ドキュメント):

- **ダッシュボード無効化: 20/20 reboot で camd フレーム生成成功**
- **ダッシュボード有効化: 3/3 reboot で camd が無出力 wedge**
  (camd・v4l2rtspserver ともプロセスは正常起動するが、フレームが
  一切生成されない)

原因はコード上で特定済み。`package/atomcam2-camera/camd.c` の JPEG
エンコーダチャンネル(`JPEG_CHN`)は、メモリ制約を理由に **H.264
チャンネル(`CHN`)とバッファを共有**する設計になっている:

```c
/* Second encoder channel, JPEG, registered to the same group so it
 * receives the same OSD-overlaid frames. Only started on demand for a
 * snapshot, so it costs nothing while idle. */
{
	IMPEncoderChnAttr jenc;
	memset(&jenc, 0, sizeof(jenc));
	rc = IMP_Encoder_SetDefaultParam(&jenc, IMP_ENC_PROFILE_JPEG, IMP_ENC_RC_MODE_FIXQP,
			W, H, FR_NUM, FR_DEN, 0, 0, 25, 0);
	if (step("Encoder_SetDefaultParam(jpeg)", rc) < 0) return 1;
	/* Share the H.264 channel's buffer instead of allocating a second
	 * full-res encoder buffer (which exhausts rmem and crashes). Must
	 * be called after the shared channel is created, before this one. */
	step("Encoder_SetbufshareChn(jpeg)", IMP_Encoder_SetbufshareChn(JPEG_CHN, CHN));
	if (step("Encoder_CreateChn(jpeg)", IMP_Encoder_CreateChn(JPEG_CHN, &jenc)) < 0) return 1;
	if (step("Encoder_RegisterChn(jpeg)", IMP_Encoder_RegisterChn(CHN, JPEG_CHN)) < 0) return 1;
}
```
(`camd.c:634-649`)

重要なのは、**JPEG チャンネルが H.264 チャンネルと同じ `W x H`
(1920x1080、`camd.c:51-52`)でエンコーダを初期化している**点。
`capture_jpeg()`(`camd.c:264-299`)は毎回のスナップショット要求で
`IMP_Encoder_StartRecvPic(JPEG_CHN)` / `StopRecvPic(JPEG_CHN)` を
呼ぶが、これは **H.264 チャンネルがメインループで
`IMP_Encoder_PollingStream(CHN, ...)` を回している最中に、同じ
共有バッファへ並行アクセスする**ことを意味する。ダッシュボードの
毎秒ポーリングでこれが繰り返し発生し、起動直後(GO ハンドシェイク
窓、[[atomcam2-rtsp]])に重なると、エンコーダパイプラインが無出力の
まま固まる。

## 目的

JPEG チャンネルを H.264 チャンネルから**バッファ的に完全に独立**させ、
ダッシュボード(または将来の他クライアント)がどれだけ高頻度にスナップ
ショットを要求しても RTSP 配信に影響しないようにする。

## 非目標

- ダッシュボードの UI・ポーリング頻度自体を変更すること(それは対症療法。
  [競合調査](20260806-RTSPと状態画面の競合調査.md) §4 の
  次善策として別途検討可能だが、本提案はエンコーダ側の根本修正が対象)。
- vendor `iCamera_app` を復活させること([[atomcam2-approach-b]] の
  方針決定「iCamera_app は使用しない」を維持)。
- v4l2loopback・RTSP 配信の仕様変更。

## 方式の比較

### 案A(推奨): JPEG チャンネルを低解像度化して独立バッファ化

`jenc` の `W, H` を **1920x1080 → 640x360**(または同等の低解像度)に
変更し、`IMP_Encoder_SetbufshareChn` の呼び出しを削除する。

- IMP エンコーダは、同一グループ内の複数チャンネルがそれぞれ異なる
  解像度でエンコードすること(メイン+サブストリーム構成)をサポート
  している。今回は物理 FrameSource チャンネルを増やす必要はなく、
  **エンコーダチャンネルの解像度指定を下げるだけ**で済む。
- 640x360 は [[atomcam2-rtsp]] で既に「メモリ制約下で安定動作する
  解像度」として実績がある値をそのまま流用する(新たな未知のリスクを
  持ち込まない)。
- バッファサイズは 1920x1080 比で画素数ベース約 1/9。共有バッファを
  やめても、当時「exhausts rmem and crashes」と記録された全解像度版
  よりもはるかに小さい追加負荷で済む見込み。
- **コード変更量が小さく**(1 関数内の数行)、リスクを局所化しやすい。

**トレードオフ**: ダッシュボードのスナップショット画像が 1920x1080 か
ら 640x360 に下がる。ライブビュー用途(ブラウザ表示は CSS で
`max-width: 100%` に縮小表示)には十分な解像度であり、実質的な
デグレードはないと判断する。

### 案B: 独立した物理 FrameSource チャンネルを追加

atomcam_tools/vendor 構成そのままに、`CHN=1` の物理 FrameSource
チャンネルを新設し、低解像度の JPEG エンコーダをそこに bind する。

- 案A よりも vendor 構成に近く「王道」だが、FrameSource の作成・bind
  チェーンが増える分コード変更量・検証項目が増える。
- 案Aで同等の効果(独立バッファ・低解像度)が得られる以上、追加の
  複雑さに見合う利点が現時点では見当たらない。**却下、将来 案Aで
  不十分と判明した場合の代替として記録だけ残す**。

### 案C: バッファ共有を維持し、アクセスを排他制御する

`capture_jpeg()` と メインループの `PollingStream(CHN, ...)` が同時に
共有バッファへアクセスしないよう、mutex 相当の排他や「GOP 境界でだけ
スナップを許可する」等のタイミング制御を camd 内に実装する。

- 症状を抑えるだけで根本原因(バッファ共有そのもの)は残る。実装も
  IMP のチャンネル内部状態への深い依存になり、脆い。
- **不採用**。ただし案Aの実機検証で予期しない副作用が出た場合の
  緊急避難策として頭には置いておく。

## 推奨案(案A)の詳細設計

### 変更箇所

`camd.c` の JPEG チャンネル初期化ブロック(634-649 行)を以下のように
変更する:

```c
#define JPEG_W 640
#define JPEG_H 360

...

{
	IMPEncoderChnAttr jenc;
	memset(&jenc, 0, sizeof(jenc));
	rc = IMP_Encoder_SetDefaultParam(&jenc, IMP_ENC_PROFILE_JPEG, IMP_ENC_RC_MODE_FIXQP,
			JPEG_W, JPEG_H, FR_NUM, FR_DEN, 0, 0, 25, 0);
	if (step("Encoder_SetDefaultParam(jpeg)", rc) < 0) return 1;
	/* Independent buffer at reduced resolution: small enough to fit rmem
	 * without sharing the H.264 channel's buffer (see 20260806 proposal).
	 * No SetbufshareChn — JPEG capture must not touch the H.264 channel's
	 * live buffer while it is streaming. */
	if (step("Encoder_CreateChn(jpeg)", IMP_Encoder_CreateChn(JPEG_CHN, &jenc)) < 0) return 1;
	if (step("Encoder_RegisterChn(jpeg)", IMP_Encoder_RegisterChn(CHN, JPEG_CHN)) < 0) return 1;
}
```

`capture_jpeg()` 自体(`camd.c:264-299`)はロジック変更不要
(StartRecvPic/PollingStream/GetStream/StopRecvPic のシーケンスは
そのまま)。ただし出力 JPEG の解像度が変わるため、コメントの
「same OSD overlay」は維持されるが解像度言及があれば更新する。

### メモリ試算(概算、実機検証で確定させる)

- 1920x1080 NV12 生フレーム: 約 3.1MB/枚
- 640x360 NV12 生フレーム: 約 0.35MB/枚(約 1/9)
- JPEG 出力(FIXQP 25, 640x360 は 1920x1080 実測 90-100KB の
  面積比から概算)おおよそ 15-25KB 程度と推定
- ワーキングバッファ+ストリームバッファを合わせても **追加消費は
  数百 KB〜1-2MB 程度**と見込む(要実機確認。[[atomcam2-rtsp]] の
  rmem=36MB 予算に対し、H.264 側が既にどれだけ使っているかは
  未計測のため、この試算はあくまで見積もり)。

### 検証計画

1. **単体起動確認**: 案A 版 camd をカナリヤ機(192.168.1.32、
   [[atomcam2-canary-device]])に投入し、`IMP_Encoder_CreateChn(jpeg)`
   が `rc=0` で成功するか(rmem 不足で失敗しないか)を確認する。
2. **画質確認**: `snap` コマンドで 640x360 JPEG を取得し、劣化が
   許容範囲か目視確認する。
3. **真の A/B 再実施**: [競合調査](20260806-RTSPと状態画面の競合調査.md)
   §3.1〜3.5 と同一手順(10 回連続 reboot、ダッシュボード有効化)を
   案A 版 camd で実施し、**wedge が再現しなくなること**を確認する
   (目標: 有効化状態でも 10/10 成功)。3 回連続失敗のサーキット
   ブレーカーは踏襲する([[atomcam2-device-handling]])。
4. **長時間観察**: 問題なければ数時間〜半日、ダッシュボードを開いた
   ままの実機で稼働確認する([[atomcam2-rtsp-stability]] の「6 時間
   安定確認」と同様の基準)。
5. 上記すべてクリアしたら `camd.c` の `VERSION` を上げてコミットし
   ([[atomcam2-approach-b]] の Buildroot 罠に注意)、カナリヤ機以外
   への展開を判断する。

### リスクと軽減策

- **rmem 不足で `IMP_Encoder_CreateChn(jpeg)` が失敗する可能性**:
  640x360 でも不足する場合は、さらに低い解像度(例 320x180)や
  `IMP_ENC_RC_MODE_FIXQP` の QP 引き上げ(ファイルサイズ削減)で
  調整する。それでも不足するなら案B(独立 FrameSource)を検討。
- **JPEG チャンネル追加によるアイドル時メモリ増**: 現状「スナップ
  要求時のみ Start/StopRecvPic」の方針は維持するため、チャンネル
  自体は常時存在するが Start されていない間のコストは小さいと
  見込む(現行実装のコメント「costs nothing while idle」の前提を
  維持)。要実機確認。
- **画質低下への不満**: ライブビュー用途では 640x360 で十分と判断
  しているが、将来「高解像度スナップショットが欲しい」要求が出た
  場合は、別途オンデマンドの高解像度チャンネルを検討する(頻度が
  低ければ都度 Create/Destroy でコストを許容できる可能性がある)。

## ロールアウト

1. カナリヤ機([[atomcam2-canary-device]] 現在 192.168.1.32)で上記
   検証計画を実施。
2. 問題なければ `checkpoint-20260805-night-fix` 系列とは別ブランチで
   実装し、レビュー後 main へ統合。
3. 他の稼働機([[atomcam2-device-handling]] のとおり断りなく叩かない)
   へは、ユーザ確認のうえで段階的に展開する。

## 実施結果(追記、2026-08-06)

案A(独立バッファ化 + 640x360)を **camd VERSION 30** として実装・投入し、
§検証計画のとおりダッシュボード有効化状態での 10 回 reboot A/B を再実施
した結果 **10/10 成功**(旧: 3/3 失敗)を確認、根本修正として妥当と実証
した(詳細は競合調査ドキュメント §3.4〜3.5)。

その後ユーザ要望でフル解像度(1920x1080、VERSION 31)を試したところ、
実機 2 台で画面全体が紫化する副作用が発生し、いったん 640x360 に戻した
(VERSION 32)。しかし**これは JPEG チャンネル分離とは無関係な別の不具合
(ISP キャリブレーションファイル `/etc/sensor/gc2053-t31.bin` の欠落)**
と判明し、そちらを修正(VERSION 34)した上でフル解像度を再度有効化した
ところ(VERSION 35)、両機とも紫化せず正常に動作した。**「画質低下への
不満」(§非目標寄りの懸念)は解消し、現在はフル解像度のまま独立バッファ
運用中**。詳細: [ISP キャリブレーション欠落 技術相談](20260806-ISP補正情報欠落の調査.md)。
