# ADR 0010: 文書の役割と配置を分離する

## 状態

2026 年 8 月 6 日に採用し、既存文書へ適用済み。

## 背景

開発初期は、提案、技術相談、実装報告、動作確認、引き継ぎ書を
`docs/` 直下へ追加していた。その結果、途中段階の情報と現行仕様が同じ階層に並び、
どの文書を優先すべきか判断しにくくなった。

また、英語と日本語のファイル名、日付区切り、文書見出し、状態表現が混在し、
関連する記録を時系列で追うことも難しくなっていた。

## 決定

文書を次の三つの役割へ分離する。

- `docs/`: 現在の利用者が最初に読む現行資料
- `docs/adr/`: 長期間維持する設計判断
- `docs/worklog/`: 調査、実装、実機検証、当時の提案などの履歴

`docs/` 直下には、次の現行資料だけを置く。

- `README.md`: 文書の入口と優先順位
- `はじめに.md`: 初回導入と最短の動作確認
- `構成.md`: 現行システムの責務と境界
- `運用.md`: 日常操作、更新、障害切り分け

画像などの文書用ファイルは `docs/assets/` に置く。

ADR は `NNNN-内容.md`、開発記録は `YYYYMMDD-内容.md` とする。
ファイル名は日本語を基本とし、製品名、規格名、プロトコル名などの固有名だけ英字を残す。

すべての ADR は、少なくとも「状態」「背景」「決定」「影響」を持つ。
開発記録は先頭に「文書情報」を置き、日付、種別、状態、現行資料への案内を明示する。

現行資料と過去記録が食い違う場合は、次の順で優先する。

1. 現行コード
2. `docs/` 直下の現行資料
3. 採用中の ADR
4. `docs/worklog/` の開発記録

## 影響

### 利点

- 初めて読む人が途中段階の提案を現行仕様と誤認しにくくなる
- 現行操作、設計判断、調査証跡を目的別に探せる
- 過去の詳細を削除せず、上位文書の読みやすさを保てる
- 新しい文書を追加する場所と書式を判断しやすくなる

### 欠点

- ファイル移動時に既存リンクとコード内の文書参照を更新する必要がある
- 過去記録の内容自体は古いため、現行資料への案内を維持し続ける必要がある
- 文書の役割が変わった場合は、移動だけでなく内容の再編集が必要になる
