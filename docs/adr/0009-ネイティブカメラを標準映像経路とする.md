# ADR 0009: ネイティブカメラを標準映像経路とする

## 状態

2026 年 8 月 3 日に承認し、2026 年 8 月 6 日までに基本実装と実機安定化を完了。

## 背景

ADR 0008 では、標準 Atom アプリと既存録画を維持するため、ベンダーカメラ実行環境を
任意の互換機能として分離した。この方式は互換性を得られる一方、既存の巨大な実行環境、
不透明な起動順序、メモリ消費、独自ネットワーク処理、映像チャンネルの競合を抱える。

本プロジェクトの通常用途では、次を優先する必要がある。

- Nerves が映像処理の起動、停止、監視、復旧を直接管理できる
- RTSP を標準的なクライアントから利用できる
- 限られたメモリで必要な処理だけを動かせる
- 障害時に SSH と更新経路を維持できる
- JPEG、夜間切替、状態表示を小さな管理可能な実装で提供できる

2026 年 8 月 3 日の段階的な試作で、センサー、ISP、H.264 エンコーダー、
`v4l2loopback`、RTSP の経路をベンダーアプリ本体なしで動かせることを確認した。

## 決定

通常の映像経路として `Atomcam2NervesApp.CameraNative` を採用する。

`CameraNative` は次を管理する。

- カメラ、音声、エンコーダーに必要なカーネルモジュールの読み込み順序
- `atomcam2-camd` の起動と監視
- H.264 を受け取る `/dev/video0`
- `v4l2rtspserver` の起動と監視
- RTSP の SDP に復号用情報が含まれることの確認
- 異常が継続した場合の映像経路全体の再構築
- JPEG スナップショット、夜間ビジョン、OSD、実測 FPS

ネイティブカメラは既定で自動起動する。次の設定がある場合だけ無効にする。

```text
/data/atomcam2-native-camera/auto-start.conf
```

```text
enabled=false
```

JPEG と H.264 は別のエンコーダーチャンネルを使用し、状態画面の JPEG 更新が H.264
配信のバッファーへ直接競合しないようにする。

ベンダーカメラ実行環境は削除しない。標準 Atom アプリと既存の一分単位 MP4 録画が
必要な場合の任意互換機能として維持する。ただし、ネイティブカメラと同じハードウェアを
使用するため、両方の同時運用は保証しない。

現在のネイティブカメラは連続 MP4 録画を提供しない。NAS 転送は、ベンダー互換機能が
生成した完了済み録画を対象とする。

## 影響

### 利点

- 映像処理の責務と再起動条件を Nerves から観測できる
- ベンダーアプリ全体を起動せず RTSP を提供できる
- 不要な処理を減らし、限られたメモリを使いやすくなる
- JPEG、H.264、状態画面、夜間切替の競合を個別に修正できる
- 異常な RTSP を検出し、電源断なしで再構築できる

### 欠点

- 標準 Atom アプリの互換機能はネイティブ経路に含まれない
- ネイティブ経路だけでは連続 MP4 録画を生成できない
- `libimp`、センサー、ISP、カーネルモジュールの機器固有知識が必要
- 映像と音声の安定化には実機での起動順序検証が必要
- 二つのカメラ経路を維持するため、境界を文書で明示し続ける必要がある

## 実装上の制約

- カメラと音声のモジュールは検証済みの順序を維持する
- `atomcam2-camd` の変更時は Buildroot の再構築条件を確認する
- RTSP の単純なポート接続だけでなく、SDP の内容まで健全性判定に含める
- 状態画面の読み取り要求で映像処理を過負荷にしない
- ベンダー互換機能へ切り替える前後では機器を再起動する
- ネイティブ録画を追加する場合は、録画形式、分割、破損時の扱い、容量管理を別の ADR で決める
