# 2026-08-12 RTSP 音声追加 提案書

現在の RTSP 配信(`rtsp://<ip>:8554/video0_unicast`)は映像(H.264)のみ
で、内蔵マイクの音声は含まれていない。マイクの音声も同じ RTSP
セッションで配信できるようにする方式を調査・検討した。

> **状態(2026-08-13 更新): 実装・実機検証・マージ完了**(commit
> `757aa2b`)。本文中の設計検討・実装方針はそのまま経緯として残すが、
> 「実装はまだ行っていない」は既に過去のもの。検証結果は末尾の
> 「検証計画」章、副産物として見つかった不具合の調査・修正は関連文書
> (参考章)を参照。

## 背景

- RTSP 配信は `v4l2rtspserver`(`package/v4l2rtspserver/`、upstream:
  `mpromonet/v4l2rtspserver`)が `camd` の書き出す v4l2loopback デバイス
  (`/dev/video0`)を読んで配信している。`camera_native.ex` が
  `/usr/bin/v4l2rtspserver` を直接子プロセスとして起動する
  (iCamera_app 非依存のネイティブパイプライン、[[atomcam2-approach-b]])。
- マイクは既に動作実績がある: `package/atomcam2-boot-announce/airec.c`
  が `libimp` の `IMP_AI_*` API で **8kHz/16bit/mono** の PCM をポーリング
  取得し、ダッシュボードの「動作確認」タブ「マイク録音(5秒)」/
  「録音を再生」で実機確認済み([[atomcam2-gpio-peripherals]])。ただし
  これは**5 秒間だけ動いて終了する one-shot プロセス**で、常時ストリー
  ミングはしていない。
- `package/v4l2rtspserver/0002-video-only-makefile.patch` に明記されて
  いる通り、**この v4l2rtspserver ビルドは音声を意図的に除外している**。
  理由: upstream の音声キャプチャは ALSA 前提だが、**この機体の制御
  カーネルは ALSA ドライバを持たず OSS(`/dev/dsp`)のみ**を提供する
  (制御カーネルの差し替えは禁止、[[atomcam2-control-kernel]])。これが
  音声未配信の直接の原因。

## 目的

- RTSP クライアント(VLC 等)で映像と同時にマイク音声を聴取できるように
  する。
- 既存の映像配信(camd → v4l2loopback → v4l2rtspserver)の安定性を
  損なわない。87MB RAM の機体でのメモリ・CPU 余裕を大きく食わない。

## 現状のマイク音声パス(既存資産)

```
libimp IMP_AI (dev=1, chn=0)
  ← IMP_AI_SetPubAttr(8000Hz/16bit/mono, numPerFrm=400, frmNum=40)
  ← IMP_AI_PollingFrame → IMP_AI_GetFrame (blocking polling loop)
  → airec: そのままファイルへ fwrite (one-shot, 既定 5 秒で終了)
```

`aoplay`(発声・再生側)と PCM フォーマットが揃っているため、録音した
そのままの形式で `atomcam2-aoplay` から再生できる、という対称設計に
なっている。今回はこの取得ループを**常時稼働**させ、**RTSP へ流し込む**
方向に拡張する。

## 制約・前提

- **制御カーネルは差し替え禁止**([[atomcam2-control-kernel]])。カーネル
  側に ALSA ドライバを追加する選択肢は無い。ユーザ空間だけで完結する
  方式に限られる。
- 87MB RAM。新規常駐プロセス・追加ライブラリの footprint は小さく
  保つ必要がある。
- IMP_AI デバイス(dev=1)は排他アクセスと見られる(`airec` のコメント
  に「iCamera_app 停止時に使うこと」とあり、同時に複数プロセスが
  掴めない前提の実装)。既存の「マイク録音(5秒)」ハードウェアテストと
  の競合を考慮する必要がある(後述)。
- v4l2rtspserver は 3 件の自前パッチを既に保守しているプロジェクトの
  ローカルフォーク運用([[atomcam2-build-toolchain]] 的な位置づけ)。
  4 件目のパッチを追加すること自体は既存の運用パターンの延長線上。

## 検討した方式

### 方式 A: alsa-lib + alsa-plugins(OSS I/O プラグイン)で ALSA 互換層を追加

alsa-lib はカーネルドライバ不要のユーザ空間ライブラリで、
`alsa-plugins` の OSS I/O プラグイン(`pcm.oss` / libasound の
`io_plug`)を使うと `/dev/dsp` を ALSA の PCM キャプチャデバイスとして
見せかけられる。これが機能すれば、v4l2rtspserver 本来の ALSA 音声
キャプチャパス(`-A <device>` オプション)を**ほぼそのまま**有効化する
だけで済み、live555 側のコード修正は不要になる。

- 長所: 自前で RTSP/live555 のコードを書かずに済む。upstream の
  実績あるパスをそのまま使える。
- 短所: alsa-lib・alsa-plugins を Buildroot へ新規追加する必要があり
  (この uClibc/MIPS ツールチェーンでのクロスビルド実績が本プロジェクト
  内に無い)、OSS ラッパー経由の遅延・ブロッキング特性が未検証。
  ライブラリ追加分だけ rootfs サイズ・RAM footprint が増える。
  `0002-video-only-makefile.patch` を書いた当時に「OSS しか無いので
  ビルドしない」と判断した経緯があり、この方式はその判断を覆すだけの
  技術検証(alsa-plugins の OSS プラグインがこの機体で実際に動くか)
  が必要で、調査コストが読みにくい。

### 方式 B(推奨): 常駐音声キャプチャデーモン + v4l2rtspserver への最小パッチ

ALSA を経由せず、**既存の `IMP_AI` 直叩きパスをそのまま常時稼働**させ、
v4l2rtspserver 側には「ファイル/FIFO から読んだ音声を RTP で流す」
という **ALSA 非依存の音声サブセッション**を追加する。

1. **`atomcam2-aicap`(新規、`airec.c` を常駐化した派生)**:
   `IMP_AI_PollingFrame`/`GetFrame` のループを one-shot ではなく
   無限ループにし、取得した 16bit PCM フレームを **G.711 μ-law** へ
   その場でエンコード(除算・テーブル参照だけの軽量処理、追加ライブラリ
   不要)して名前付きパイプ(例: `/tmp/camd-audio.fifo`)へ書き出す。
2. **v4l2rtspserver への追加パッチ**(`0004-audio-fifo-subsession.patch`
   のようなファイル名を想定): live555 の `ByteStreamFileSource`
   (`FILE*` を渡せる、FIFO でも問題なく動く)で FIFO を読み、
   `SimpleRTPSink::createNew(env, rtpGroupsock, 0 /* PT=PCMU */, 8000,
   "audio", "PCMU", 1)` で音声サブセッションを構成し、既存の映像
   サブセッションと同じ `ServerMediaSession` に追加する。upstream の
   ALSA 音声パスも最終的には同じ `SimpleRTPSink`/PCMU 出力に行き着く
   実装なので、**キャプチャ元を ALSA から FIFO に差し替えるだけ**の
   比較的小さい差分で済む見込み。
3. RTSP の `DESCRIBE` 応答に `m=audio` 行が追加され、対応クライアント
   (VLC / ffplay 等)は自動的に映像・音声を両方受信する。

- 長所: 新規の重量級依存ライブラリが不要。G.711 は 8kHz/mono に対して
  十分な品質で帯域も小さい(64kbps)。既存の `IMP_AI` 連携コード
  (`airec.c`)をほぼそのまま土台にでき、動作実績のある API 呼び出し
  順序を再利用できる。
- 短所: live555/v4l2rtspserver の C++ コードへの自前パッチ開発・保守
  コストが発生する(ただし本プロジェクトは既に同種のパッチを 3 件
  保守しており、初めての試みではない)。

### 比較表

| 観点 | 方式 A(ALSA 互換層) | 方式 B(FIFO + 自前パッチ、推奨) |
| --- | --- | --- |
| カーネル変更 | 不要 | 不要 |
| 新規ライブラリ | alsa-lib + alsa-plugins(未検証) | なし |
| live555 への変更 | 不要(既存 `-A` パスを有効化) | 音声サブセッション追加パッチが必要 |
| 既存資産の再利用 | v4l2rtspserver 側のみ | `airec.c` の IMP_AI 連携をそのまま活用 |
| footprint 増加 | ライブラリ分(未知) | ほぼゼロ(FIFO + ルックアップ計算のみ) |
| 技術的な不確実性 | OSS ラッパーの実動作が未検証 | ByteStreamFileSource の FIFO 読みは live555 の標準機能で実績多数 |

## 推奨方式

**方式 B(常駐 `atomcam2-aicap` + v4l2rtspserver への FIFO 音声パッチ)**
を推奨する。理由:

- 制御カーネル差し替え禁止という制約下で、方式 A が前提とする
  「OSS→ALSA 変換が実機で正しく動く」保証が無く、検証コストが読めない。
- 方式 B は本プロジェクトが既に確立している 2 つのパターン
  (① `libimp` 直叩きの小さな C バイナリを増やす、② v4l2rtspserver へ
  小さな自前パッチを重ねる)の組み合わせで、過去の実績と一貫性がある。
- G.711 は品質・帯域ともにマイク用途(会話・環境音の確認)に十分で、
  実装がシンプル。

## 実装方針(詳細)

1. `atomcam2-aicap.c` を `airec.c` から派生: `while (1)` ループ化、
   `numPerFrm=400`(400 サンプル = 50ms @ 8kHz)ごとに 16bit → G.711
   μ-law へエンコードして FIFO へ `write`。`mkfifo` は `pre-run` 相当の
   起動処理で作成。
2. `camera_native.ex`(または新規の小さな GenServer)に `aicap` の
   起動・監視を追加。`camd`/`v4l2rtspserver` と同様に子プロセス管理し、
   落ちたら再起動する(既存の `rtsp_pid` 監視パターンを踏襲)。
3. v4l2rtspserver 側パッチ: `main.cpp`/`V4l2RTSPServer` に
   `ServerMediaSubsession` を 1 つ追加する最小差分。既存の 3 パッチと
   同様、Buildroot の `V4L2RTSPSERVER_VERSION` ピン(コミットハッシュ
   固定)は変更せずパッチ適用のみで対応。
4. **既存のハードウェアテスト「マイク録音(5秒)」との排他制御**:
   `aicap` が IMP_AI デバイスを常時保持するため、同時に `airec`
   (one-shot)を起動すると `IMP_AI_Enable` が失敗する見込み。対応案:
   - (a) `aicap` 常駐後は「マイク録音」ボタンを削除し、RTSP 音声で
     代替する(シンプル、ただし単体テストの手軽さが下がる)。
   - (b) `HardwareTest.mic_record/0` 実行時だけ `aicap` へ一時停止
     シグナルを送り、録音完了後に再開する(複雑だが両立できる)。
   - **採用: (a)**。ダッシュボードの「マイク録音(5秒)」/「録音を
     再生」ボタンと `HardwareTest.mic_record/1`/`mic_play/1`、対応する
     `/test/mic/record`・`/test/mic/play` ルートを削除し、動作確認は
     RTSP 音声(本提案の配信そのもの)で代替する。単体テストの手軽さは
     下がるが、`aicap` 常駐との衝突を実装レベルで作らずに済む方を
     優先した。`atomcam2-airec`/`atomcam2-aoplay` バイナリ自体
     (`package/atomcam2-boot-announce/`)は rootfs から削除せず残す
     (手動デバッグ用途に残しても実害が無いため)。

## 実装時の変更点(G.711 → 生 L16)

実装(`package/atomcam2-aicap/atomcam2-aicap.c` /
`package/v4l2rtspserver/0004-fifo-audio-source.patch`)では、上記の
G.711 μ-law 案から**エンコード無しの生 PCM(RTP `audio/L16`)**へ変更した。
`IMP_AI` が出す 16bit PCM をネットワークバイトオーダ(ビッグエンディアン)
へ swap するだけで FIFO に書き出し、v4l2rtspserver 側もそれをそのまま
`SimpleRTPSink` の L16 として送出する(`PT=PCMU`/`SimpleRTPSink` ではなく
動的ペイロードタイプの L16)。

- 理由: μ-law のテーブル参照・量子化を丸ごと省略でき、`aicap.c` が
  さらに単純になる。帯域は 64kbps → 128kbps に増えるが、LAN 配信・
  8kHz/mono という規模では無視できる差。
- 影響: 検証計画のデコードコマンド、`SDP`/`RTPMAP` の中身
  (`PCMU/8000` ではなく `L16/8000`)が変わる。品質・実装コストの
  トレードオフとしては当初の G.711 案より単純な方向への変更であり、
  「推奨方式」章の結論(方式 B 採用)自体には影響しない。

## リスク・懸念点

- **IMP_AI 排他アクセス**: 上記の通り、既存のマイク録音テストとの
  競合を設計で解消する必要がある。
- **音声・映像の同期**: `camd`(映像)と `aicap`(音声)は別プロセスで
  タイムスタンプ生成の仕組みが異なる。RTP のタイムスタンプ整合が
  取れないと口パクのようにズレる可能性があり、実装時に要検証。
- **RAM/CPU 余裕**: 87MB RAM の機体で新規常駐プロセスを追加する。
  G.711 エンコードは軽量だが、FIFO のブロッキング読み書きが
  `camd`/`v4l2rtspserver` の動作(特に v4l2rtspserver の RTSP
  イベントループ)に悪影響を与えないか実機で確認が必要。
- **live555 自前パッチの保守コスト**: `V4L2RTSPSERVER_VERSION` の
  upstream 追従時にパッチが当たらなくなるリスク(既存 3 パッチと同種の
  リスクであり、新規に増えるものではないが件数は増える)。
- **音量・ノイズ**: `IMP_AI_SetGain`/`SetVol` の既定値をそのまま流用
  する想定だが、常時配信では録音時とは異なる聞こえ方になる可能性が
  あり、実機での聞き取り確認が必要。

## 非目標

- ステレオ化・高音質化(AAC 等)は対象外。まずは既存フォーマット
  (8kHz/mono)を G.711 化するだけに留める。
- 双方向音声(トークバック機能、スピーカーへの逆方向配信)は対象外。
  今回はマイク → RTSP の一方向のみ。
- 方式 A(alsa-lib 導入)の実装は今回は行わない。方式 B が実機で
  致命的な問題(同期が取れない等)にぶつかった場合の代替候補として
  記録に残すのみ。

## 検証計画

1. ✅ `atomcam2-aicap` 単体で FIFO に書き出された生 PCM(S16_BE)データを
   `ffmpeg -f s16be -ar 8000 -ac 1 -i /tmp/camd-audio.fifo out.wav`
   等でデコードし、正しく聴取できることを確認(実装が G.711 から
   生 L16 に変わった経緯は「実装時の変更点」章を参照)。
2. ✅ v4l2rtspserver パッチ適用後、`DESCRIBE` の SDP 応答に `m=audio`
   行が追加されることを確認(`curl`/`nc` での RTSP セッション手動発行、
   または VLC のメディア情報表示)。
3. ✅ VLC/ffplay で `rtsp://<ip>:8554/video0_unicast` を開き、映像と
   音声が同時に再生され、大きなズレが無いことを確認(ユーザ実機確認、
   2026-08-13)。
4. ⚠️ **数時間の長時間配信**でのメモリリーク・音声の途切れ・ドリフトの
   有無は今回未実施(短時間の複数回再起動確認のみ)。長期運用での再現性
   確認は今後の課題。
5. ✅ ダッシュボードの「マイク録音(5秒)」/「録音を再生」ボタン・ルート
   (上記「実装方針」4. で削除済み)が残っていないこと、
   `HardwareTest`/`Router` に旧コード・デッドコードが残っていないことを
   確認済み。
6. ✅ カナリヤ機([[atomcam2-canary-device]])含む**独立した実機 2 台**
   (192.168.1.77、192.168.222.56)で確認済み。

**まとめ(2026-08-13)**: 音声機能は実機で動作確認済み、本採用してよいと
判断し commit `757aa2b` としてマージ済み。検証の過程で見つかった
「映像がすぐ表示されない」問題は音声機能とは無関係な既存の
`v4l2rtspserver` sprop 捕捉レースと判明し、別途調査・修正
(commit `acbab4b`、
[映像信頼性・sprop 捕捉機構特定 技術相談](20260813_video信頼性_sprop捕捉機構特定_技術相談.md))。
そちらの調査中に見つかった `v4l2rtspserver` epipe クラッシュループの
watchdog 自己増幅問題も別途修正済み(commit `34e2ff9`、
[epipe クラッシュループ 技術相談](20260813_v4l2rtspserver_epipeクラッシュループ_技術相談.md))。
